## Project status

**Phase 1–20 done — the whole backend (scaffolding + domain model + application ports/use cases + PostgreSQL persistence + transactional outbox relay → Kafka + inbound REST/Kafka/callback adapters + SMS provider adapters + routing/channel/provider/quota configuration in the DB + templates and personalisation + filtering and compliance + Email + Push + observability/security/operations + admin REST BFF + testing and acceptance + Keycloak and the removal of the unauthenticated mode) and the whole frontend (Phase 16 scaffolding, Phase 17 screens, Phase 18 testing). The plan has no phase left, and the two Phase-15 debts are closed (Phase 20, below).** `domain/` holds the full model (`model/{vo,type,content}`, aggregates, `service/{SegmentCalculator,Router,FallbackChain}`, `support/{Guard,UuidV7}`) with 291 unit tests at ~97% line coverage; `application/` holds `port/in` + `port/in/{command,query}`, `port/out` (+`port/out/provider`), `service` (use cases) with `service/{pipeline,support}`, `dto/`, `mapper/`, `policy/`, 204 unit tests at ~87% line coverage; `adapter/` holds `out/persistence` (`config`, `messaging`, `delivery`, `template`, `audit`, `export`, `admin`, `json`, `crypto`, `support`), `out/kafka`, `out/metrics`, `out/time`, `out/secret`, `out/compliance`, `out/policy`, `out/provider/{support,playmobile,smsgate,smtp,fcm,apns,mock}`, `in/{contract,rest,admin,kafka,callback,importer,scheduler,security}`, `observability/`; `bootstrap/` adds `config/` and `health/`. 900+ unit tests and 160+ integration tests (Testcontainers — PostgreSQL, Kafka and Keycloak — WireMock, GreenMail) pass; everything tagged `integration` runs only via `./gradlew integrationTest`.

**Both Phase-15 debts are closed (Phase 20).** `adapter/in/scheduler` now holds `MessageDispatchScheduler` — one `@Scheduled` per traffic class, so TC-01 isolation is structural — and `ExpireMessagesScheduler`; rows are claimed with `FOR UPDATE SKIP LOCKED` plus a lease and released with a `next_attempt_at`, which is what finally gives `SendingPolicy.backoffFor` a caller (ADR-0039). The saga is split around the provider call: `DispatchPreparation` commits the guards, the route and the open attempt, the HTTP call happens in no transaction, and `DispatchSettlement` applies the answer to a freshly loaded aggregate — that also closes H2 of the audit, where a pod killed after the provider accepted turned one message into two SMS. Batch counters are `BatchProgressRecorder` with the rule *delta = contribution(after) − contribution(before)* over an atomic `applyProgress` (ADR-0040), so a repeated callback costs nothing and a DLQ retry subtracts by itself. `AcceptanceScenariosIT` no longer hand-drives the saga, and `DispatcherConcurrencyIT` proves two instances hand a message to the provider exactly once.

**Sending from the panel (Phase 20, ADR-0038).** The panel has its own section, `/api/admin/v1/send/*` — deliberately not a share of §8.2, which authorises by a machine token's stream claim, knows no `X-Commhub-Reason` and legitimately allows free content. Content comes **only from a published template**: neither `OperatorSendCommand` nor `OperatorBatchCommand` has a text field, so an unreviewed wording cannot reach a customer without changing the record. `PublishedTemplates` is the single place that rule lives, used by both the estimate and the send. `EstimateSend` prices the real list against the real configuration — rows rendered non-strictly, grouped by segment count, one `EvaluateRoute` call per group — and the screen refuses to send until an estimate for the current form state exists. A bulk send is an ordinary `Batch`; a row without `externalId` takes its identity from `sha256(file)+line`, so re-uploading the same file is `DUPLICATE` rather than a second SMS to everyone. `adapter/out/provider/mock` (ADR-0041, off by default, enabled only by the root `config/application.yml`) answers instead of a real provider on the local stand, with behaviour read off the address suffix — `…00` delivered, `…01` undelivered, `…02` no answer, `…03` blocking, `…04` unusable address.

Domain naming to keep straight: the `Channel` aggregate of spec §6.1 is the class `ChannelConfig` (the name `Channel` belongs to the channel enum), and a message carries `MessageContents` — content per channel (MP-02) — instead of a single `MessageContent`. Aggregates take instants as parameters; the domain never reads a clock — the application layer gets "now" from `ClockPort`.

Application-layer conventions worth knowing before adding to it: use case interfaces are named after the use case (`SubmitMessage`, `DispatchMessage`) and their implementations `…Service`; a rejection is never an exception but a verdict/result record carrying a `RejectionReason` (IR-01) — `NotFoundException` is the only business-ish exception; `MessagePipeline` is the single entry point to the stages (dedup → template → validate → route → filters → quotas) so a single message, a batch item and a DLQ retry all traverse the same path; use cases append to `OutboxPort` and never publish directly (AD-03). Every record stays at ≤ 8 components — Checkstyle's `ParameterNumber` covers record headers too. Query use cases are separate from commands: `GetMessage`/`GetBatch` take a record from `port/in/query`, open a read-only transaction and return a `…View` DTO that deliberately carries no content and no recipient address. Spring beans are wired by component scan; the persistence ports and `ClockPort` are implemented since Phase 4, `StatusPublisherPort` since Phase 5, `SecretResolverPort` since Phase 7, `ProviderStatsPort` since Phase 8, `FrequencyCounterPort`/`CustomerPreferencePort` since Phase 10, `PushDeliveryLogPort` since Phase 12, `MetricsPort`/`AuditQueryPort`/`EventExportRepository`/`AnalyticsPublisherPort` since Phase 13 and `KillSwitchPort`/`MessageSearchPort`/`StatisticsPort`/`SystemParameterPort` since Phase 14. Exactly two output ports are left without an implementation and both by design: `ProviderProbePort` (a placeholder, injected through an `ObjectProvider`, and SMS will never get one) and `AudienceResolverPort` (FR-8.11 is out of scope and nothing injects it) — `ApplicationContextIT` asserts that list, so a third one fails the build until it has an adapter. Three of the layer's `policy/` records are built from deployment settings in `adapter/out/policy` (dedup window, sending budget, health thresholds) the way the compliance ones are built in `adapter/out/compliance`, and the domain services (`Router`, `FallbackChain`, `SegmentCalculator`) are declared in `bootstrap/config/DomainServiceConfig` — the domain carries no annotations, so the component scan cannot find them. The application layer has **no logging dependency** on purpose — only `spring-context`, `spring-tx`, MapStruct and the domain — so anything worth reporting from a use case goes through `MetricsPort`, not a logger. Configuration administration follows the same shape as the rest of the layer with one deliberate exception: a `Manage…` use case groups the CRUD of one aggregate instead of being split into one interface per operation, because those operations share their transaction, their audit entry and their cache invalidation. Their rejections are exceptions, not verdicts — `ConfigurationConflictException` (409) and `NotFoundException` (404) — because a contradictory configuration edit is an operator mistake in an interactive session, not traffic the Bank's systems have to handle (IR-01 is about the pipeline).

Three fixes came out of that phase and are worth knowing. **A Russian justification never left the browser**: an HTTP header value is a byte string, so `X-Commhub-Reason: разобрано вручную` throws when the request is built. ## Build, test, run

Gradle wrapper 9.7.0; Java 25 toolchain (Gradle downloads JDK 25 via foojay if it is not installed locally — the machine's default JDK may be newer).

```bash
./gradlew build                     # compile + spotlessCheck + checkstyle + unit tests + ArchUnit
./gradlew spotlessApply             # auto-format (palantir-java-format) — run before committing
./gradlew integrationTest           # tests tagged "integration" (Testcontainers; needs Docker)
./gradlew :bootstrap:bootRun        # run the app (needs docker compose up first)
./gradlew :bootstrap:bootJar        # -> bootstrap/build/libs/notification-hub.jar
./gradlew :domain:test              # single module

docker compose up -d                # PostgreSQL 5432, Kafka 9092, Schema Registry 8081, Kafka UI 8090,
                                    # Keycloak 8180 (realm commhub, demo/demo),
                                    # WireMock 8089, GreenMail 3025/3143/8085
                                    # (the email ITs start their own GreenMail on a dynamic port —
                                    #  no Docker needed, and no clash with the compose one)
docker compose down -v
```

Tests tagged `integration` are excluded from `test` and only run via `integrationTest` — tag every Testcontainers/WireMock test with `@Tag("integration")` and name it `*IT`. There is no CI pipeline in the repo (removed deliberately): run `./gradlew build` and `./gradlew integrationTest` locally; SAST/dependency scanning (SEC-09) belongs to the Bank's own pipeline.

Versions live in `gradle/libs.versions.toml` (Spring Boot 4.1.0, MapStruct, ArchUnit, Resilience4j, Spotless, Checkstyle); everything else is managed by the Spring Boot BOM — do not pin versions in module build files. Checkstyle config: `config/checkstyle/checkstyle.xml` (it mechanically enforces the no-`var` and constructor-injection rules); suppressions in the adjacent `suppressions.xml`.

Flyway migrations: `adapter/out/persistence/src/main/resources/db/migration`, schema `comm_hub`, `V<n>__<snake_case>.sql`. `FlywayMigrationIT` checks the schema still builds from scratch (DB-01).

Outbox relay (Phase 5): use cases only ever `OutboxPort.append` inside their transaction (the payload is the sealed `OutboxPayload` — a status event or, since Phase 12, an invalidated push token); `PublishOutboxEventsService` claims rows with `FOR UPDATE SKIP LOCKED`, publishes through `StatusPublisherPort`, and sets `published_at` **only after the broker acked** — never reorder those two. A publication failure stops the pass (status order per message beats throughput) and leaves `attempts`/`last_error` on the row. `adapter/out/kafka` owns the producer (`acks=all`, idempotent) and `StatusEventCodec`, which writes the flat §6.4 JSON field by field because that record would exceed 8 components; its field list must stay in step with `resources/schema/comm.outbound.status.v1.json` (a test asserts it). `adapter/in/scheduler` only ticks the use case. Kafka settings live under `commhub.kafka`, not `spring.kafka` — Boot 4's Kafka autoconfig module is not on the classpath.

Message content is encrypted at rest (DB-04): `persistence/crypto` holds `ContentCipher` (AES-256-GCM, app-level rather than pgcrypto) and `ContentCodec`, and `message.contents` / `message.template_variables` go through it — stored as the JSON scalar `"CH1.<keyId>.<base64url>"`, with cleartext still readable. `recipient` deliberately stays in clear (GIN index, DB-05). Encryption is on by default and a missing `commhub.persistence.encryption.keys.<activeKeyId>` fails startup — never "fix" that by disabling it. The one exception is local development: `config/application.yml` at the repository root supplies a known local key. Spring Boot reads `./config/application.yml` relative to the **working directory**, and that differs by launch path — `bootRun` works in the `bootstrap` module directory, an IDE Spring Boot run configuration defaults to the project root — so `bootstrap/config/application.yml` sits next to it and does nothing but `spring.config.import` the root one; the value lives in exactly one file. Encryption stays on, an exported key still wins, and neither file reaches the jar (`config/` is not a resource directory) or the image (the runtime stage copies only the jar) — so the container and a jar started outside the source tree keep failing without a real key. `.run/Notification Hub (local).run.xml` is the shared IntelliJ configuration, which pins the working directory and the key explicitly.

Inbound conventions (Phase 6): §8.2 says the REST body *is* IK-03, so one package parses it for both transports — `adapter/in/contract` (payload records in `dto`, MapStruct `InboundPayloadMapper`, `InboundMessageCodec`/`InboundBatchCodec` over its own `InboundJson`). The IK-03 root is read field by field because its thirteen fields exceed the 8-component record limit — the inbound mirror of `StatusEventCodec`; only the nested blocks are bound by Jackson. There is no bean validation: the domain value objects own the rules and the codec adds only what they cannot see, raising `InboundContractException` with a field pointer that both transports render (REST → `problem+json`, Kafka → `comm.inbound.parse-error.v1` headers). **The traffic class comes from the Kafka topic and overrides the document** — TC-01 isolation is built from topics, one container factory and thread pool per class in `KafkaConsumerConfig`. A pipeline *rejection* is a verdict, never a listener failure or a 202: listeners log it and commit, REST turns it into `problem+json` via `rest/problem/ProblemType` (IR-01). Advices live one-per-concern in `rest/handlers` (+ `callback/handlers` for the 403); `UnexpectedFailureHandler` must stay ordered last. The OpenAPI 3.1 contract is hand-written in `adapter/in/rest/src/main/resources/openapi/` (admin contract — in `adapter/in/admin/.../openapi/`) and kept honest by `OpenApiContractTest` — springdoc has no Boot 4 release; swap in generation when it does. `ProviderCallbackTranslator` implementations live in the provider adapter packages (AR-04) — the callback endpoint itself is provider-agnostic.

Provider adapter conventions (Phase 7): `adapter/out/provider/support` owns everything that is not provider-specific — the JDK HTTP client on virtual threads with mandatory connect/read timeouts (`ProviderRestClients`), retry + circuit breaker per provider (`ProviderCallExecutor` over plain Resilience4j registries, no AOP starter), throughput and per-recipient ceilings (`ProviderThrottle`), and log masking (`Masking`). **The contract with the executor is the load-bearing rule:** a provider call *returns* a `ProviderAck` for any answer the provider gave and *throws* `ProviderCallException` only when there was none — retry and the breaker key off the exception alone, so a stream of content rejections never trips a breaker while a silent provider trips it fast. A blocking failure (Playmobile 102, SMS Gate 10–13) opens the breaker immediately; an open breaker answers a *retryable* ack so the message fails over instead of landing in the DLQ. Each provider package owns only its request shape and its error table (`PlaymobileErrorCatalog` §18.1, `SmsGateResponseCatalog`/`SmsGateStatusCatalog` §18.2), and its `ProviderCallbackTranslator` lives there too — status vocabulary belongs next to error vocabulary. Playmobile retries inside a delivery attempt because the Hub generates its `message-id`; SMS Gate deliberately does not, because `/api/v2/send` takes no client id and a retry would be a second SMS. Two departures from the §18.2 table are intentional and documented in code: FEEDBACK code 6 (Unknown) is applied as nothing and left to `SmsGateReconciler` (SG-03), and code 7 (InBlackList) becomes `UNDELIVERED`, not `REJECTED` — ST-01 has no such transition from `SENT_TO_PROVIDER`. Provider settings under `commhub.provider.<code>` are the deployment defaults; since Phase 8 the throughput limits come from `provider.rate_limit_config` and the sending knobs (originator/sender, priorities, weights, default TTL) from `provider.endpoint_config` via `ProviderRuntimeSettings`. Credentials never moved — they stay refs resolved by `adapter/out/secret` (ADR-0036: `env:NAME` is the contour's source and `prop:key` a Spring property, either may carry a `base64:` modifier for a multi-line blob such as the FCM service account or the APNs `.p8`; scheme-less is a `commhub.secrets.values` literal for the local stack and the tests; the env lookup goes through `System.getenv`, never Spring's `Environment`, so a yaml key of the same name cannot beat the variable. There is no secret directory and no `file:` scheme — the TTL cache keeps a per-message call away from the lookup, it no longer applies a rotation, and rotating a credential is a rolling restart) — and neither did base URL, timeouts or breaker windows, which decide how the HTTP client is built. Everything an adapter shares with the others travels in one `ProviderSupport` record. The Hub never talks to Vault itself. **SMPP (PM-04) is deliberately not built** — rationale in `adapter/out/provider/package-info.java`.

Configuration conventions (Phase 8): routing configuration is read through `CachingProviderConfigRepository` (`@Primary`), which caches **only** `routingConfiguration(streamId)` — the hot, read-only path — and delegates everything else straight to the database, because the administration use cases load an aggregate in order to mutate it and must never share a cached instance. A local write invalidates the snapshot immediately; other instances catch up within `commhub.config.cache.refresh-interval` (default 10s, capped at 30s by NF-07 and validated at startup), kept warm by `ConfigurationRefreshScheduler`. The same "read once per window" shape is used by `StreamLimits` (per-stream REST limits from `stream.rate_limit_config`, IR-02) and `ProviderRuntimeSettings` (limits + `provider.endpoint_config`); all three fall back to the deployed yaml when the registry has nothing or cannot be read — a limiter must never become the reason messages stop. Quotas are three dimensions, not one: `QuotaGuard` walks stream → channel → provider and `check`/`register` must always walk the same scopes. Provider health is passive (`ProviderStatsPort` over `delivery_attempt`): `DOWN` makes a provider unselectable so failover needs no extra code, and failback works through a probation step — after `recovery-after` of silence a `DOWN` provider returns to `UNKNOWN` (selectable, untrusted) because a provider without traffic can never produce the figures that would clear it. `EvaluateRoute` answers "which route would message X get" by building a throwaway `Message` and running the real `Router` against the real snapshot; never write a second simulation of the routing rules.

Template conventions (Phase 9): the template layer follows the Phase 8 shape — `ManageTemplates` groups the aggregate's CRUD, `GetTemplates` is the read side (card, catalogue page without bodies, preview), rejections are `ConfigurationConflictException`/`NotFoundException` rather than verdicts. Two rules stay in the domain and must not be re-implemented above it: **a locale has exactly one sendable version**, enforced by `Template.publishVersion` (publishing v2 archives v1; publication runs first so a maker/checker rejection leaves the previous version published), and **only a `DRAFT` may be rewritten** (`TemplateVersion.updateBody`) — a version on review is what a reviewer is looking at and a published one is what sent messages were rendered from. The author of a version and the reviewer of a publication come from the `Actor`, never from a command field (FR-4.2), and a nameless actor — the Hub — may do neither. Deleting a template is archiving it (`TemplateCatalogStatus`, `template.status`): its code sits in the history of every message rendered from it; an archived card keeps its versions and stops being sendable (`Template.isSendable`, checked by `TemplateApplier`). The admin preview (`renderPreview`/`missingVariables`) is deliberately *not* strict mode and *not* status-checked — it exists to be used on a draft, and an unfilled field stays visible as `{NAME}` and is listed — while the sending path stays strict (`TEMPLATE_VARIABLE_MISSING`). FR-4.4 costs come from the real `SegmentCalculator` and the real provider tariffs, quoted per provider with a `selectable` flag; never write a second segment calculation. The FR-4.6 import goes through the aggregate (`ImportTemplates` + `adapter/in/importer`, CSV columns by name, off by default behind `commhub.import.templates.enabled`), is idempotent by wording, reports bad rows and keeps importing, and needs an `approver` different from `author` to publish anything.

Compliance conventions (Phase 10): the filters themselves date from Phase 3 (`DeliveryFilters`, order suppression → consent → quiet hours → frequency cap); Phase 10 added what stands around them. **One place hashes an address** — `service/support/RecipientAddresses` — because the pipeline, the counters and the administration must agree on the hash or a ban silently matches nothing; SMS/EMAIL go through their value objects, a push token is opaque and hashed as-is. The suppression list has two lookup families that read alike and are not the same: `findActive…` is the sending path (channel *or* all-channels row, expiry applied) and `find…` is the administration path (one exact channel scope, expired rows included, because that is the row the unique index collides with). Automatic entries — a provider naming the address unusable (§18.2 codes 20/7), an email hard bounce (EM-02), later an invalidated push token — never go through `ManageSuppressions` but through `SuppressionRegistrar` (reached from the saga via `MessagePipeline.suppress`, and from `ProcessProviderStatus` via the new `ProviderStatusCommand.suppressAs`); it is idempotent by `saveIfAbsent` (`ON CONFLICT DO NOTHING`) and records the provider as `created_by`. A suppression consequence is applied **before and independently of** the status transition: "this address is dead" is a statement about the address, so a report that changes no status must still stop the next send. Quiet hours resolve client → stream → channel, and the client's window wins because it is the only one carrying the recipient's zone — that is the whole of the `localtime` support the Hub can honestly give (every accepted MSISDN is `9989…`, i.e. `Asia/Tashkent`, and the flag still travels to Playmobile). `frequency_counter` aggregates into hour buckets, not one row per send (§12.2 volumes), so its count is a documented ceiling; `RetentionSweepScheduler` is what keeps it and `dedup_registry` the size of their windows. PAN detection always counts a finding (`MetricsPort.panDetected`) and never logs the text; `PanPolicy` decides whether it also rejects, except on SMS where it always does, and template bodies are checked unconditionally. `CustomerPreferencePort` is a documented stub (FR-8.2) — do not turn it into a consent register. The two policies are built from `commhub.compliance` in `adapter/out/compliance` (`CompliancePolicyConfig`), which is also where that stub lives; quiet hours deliberately stay in the database per stream and channel (AD-07) and never move into the yaml. Administration REST for the list arrives with the rest of the admin BFF in Phase 14 — the use cases (`ManageSuppressions`, `GetSuppressions`) are ready and, like Phase 8/9, have no controller yet.

Email conventions (Phase 11): the SMTP adapter (`adapter/out/provider/smtp`) sits on the Phase 7 framework and keeps its contract — a relay that answered produces a `ProviderAck`, only a call without a verdict throws — but four things about email are genuinely different and shape the package. **The connection is the unit of cost**, so `SmtpTransportPool` keeps connections open and *its size is the concurrency limit of the channel*; a sender that finds none free gets a retryable ack (virtual threads make it trivial to offer a relay ten thousand connections, and a relay handed ten thousand connections stops relaying). **The Hub writes the `Message-ID`** (`IdentifiedMessage` overriding `updateMessageID`), carries the same value in `X-Comm-Message-Id`, and that single decision is what lets a bounce arriving hours later name its row. **There is no callback** — `EmailBouncePoller` reads the bounce mailbox over IMAP and feeds `ProcessProviderStatus` like any DLR (AD-06), which is why `return-path` stays deployment configuration and never moves into `provider.endpoint_config`: it has to name the mailbox the poller reads. **A rejection is usually about the address, not the relay**, so `SmtpResponseCatalog` throws only 4xx/auth (auth is blocking, the email version of Playmobile 102) and returns 5xx as rejections; both it and `BounceCatalog` suppress an address only on an explicit "no such mailbox" (`5.1.x`, `5.2.1`) — a spam filter's refusal of one wording must never cost a live customer address, and `delayed` reports are applied as nothing (ST-01 has no transition for "still trying", same call as SMS Gate code 6). DKIM (`DkimSigner`, RFC 6376 relaxed/relaxed rsa-sha256) is implemented and off by default; it signs the *serialised* message, never the model, and never calls `saveChanges()` after signing. Attachment ceilings (EM-01) are enforced at validation by `EmailPolicy`, not in the adapter — a pipeline rejection carries a canonical reason (IR-01) where an SMTP code carries none — and the bytes come from `AttachmentStore` (a mounted directory with a traversal check). Email templates carry an HTML alternative on the same `TemplateVersion.Body` (V11 `template_version.html_body`): text is always required, HTML only alongside it, and HTML on a non-email template is refused.

Push conventions (Phase 12): push is the one channel where a message has several addresses, and everything specific about it follows from that. **The fan-out lives above the port** — `service/support/PushFanOut` — so the saga keeps seeing one provider call with one answer (AR-05) while one submission per token goes out underneath; a single-device recipient stays on the calling thread, several devices go in parallel on virtual threads. Its aggregation rule is load-bearing: **one accepted device makes the message accepted** (the customer was notified; failing it because the tablet's token expired would be a lie to the source system), and when nothing was accepted the worst class wins — blocking > retryable > permanent — because that is the instruction the saga has to act on. Per-device detail is a row, not a log line: `push_delivery` (V12, monthly partitions like `delivery_attempt`) holds one row per token under the attempt's id, which is what PU-09's "aggregated per recipient, detailed per token" actually asks for, and what makes "how many iOS devices failed today" answerable. **A dead token has two consequences and both are mandatory** (`PushTokenRegistrar`): a suppression entry keyed by the token hash so the Hub stops, and `comm.outbound.push-token.invalidated.v1` so the system that registered it stops — only the second prevents tomorrow's campaign from paying for the same dead device again. That topic is the first outbound contract that is not a status, which is why `OutboxPayload` is now sealed over `MessageStatusEvent` and `PushTokenInvalidatedEvent`: a new outbound contract does not compile until it has a topic, a codec and a stored shape. The token travels in the event **in the clear** — the consumer's registry is keyed by it and a hash would name nothing — and is never logged. Adapter-side, both packages keep the Phase 7 contract (an answer is a `ProviderAck`, no answer throws) and both make the same call about refusals: a dead token, a bad payload, a throttle are *returned*, only 5xx and a refusal of the Hub's own credentials are *thrown*, so a campaign against ten thousand uninstalled applications never opens a breaker. Two classifications are deliberate and easy to get wrong: FCM answers `SENDER_ID_MISMATCH`/`THIRD_PARTY_AUTH_ERROR` with 401/403 although they describe the message, so "401 means bad credentials" is qualified by a message-level code list; and APNs `DeviceTokenNotForTopic` retires the token, because for the Hub it is as dead as an uninstalled app. `FcmAccessTokens` and `ApnsJwtProvider` are hand-written rather than library-backed (one signature and one form post each) and both drop their cached credential when the platform refuses it, so an expired one costs a message instead of an hour. APNs needs **no connection pool of ours** — the JDK client multiplexes and handles `GOAWAY`; the DER→JOSE conversion of the ES256 signature is the one piece of cryptography here that cannot be read off the specification. Sandbox is chosen **per message** from the TEST flag (PU-13), never per deployment, and FCM's equivalent is `validate_only`. Push is terminal at `SENT_TO_PROVIDER` (PU-12): neither platform reports delivery, and the phase-2 path for an application event is the existing `ProcessProviderStatus`.

Observability, security and operations conventions (Phase 13): **the application layer still has no logger and no metrics library** — everything it wants to report leaves through `MetricsPort`, and `adapter/out/metrics` is the only place that turns it into a number. Three kinds of thing live there and the split matters: the port implementation (what the pipeline reports), `CircuitBreakerMetrics` (state that belongs to an adapter — the core is not told when a breaker opens, because it is not its decision) and `BacklogMetrics` (**what is not moving**; counters describe events, a backlog is a state, and the age of the oldest unpublished outbox row is the only figure that tells a busy relay from a stopped one). Metric names and tag keys are an operational contract in `MetricNames` — the alert rules and dashboards shipped in `deploy/observability/` are written against them — while the *stage* names stay in the core (`service/support/PipelineStages`), because a stage is a statement about §5.1. Two latencies are measured and no more: `accept` (the ingress) and `accept-to-provider` (the p99 the OTP SLA of TC-01 is stated in, recorded on the attempt the provider accepted, so retries and failovers are part of the number); the provider leg is already timed by `MetricsPort.providerCall`, which wraps the *whole* answer the saga waits for, including the framework's retries and the push fan-out. **FR-7.4 is a dimension, not a deletion**: a test send carries `test=true` through the metrics and the mart contract, and dashboards and alerts filter on it — a configuration check has to stay visible to the operator who ran it. `adapter/observability` is neither in nor out (a correlation id is not a use case): `CorrelationIdFilter` gives every HTTP call the identifier of FR-8.6 — the header wins over the `correlationId` field of IK-03, because a body is parsed per message and a batch carries many — and MDC is opened around the *use case*, not around the log lines, so everything the pipeline writes is searchable by the same stream and batch. `LogMasking`/`PiiMaskingJsonCustomizer` are the safety net under the rule that masking happens where the value is written (`provider/support/Masking`), never a replacement for it; the customizer is instantiated by the logging system rather than the context, so it is in place before the first bean and survives a failed start. Security (`adapter/in/rest/security`) was off by default until Phase 19 replaced that with a local issuer (see below); `StreamAccessGuard` enforces SEC-01 where the stream is known (the path never names it), answers 403 rather than 404, and takes the entitlement from the token's stream claim. An identity from a token always beats the `X-Commhub-Actor` header, and `AuthenticatedCaller` separates a person (SSO groups → `Actor.operator`) from a machine (stream claim → `Actor.sourceSystem`) because that difference decides whether a lookup is journalled: SEC-08 audits an employee opening a customer's message, never a source system polling its own. The audit journal refuses `UPDATE`, `DELETE` and `TRUNCATE` in the database (V7) — a journal a test can empty is one an administrator can empty — so its tests are written to be indifferent to what is already in it. FR-6.4 exports **one row per finished message**, not per transition (the transition stream already exists as `comm.outbound.status.v1`), with a cursor over `(terminal_at, id)` in `export_cursor`, advanced only after the broker acked; it carries no recipient and no content, because what leaves for the analytical contour is what was sent, not to whom. The health groups of NF-05 are deliberately unequal: liveness knows nothing external (restarting a pod because PostgreSQL is down replaces an outage with a crash loop during it), readiness adds the database (an uncommitted submission is an unaccepted one), and the broker and provider indicators are published but kept *out* of both — the outbox exists so a broker outage does not stop ingest, and a provider is down on every pod equally.

Admin BFF conventions (Phase 14): the panel is its own API under `/api/admin/v1` (`adapter/in/admin`), one controller per section of §11.2, and it is deliberately not a share of `/api/v1` — §8.2 is a published contract the Bank's systems integrate against and may not be moved under them, while this is the backend of one SPA that ships with it, and the SEC-02 chain is applied to a prefix rather than to a list of endpoints somebody has to remember to extend. **The message card and the batch card answer exactly the §8.2 body**: the screen an operator reads during an incident and the answer the Bank's system polled are then the same document. Drill-down from a batch to its messages is the message list with a `batchId` filter, never a nested endpoint — same paging, same masking, same SEC-08 entry. Three decisions live in this layer and nowhere below it. **Who may call what** is `@PreAuthorize` from `support/AdminAuthority`, written once per section (a mistyped role is neither a compile error nor a test failure, it is an endpoint nobody can reach or one everybody can), and the expressions carry no escape hatch: the `@adminAccess.open()` prefix and `AdminAccess` itself are gone (ADR-0037). Authentication sits on the chain and authorisation on the method, and both are needed: 401 is "who are you", 403 is "may you". **How much of an address a role sees** is `support/AdminMasking` on the way out — never in the query, which has to compare full addresses to find anything (DB-05), and never in the application layer, which knows nothing about roles. **What a period defaults to** is `support/AdminPeriod`: `message` is partitioned by `accepted_at` (DB-02), so a screen opened without one would scan every partition retention kept, and screens get opened without one exactly when somebody is in a hurry — hence a 24h default and a 92-day ceiling. Paging is offset-based on purpose (a person jumps to page seven and sorts; the only thing that cannot tolerate drift is the export, and the export walks the query to the end instead of paging). SEC-08 now covers search: one audit entry per search, not per row, and its entity is the **address hash** rather than a message id — that is what makes "who has been looking at this customer" one indexed query, and a raw address in an append-only journal would be a second store of customer addresses with no retention story. Jackson 3 refuses to map an absent field onto a primitive, so optional `boolean`/`int` in request bodies are boxed and defaulted in the compact constructor — a body without `includeCriticalOtp` is exactly what releasing the kill switch looks like. The kill switch itself is `kill_switch` (V14, one row) read through a TTL cache with the routing-configuration window, because it is read on **every** submission and again on every dispatch; its one departure from every other cached read is that an unreadable table does **not** fall back to "nothing is stopped" — everywhere else a failed configuration read falls back to the deployed default so a limiter never becomes the reason messages stop, and here the polarity is reversed. Exports are the same query as the screen, rendered by `support/CsvRenderer` (UTF-8 with a BOM so Excel does not mangle Cyrillic, and a leading apostrophe on `= + - @` so a cell is not a formula); the audit export announces its 50 000-row ceiling in `X-Commhub-Truncated`, because an unannounced cap is a file that looks complete. XLSX is deliberately not produced. CSV *reading* lives in `in/importer/CsvRecords`, shared by the template and suppression imports, so there is one RFC 4180 parser rather than two that will disagree about a quoted newline. The dashboard is one answer to one question (it is polled by every open tab) and carries no alerts — Alertmanager already evaluates OBS-04 and knows about pods that stopped scraping, which a database query cannot see. `AnalyticsJdbcClient` finally uses DB-06: the heavy panel reads go to the replica when one is configured, chosen explicitly rather than by transaction attribute, because silent routing turns replication lag into "the data is missing". Users and roles are absent from the administration section and §11.2 allows it — the Hub stores no users and no passwords (§10.1); identity comes from the corporate SSO and the group→role mapping is deployment configuration. One endpoint here answers from the container rather than from the database and is the only one of its kind: `GET /providers/adapters` (ADR-0042) lists the `(adapterType, channel)` pairs of the channel-port beans this contour deployed, read through `GetDeployedAdapters` → `ProviderGateway.deployedAdapters()` — the same `ObjectProvider`s a routed message is matched against, so a type the form offers is a type the send will resolve. It is ADMIN (narrower than `GET /providers`, whose widening to `TEMPLATE_MANAGER` is about provider *codes*), carries no reason header and no audit entry, is not transactional and is not cached; `adapterType` stays `type: string` in the contract because an `enum` would freeze AR-04 into a published document. Registration deliberately still accepts any syntactically valid type — the deployed set is a property of the pod, and a profile may legitimately be created before its adapter ships. **The hand-written contract's enums are pinned to the domain enums** by `AdminOpenApiContractTest.enumsMatchTheDomain`, and that test exists because they had silently diverged: the yaml and the SPA spoke of `IN_REVIEW`/`REJECTED` template statuses (and `INVALID_ADDRESS`/`BLACKLISTED` suppression reasons) that neither `TemplateStatus`/`SuppressionReason` nor the `CHECK` constraints have, so the panel's "to review" button answered 400 forever and no test in any layer crossed the boundary where the two vocabularies met. A value travels out as `…name()` and comes back through `AdminValues.requiredEnum`, so a name the document invents is an endpoint nobody can call and a name it omits is a value nobody can render — add a schema to `ENUM_SCHEMAS` whenever a domain enum reaches the contract. The same drift was found again in `BalancingStrategy`, and for the same reason: it was written *inline* in five places (`ChannelConfig`, `ChannelRequest`, `StreamDefaults`, `RoutingAction`, `RouteEvaluation`) rather than as a named schema, so `ENUM_SCHEMAS` — which keys off schema names — could not see it, and the contract's `PRIORITY` had no counterpart in the domain's `PRIMARY_ONLY`. It is now one named schema everything refs, and it is pinned; an enum inlined into a property is an enum nothing checks. `bootstrap/.../admin/TemplateWorkflowIT` walks the FR-4.2 path over HTTP with two real Keycloak users for the same reason.

Authentication conventions (Phase 19): **the admin panel is behind OIDC on every contour and there is no configuration that opens it** (ADR-0037). `spring.security.oauth2.resourceserver.jwt.issuer-uri` is mandatory — `WebSecurityConfig`'s constructor refuses to start without it, which beats Boot's `NoSuchBeanDefinitionException: JwtDecoder` — the admin chain is unconditionally `authenticated()`, and `AdminAccess`/`@adminAccess.open()` are deleted. What a contour still decides is whether *source systems* need a token on `/api/v1`: that is `commhub.security.require-source-system-token` (the old `oauth2-enabled`, renamed because OAuth2 is now always on and the name would otherwise lie), off locally so a developer can watch one SMS leave without minting a client-credentials token first. **mTLS is gone entirely** — the panel was never offered it (a certificate names a machine, and the panel needs the employee) and for source systems it was a mechanism with no CA whose empty subject allowlist meant "any trusted certificate names its own stream"; that closes S2, S3 and S7 of `docs/AUDIT-2026-08-09.md`. The local issuer is a Keycloak in `docker compose` (`8180`) importing `docker/keycloak/commhub-realm.json` — the *same file* the integration tests copy into their container, because a second copy would drift and the tests would then prove something about a realm nobody runs. Two things in that realm are load-bearing: groups are named exactly after the `Roles` constants and the mapper has `full.path=false`, since the converter uppercases the claim value and strips nothing (a group emitted as `/commhub-admin` becomes `ROLE_/COMMHUB-ADMIN`); and users are `demo/demo` (ADMIN) plus one per §10.1 role, password = login, each with an email — without one Keycloak's Verify Profile action fires and the password grant answers "Account is not fully set up". The operator's name for the SEC-08 journal comes from `preferred_username` resolved in `AuthenticatedCaller`, not from `setPrincipalClaimName`, which has no fallback and answers the empty string for a token without the claim. `AuthenticatedCaller.hasAnyRole` now fails closed (no authentication → no role); `mayUseStream` deliberately does not, because a contour that has not switched SEC-01 on has no way to name a source system's streams and refusing them would stop ingest rather than protect it. Two defects that only became reachable here are fixed with it: a denied `@PreAuthorize` throws inside the dispatcher rather than the filter chain, so it reached `UnexpectedFailureHandler` and came back as **500** until `adapter/in/admin/handlers/AuthorizationDeniedHandler` (the only advice this module owns — everything else it shares with `rest/handlers`), and `StatisticsController.Filters.includeTest` was a primitive the binder cannot fill from an absent query parameter, so the statistics screen answered 500 to the very first, parameterless request.

Persistence conventions (Phase 4): adapters are `…PersistenceAdapter` over `JdbcClient` with hand-written row mappers — the domain carries no persistence annotations (AR-02) and is rebuilt through its factories or `rehydrate` builders, which no entity mapper can drive (rationale in `adapter/out/persistence/package-info.java`). `jsonb` columns go through the module's own `JsonCodec` (Jackson 3, `tools.jackson.*` since Boot 4) and explicit `…Json` records, never the shared REST `ObjectMapper`. `message`, `message_status_history`, `delivery_attempt` and `outbox_event` are monthly range partitions maintained by `comm_hub.ensure_partitions` / `detach_partitions_before` and `PartitionMaintenanceJob`; every one has a DEFAULT partition as a safety net, and a non-empty one means the scheduler failed. Instants are bound as `OffsetDateTime` at UTC — the driver has no mapping for `Instant`.

## What this system is

**Notification Hub** — a centralized transport & orchestration layer for the Bank's client/service notifications across **SMS, Email, Push** (extensible to Inapp/Stories/WhatsApp/Telegram/Viber/RCS/Web Push). It is a **transport and orchestration layer only**: it does NOT build audiences, content, or campaign logic — source systems submit already-formed messages/batches via **Kafka (primary)** or **REST (synchronous, incl. OTP)**. The Hub does routing, load-balancing, fallback, templating, filtering (suppression / quiet hours), delivery via provider adapters, status aggregation, retries/DLQ, stats, and an admin panel.

## Non-negotiable architectural constraints (from the spec)

These are hard requirements, not preferences. Verify against the spec section before deviating.

- **Hexagonal architecture (Ports & Adapters)** enforced by ArchUnit in `./gradlew build` (AR-01…AR-06). Dependencies point inward only: `adapter → application → domain`.
- **`domain/` has zero compile deps on Spring, JPA, Kafka, Jackson** (AR-02). Only JDK, `java.time`, and own value objects.
- **Multichannel via the Message pattern** (spec §5): one canonical `Message` (channel-independent envelope) + a `sealed MessageContent` hierarchy (`SmsContent`, `EmailContent`, `PushContent`). The pipeline (validate → dedup → route → filter → template → send → status) is single and channel-agnostic.
- **Adding a provider = new adapter only** — no changes to `domain/` or `application/` (AR-04). Each provider implements a channel output port: `SmsProviderPort`, `EmailProviderPort`, `PushProviderPort` (MP-05, AR-04).
- **Adding a channel** = new content specialization + new channel port + provider adapters + DB config; pipeline core unchanged (AR-05).
- **Delivery guarantee**: Transactional Outbox + at-least-once + idempotency by dedup key (AD-03). Consumers must be idempotent.
- **Traffic-class isolation** (`CRITICAL_OTP` / `TRANSACTIONAL` / `NOTIFICATION`): separate Kafka topics, thread pools, and rate limits. Bulk `NOTIFICATION` load must never breach the OTP SLA (p99 ≤ 5s accept→provider; TC-01).
- **Canonical status model** (spec §6.3): provider statuses map onto canonical statuses in the adapters (mapping tables in §18.1 Playmobile, §18.2 SMS Gate).
- **Routing/provider config lives in PostgreSQL**, editable via admin panel, applied **without restart** (≤30s, AD-07/NF-07).
- **Virtual Threads (Java 25 Loom)** for mass provider I/O; blocking HTTP clients are fine, no reactive stack (AR-07).
- **Resilience4j** for retry (exp backoff + jitter) + circuit breaker + automatic failover/failback per provider (PR-01, FR-6.3).

## Module layout (spec §4.2, AR-01)

Every adapter is its own Gradle module and the project path mirrors the directory: `:adapter:in:rest`, `:adapter:out:persistence`, `:adapter:out:provider:playmobile` (so `settings.gradle.kts` sets no `projectDir`). Base package `uz.hamkorbank.commhub`, so e.g. the Playmobile adapter lives in `adapter/out/provider/playmobile/src/main/java/uz/hamkorbank/commhub/adapter/out/provider/playmobile/`. Java packages did not change when the split happened — ArchUnit still checks the layer rules by package; Gradle now also enforces the adapter-to-adapter edges. `:adapter` itself is an aggregator with `api` dependencies on all of them: `./gradlew :adapter:build` builds the layer, and `bootstrap` depends on that one project rather than on twenty-two. Adding a provider = adding a module (AR-04): directory + `build.gradle.kts` + a line in `settings.gradle.kts` + a line in `adapter/build.gradle.kts`.

Two things in the root build exist only because the project path is now nested and must not be "simplified" away: **`group` is derived from the project path** (`uz.hamkorbank.commhub` + parent path) and **`archivesName` is the full path** (`adapter-in-kafka`). A Gradle module's name is the last path segment, so `:adapter:in:kafka` and `:adapter:out:kafka` are both named `kafka` — with a shared group their `group:name` coordinates collide and a `testFixtures(project(...))` on one resolves to the other, and with a shared archive name the fat jar hits two `kafka-0.1.0-SNAPSHOT.jar` entries (which fails the build, and would silently drop half of one adapter under a "take first" duplicates strategy).

```
notification-hub/
├── domain/          # pure model + domain services (Router, FallbackChain, SegmentCalculator). No frameworks.
├── application/      # port/in (use cases), port/out (repos/providers/publishers), orchestration, outbox saga
├── adapter/          # one Gradle module per adapter:
│   ├── in/   rest · admin (BFF §11.2) · kafka · callback · importer · scheduler ·
│   │         contract (IK-03 parsing shared by rest+kafka, BatchActions) ·
│   │         security (AuthenticatedCaller/Roles/StreamAccessGuard, shared by rest+admin)
│   ├── out/  persistence (+Flyway) · kafka (+schema/) · metrics · time · secret · compliance · policy ·
│   │         provider/{support,playmobile,smsgate,smtp,fcm,apns}
│   └── observability/  correlation id, MDC and log masking — neither driving nor driven
└── bootstrap/        # Spring Boot app, config, wiring (incl. WebSecurityConfig), health indicators
```

Cross-module facts worth knowing before touching the graph: `WebSecurityConfig` lives in `bootstrap/config` — it assembles the security chains of rest+admin+callback at once, which is composition-root wiring, not an adapter (moving it back into any one of the three recreates the dependency cycle it was moved to break). `:adapter:in:admin` depends on `:adapter:in:rest` because the message/batch cards answer exactly the §8.2 body (dto+mapper), on `:adapter:in:importer` for the shared CSV parser, and on `:adapter:out:provider:support` for `Masking`. Provider modules depend on `:adapter:in:callback` only for the `ProviderCallbackTranslator` interface (AR-04: vocabulary next to the provider, endpoint provider-agnostic). Shared test infrastructure travels as `testFixtures`: `AbstractPersistenceIT`/`PostgresSchema` (`:adapter:out:persistence`), `KafkaBroker` (`:adapter:out:kafka`), `ProviderStubs`/`FixedClock` (`:adapter:out:provider:support`); cross-adapter tests (`ProviderDocumentationContractTest`, `ProviderRuntimeSettingsTest`) live in `bootstrap`. testFixtures configurations do not inherit the BOM from the root build — add `testFixturesImplementation(platform(libs.spring.boot.bom))` in any module that grows fixtures.

Use cases (input ports) are interfaces taking explicit `Command`/`Query` records and returning `Result` records; REST/Kafka adapters only translate transport DTO ↔ command (AR-06).

## Key domain facts to keep straight

- **Kafka inbound topics** split by traffic class: `comm.inbound.critical.v1` / `.transactional.v1` / `.notification.v1` / `.batch-control.v1`. Outbound: `comm.outbound.status.v1`, `comm.outbound.dlq.v1`, parse-errors → `comm.inbound.parse-error.v1` (§8.1).
- **Idempotency**: `(streamId, externalMessageId)` or `dedupKey` within the dedup window (default 24h) → returns `DUPLICATE`, no resend (FR-1.5).
- **SMS segmentation** (`SegmentCalculator`, §18.3): GSM-7 = 160/153 chars, UCS-2 = 70/67; any non-GSM char forces the whole message to UCS-2; `^ { } \ [ ~ ] | €` count as 2 in GSM-7. Segment count drives cost and quotas.
- **MSISDN format** is strictly `9989xxxxxxxx` (no `+`, no spaces) for Playmobile.
- **Playmobile** `message-id` ≤ 20 chars, generated by the Hub, stored on `DeliveryAttempt`. Error-code classification (retryable / non-retryable / blocking→circuit-breaker) in §18.1; code 102 (Account lock) trips the breaker.
- **Push** has no delivery receipt from APNs/FCM → terminal canonical status is `SENT_TO_PROVIDER`; `UNREGISTERED`/`410` invalidates the token and emits `push-token.invalidated`.
- **PCI DSS**: content validator must reject/alert on full PAN (Luhn detector); no PAN in SMS. PII masked in logs/UI (`99890***4567`).
- **Campaigns without recipient lists (FR-8.11) are OUT of scope** (deferred 06.08.2026). Only an unimplemented `AudienceResolverPort` is reserved in the core. Bulk sends go through the normal batch mechanism with recipient lists.

## Global engineering rules (apply to all Java code here)

- No `var`; constructor injection only; UUIDv7 for primary keys; AAA pattern in tests.
- **Separate classes/packages for the four app-layer concerns** — never collapse: service/use case (orchestration, no mapping logic) · input `XxxCommand`/`XxxQuery` records · output DTO records (in `dto/`) · **MapStruct mappers only** (`@Mapper(componentModel="spring")`, in `mapper/`). MapStruct is mandatory — add `org.mapstruct:mapstruct` + processor before the first mapper.
- `@ControllerAdvice`/`@RestControllerAdvice` live in a dedicated `handlers/` package, one class per concern.
- Delegate: Java tests → `jvm-test-architect` agent; architecture → `solution-architect`; JMS/messaging → `jms` skill; Java+Spring → `spring-java-architect`. New service/entity/ports scaffolding → `hexagonal-ddd` skill.
- Mark finished TODO items with ✅ (not `[x]`) — this applies to `docs/IMPLEMENTATION-PLAN.md`.

## Testing expectations (spec §15)

Domain/use-case unit coverage ≥80% lines / ≥90% for critical logic (routing, dedup, status machine, segmentation). ArchUnit tests for hexagonal rules. Integration tests via Testcontainers (PostgreSQL, Kafka) + WireMock stubs for Playmobile/SMS Gate/FCM/APNs and GreenMail for SMTP. Contract tests, Gatling/k6 load tests (NF-01, TC-01), chaos tests (no loss/dup on instance kill), Playwright E2E for admin.

Testing conventions settled in Phase 15, worth knowing before adding a test. **ArchUnit is split by question**: `HexagonalArchitectureTest` answers "may this layer see that one" (layering, AR-02, and the AR-04 rule that nothing outside a provider package may name it), `LayerConventionsTest` answers "is this class where its kind lives" (naming, records vs classes, `mapper/`, `handlers/`, no field injection, no logger or transport in `application`, no clock in the domain). **The bootstrap module owns the tests that need a whole Hub**: `HubTestContainers` (one PostgreSQL and one broker per JVM, migrated by the application itself), `HubConfiguration` (streams, channel, providers and a routing policy written through the repositories, never through SQL), `ProviderStub` (one WireMock). `ApplicationContextIT` is the one that is not about a feature — it starts the deployment defaults and asserts that every driven port has an adapter, which is how a missing bean stops being a production discovery. Chaos uses **`docker pause`**, not a stub, because the failure worth testing is a connection that hangs rather than one that is refused; a test that pauses a shared container unpauses it in `@AfterEach`, and the helper is idempotent so cleanup never fails on a container that was never paused. Contract compatibility (NF-08) is a **hand-written field list** in `OutboundContractCompatibilityTest`: a codec and the schema next to it move together, so only a frozen copy notices a rename that would break every consumer in the Bank.
