# SQL-обвязка тест-кейсов

Скрипты для ручного прогона кейсов из [`docs/testing/TEST-CASES.md`](../../docs/testing/TEST-CASES.md) на живом стенде: очистка → эталонный контур → предусловия кейса → *действие* → проверки → очистка.

Коллекция ничем не собирается и ни на что не влияет: Gradle её не видит, приложение о ней не знает. Это инструмент для человека, который проверяет Модуль руками или разбирает, почему автотест повёл себя не так, — ровно как [`http/`](../../http/) и [`kafka/`](../../kafka/), с которыми она и работает в паре.

Границы, эталонный контур и правила изоляции — в [`docs/testing/INTEGRATION-TEST-SPEC.md`](../../docs/testing/INTEGRATION-TEST-SPEC.md).

---

## Файлы

| Файл | Что делает |
|---|---|
| `00-reset.sql` | Очистка **состояния**: сообщения, попытки, outbox, дедуп, подавления, счётчики, батчи, DLQ. Конфигурацию не трогает |
| `01-contour.sql` | Эталонный контур §2 спецификации: 5 провайдеров, 3 канала, 11 потоков, 5 шаблонов. Идемпотентен |
| `99-teardown.sql` | Полная уборка: состояние **и** контур. Чужую конфигурацию не трогает — удаляет только своё, по имени |
| `cases/1x–2x-*.sql` | 12 файлов по областям, блок на каждый из 157 кейсов: `@arrange` (предусловия) и `@assert` (проверки) |
| `bin/run-case.sh` | Полный цикл одного кейса. `--list`, `--arrange-only`, `--assert-only`, `--no-teardown` |
| `bin/purge-topics.sh` | Удаление и пересоздание топиков Kafka |

## Как пользоваться

```bash
docker compose up -d postgres kafka          # стенд
./gradlew :bootstrap:bootRun                 # Модуль (в отдельном окне)

sql/testing/bin/run-case.sh --list           # какие кейсы есть
sql/testing/bin/run-case.sh IT-FLT-006       # прогнать один
```

`run-case.sh` чистит базу и топики, ставит контур, применяет предусловия кейса и **останавливается**: действие кейса — REST-запрос из `http/`, документ из `kafka/` или экран панели — выполняете вы. После Enter скрипт показывает проверки и убирает за собой.

Когда действие занимает время (или его делает кто-то другой), удобнее двумя вызовами:

```bash
sql/testing/bin/run-case.sh IT-QTA-001 --arrange-only
# ... четыре отправки через http/30-send.http ...
sql/testing/bin/run-case.sh IT-QTA-001 --assert-only
```

`psql` берётся из `PATH`, а если его нет — из контейнера `docker compose`. Отдельная база задаётся переменными: `COMMHUB_DB` для локального `psql`, `PGDB`/`PGUSER_` для контейнерного.

## Что стоит знать до первого запуска

**`(0 rows)` — это не «прошло».** Запросы с `count()` дают строку всегда, а `SELECT status = 'REJECTED' … FROM message` — только если сообщение существует. Пустой вывод означает «объекта, о котором спрашивали, нет», и почти всегда это провал кейса, а не его успех. Читать колонку `ok` — `t` прошло, `f` не прошло, пусто — не проверено.

**Модуль надо останавливать перед очисткой топиков.** Удаление топика под работающим консьюмером даёт `UNKNOWN_TOPIC_OR_PARTITION` и переподписку с непредсказуемой позиции. Если кейс не про Kafka — быстрее и безопаснее `SKIP_TOPICS=1`.

**Кэш конфигурации живёт до 10 секунд.** `commhub.config.cache.refresh-interval` (потолок 30 с по NF-07): правка канала или провайдера в `@arrange` доезжает до маршрутизатора не мгновенно. Это не задержка скрипта, а поведение Модуля — его проверяет `IT-RTE-014`.

**Канал в системе ровно один на код.** `channel.code` — первичный ключ с `CHECK` по перечислению; второго профиля `SMS` не бывает. Кейсы, меняющие стратегию балансировки или статус канала, переписывают общую строку и потому не параллелятся. Возвращать её не нужно: `01-contour.sql` накатывается заново перед каждым прогоном.

**Контент сообщений зашифрован (DB-04).** `message.contents` и `message.template_variables` лежат как `"CH1.<keyId>.<base64url>"`, поэтому «в отправленном тексте нет `{CODE}`» проверяется не SQL-ом, а журналом отправок (`commhub.provider.content-log.enabled` в корневом `config/application.yml`) или запросом, который увидел провайдер. В базе проверяется то, что в ней действительно есть: код шаблона, локаль и идентификатор версии.

**Хеш адреса считается как в домене:** `encode(sha256(lower(адрес)::bytea), 'hex')` — это `AddressHash.of`. По этому хешу ищут и список подавления, и счётчики частоты. Посчитаете иначе — запрет молча перестанет совпадать, и кейс станет зелёным по неверной причине.

**`audit_log` не чистится нигде.** V7 запрещает `DELETE` и `TRUNCATE` на уровне БД: журнал, который может опустошить тест, может опустошить и администратор (SEC-08). Кейсы, читающие журнал, пишутся безразличными к тому, что в нём уже есть.

**`99-teardown.sql` удаляет только своё.** Провайдеры `MOCK_*`, одиннадцать потоков набора, пять шаблонов, все политики маршрутизации. Боевые профили и потоки остаются; из порядка отката канала вычищаются только коды `MOCK_*`, порядок остальных сохраняется — он значащий.

## Что проверяется не в базе

SQL не покажет и не должен:

| Что | Чем проверять |
|---|---|
| Коды и тела ответов (`202`, `400`, `403`, `405`, `409`, `415`, `422`, `429`, `503`, `problem+json`) | клиент из `http/` |
| Заголовки `Allow`, `Accept`, `Retry-After`, `Location` | там же |
| Записи в `comm.inbound.parse-error.v1` и заголовки `commhub-origin-topic` / `commhub-failed-field` | Kafka UI (`8090`) или `kafka-console-consumer` |
| Порядок и ключ раздела исходящих событий | вычитка раздела топика; в базе виден только порядок `outbox_event.created_at` |
| Состояние размыкателя (circuit breaker) | метрика `CircuitBreakerMetrics` — размыкание не решение ядра, а свойство адаптера |
| Метрики `quotaBreached`, `panDetected`, `frequencyCapExceeded` | `/actuator/prometheus` |
| Отсутствие PAN и адресов в логах | `docker compose logs`, поиск по номеру должен давать ноль |
| Форма запроса к Playmobile и SMS Gate | WireMock в контрактных IT адаптеров |
