## 1. Введение

### 1.1. Назначение документа

Документ определяет полный набор требований, необходимых для проектирования и разработки Коммуникационного модуля (далее — «Модуль») — централизованного транспортно-оркестрирующего слоя для отправки клиентских и сервисных уведомлений Банка по каналам **SMS, Email, Push** (с архитектурным заделом на Inapp, Stories, WhatsApp Business, Telegram, Viber, RCS, Web Push).

Документ детализирует бизнес-требования ТЗ v1.2 до уровня, достаточного для разработки: архитектура, доменная модель, контракты API, схема БД, требования к админ-панели, NFR.

### 1.2. Исходные документы

| № | Документ | Использование |
|---|---|---|
| 1 | ТЗ «Коммуникационный модуль АКБ Hamkorbank» v1.2 (12.07.2026) | Базовые бизнес- и архитектурные требования |
| 2 | Playmobile SMS-Broker API | Контракт основного SMS-провайдера (HTTP/JSON) |

### 1.3. Ключевое архитектурное ограничение (из ТЗ)

> Модуль является **транспортным и оркестрирующим слоем** и не создаёт рассылки самостоятельно. Формирование состава получателей (аудитории), содержания и бизнес-логики инициации рассылки — зона ответственности систем-источников. Модуль принимает уже сформированные рассылки (единичные сообщения либо батчи) через REST API или Kafka и обеспечивает их маршрутизацию, доставку, мониторинг и управление на уровне каналов и провайдеров.

### 1.4. Термины и сокращения

| Термин | Определение |
|---|---|
| Message | Каноническая доменная сущность «сообщение» — единица доставки, не зависящая от канала (см. раздел 5) |
| Батч (batch) | Пакетная рассылка — набор сообщений, переданный системой-источником за одну операцию |
| Входящий поток (stream) | Зарегистрированная в Модуле система-источник со способом интеграции и настройками маршрутизации по умолчанию |
| Канал (channel) | Тип коммуникации: SMS, EMAIL, PUSH (расширяемо: INAPP, STORIES, …) |
| Провайдер (provider) | Внешняя система доставки в рамках канала (Playmobile, SMS Gate, SMTP-сервер, APNs, FCM) |
| OTP | One-Time Password — одноразовый код подтверждения |
| Outbox-паттерн | Атомарное сохранение события в БД вместе с бизнес-транзакцией с последующей асинхронной публикацией |
| DLQ | Dead-Letter Queue — очередь недоставленных сообщений |
| Suppression list | Список получателей, которым отправка запрещена |
| Quiet hours | Интервал времени, в течение которого отправка нетранзакционных уведомлений блокируется |
| RBAC | Role-Based Access Control |
| ЦБ РУз | Центральный банк Республики Узбекистан |
| Hexagonal architecture | Архитектура «порты и адаптеры» (Ports & Adapters, A. Cockburn) |

## 2. Общее описание системы

### 2.1. Контекст (AS-IS)

Отправка уведомлений в Банке реализована децентрализованно: прикладные системы интегрируются с каналами доставки напрямую либо через шины Банка. SMS отправляются только через провайдера; Email не имеет централизованного сервиса; Push/Inapp/Stories реализованы в составе мобильных приложений.

### 2.2. Целевая роль Модуля (TO-BE)

Модуль — единая точка интеграции коммуникационных каналов для всех внутренних систем Банка (N систем-источников × M каналов/провайдеров), обеспечивающая:

- единую точку подключения систем-источников к каналам и провайдерам;
- унифицированную маршрутизацию и балансировку нагрузки между каналами и провайдерами;
- единые политики безопасности и compliance;
- агрегацию и возврат статусов доставки в едином формате независимо от фактического канала/провайдера;
- централизованную шаблонизацию уведомлений;
- сквозной аудит и наблюдаемость;
- горизонтальное масштабирование без деградации сервиса.

### 2.3. Пользователи и внешние акторы

| Актор | Тип | Взаимодействие |
|---|---|---|
| Системы-источники (мобильное приложение ФЛ, ДБО ЮЛ, iABS, Эквайринг, Creatio, Сайт, TIETO, EVAM, R-Style, AutoPayment, AgentTelecom, HR, Маркетинг, Ундирув/Collections, СРМ и др.) | Системы | Публикация рассылок через Kafka / REST, получение статусов через Kafka |
| Playmobile | Внешняя система | Основной SMS-провайдер (HTTP/JSON, опционально SMPP) |
| Резервный SMS-провайдер (SMS Gate, smsgw.vas.uz) | Внешняя система | Резервный SMS-канал (HTTP) |
| Корпоративный почтовый сервер | Внешняя система | Email (SMTP) |
| APNs / FCM | Внешние системы | Push-уведомления |
| Администратор / Саппорт | Пользователь | Админ-панель: провайдеры, маршрутизация, потоки, шаблоны, управление рассылками |
| Аналитик / Оперблок | Пользователь | Админ-панель: статистика, мониторинг; витрина данных (BigData) |
| Telecom Antifraud, Uzcard, Humo | Внешние системы | Отправка OTP через Open API контур (существующий), интеграция через ESB/Open API |

### 2.4. Границы системы

**Входит в объём разработки:** приём и постановка сообщений в обработку, маршрутизация/балансировка/fallback, шаблонизация, фильтрация (suppression, quiet hours), доставка через адаптеры провайдеров, приём и агрегация статусов, ретраи и DLQ, статистика и алертинг, админ-панель, RBAC, аудит, выгрузка в витрину данных.

**Не входит:** формирование аудиторий и контента рассылок, CRM-логика, campaign management, а также сами мобильные приложения (SDK push-регистрация токенов — на стороне приложений; Модуль хранит и использует переданные токены/адреса).

## 3. Технологический стек и архитектурные решения

### 3.1. Утверждённый стек

| Слой | Технология | Примечание |
|---|---|---|

| Framework | **Spring Boot 4.x** (Spring Framework 7) | Spring Web MVC / WebClient (HTTP interfaces), Spring for Apache Kafka, Spring Data JDBC/JPA, Spring Security, Spring Actuator |
| СУБД | **PostgreSQL 16+** | Основное хранилище состояния сообщений, конфигурации, шаблонов; партиционирование по времени |
| Брокер | **Apache Kafka** (корпоративный кластер Банка) | Основной асинхронный транспорт входящих рассылок и исходящих статусов |
| Frontend | **React 18+** (TypeScript) | SPA админ-панель |
| Миграции БД | Flyway / Liquibase | Версионирование схемы |
| Наблюдаемость | Micrometer + OpenTelemetry, Prometheus, Grafana, structured JSON logs | Метрики, трассировка, логи |
| Контейнеризация | Docker, Kubernetes/OpenShift Банка | Горизонтальное масштабирование, rolling-обновления без downtime |
| Аутентификация админ-панели | OIDC / корпоративный SSO (Keycloak/AD) | + RBAC внутри Модуля |

### 3.2. Ключевые архитектурные решения (Architecture Decisions)

| ID | Решение | Обоснование |
|---|---|---|
| AD-01 | Backend строится по **гексагональной архитектуре** (Ports & Adapters) | Изоляция домена от провайдеров/транспортов; добавление канала или провайдера = новый адаптер без переработки ядра (требование ТЗ п. 5.8 о расширяемости) |
| AD-02 | Мультиканальность реализуется через **паттерн Message** (каноническое сообщение + канальные специализации) | Единый жизненный цикл, единая статусная модель и единый pipeline обработки для всех каналов |
| AD-03 | Гарантия доставки — **Transactional Outbox + At-Least-Once + идемпотентность по ключу дедупликации** | Требование ТЗ п. 4.4: сообщение не теряется и не дублируется при сбое/перезапуске |
| AD-04 | Отказоустойчивость вызовов провайдеров — **Retry с экспоненциальной задержкой + Circuit Breaker + автоматический fallback на резервного провайдера** | Требования ТЗ п. 4.3, 4.4, 5.6 |
| AD-05 | **Изоляция классов трафика** (critical/OTP, transactional, notifications): раздельные топики Kafka, раздельные пулы обработки, раздельные rate-limits | Требование ТЗ п. 4.5: массовые рассылки не деградируют OTP |
| AD-06 | Статусная модель — единая каноническая, статусы провайдеров маппятся на канонические | Требование ТЗ: возврат статусов в едином формате |
| AD-07 | Конфигурация маршрутизации (каналы, провайдеры, потоки, политики) хранится в PostgreSQL и управляется через админ-панель, применяется без рестарта | Управляемость эксплуатацией |
| AD-08 | История отправок партиционируется по датам; горячие данные в PostgreSQL, аналитика — выгрузка в витрину данных (BigData) | Объёмы >13 млн SMS/мес + Email/Push; retention по регуляторике |

### 4.2. Требования к структуре кода

**AR-01.** Проект backend структурируется по модулям (Gradle/Maven multi-module или пакетная структура с enforcement через ArchUnit):

```
communication-module/
├── domain/                  # чистая доменная модель, без зависимостей на Spring/JPA
│   ├── model/               #   Message, Batch, Stream, Provider, Template, ...
│   └── service/             #   доменные сервисы: Router, FallbackChain, SegmentCalculator
├── application/             # интерфейсы портов, реализация use cases, транзакции, оркестрация, saga отправки
|.  └── port/
│       ├── in/              #   input ports (use case интерфейсы)
│       └── out/             #   output ports (репозитории, провайдеры, паблишеры)
├── adapter/
│   ├── in/
│   │   ├── rest/            #   REST API систем-источников (v1)
│   │   ├── kafka/           #   консьюмеры входящих рассылок
│   │   ├── admin/           #   REST BFF админ-панели
│   │   └── callback/        #   приём статусов от провайдеров (webhook)
│   └── out/
│       ├── persistence/     #   PostgreSQL (Spring Data), outbox
│       ├── kafka/           #   публикация статусов, DLQ
│       ├── provider/
│       │   ├── playmobile/  #   HTTP-адаптер Playmobile SMS-Broker API
│       │   ├── smsgate/     #   HTTP-адаптер SMS Gate v4.3
│       │   ├── smpp/        #   (опция) SMPP-адаптер
│       │   ├── smtp/        #   Email
│       │   ├── apns/        #   Push iOS
│       │   └── fcm/         #   Push Android
│       └── notification/    #   алертинг ответственным
└── bootstrap/               # Spring Boot приложение, конфигурация, wiring
```

**AR-02.** Домен (`domain/`) не должен иметь compile-зависимостей на Spring, JPA, Kafka, Jackson. Допустимые зависимости: JDK, java.time, собственные value objects.

**AR-03.** Все зависимости направлены внутрь: `adapter → application → domain`. Правило контролируется автоматически (ArchUnit-тесты в CI).

**AR-04.** Каждый провайдер реализуется как отдельный адаптер, реализующий канальный output port (`SmsProviderPort`, `EmailProviderPort`, `PushProviderPort`). Добавление нового провайдера не должно требовать изменений в `domain/` и `application/`.

**AR-05.** Добавление нового канала (WhatsApp, Telegram, Viber, RCS, Web Push, Inapp, Stories) должно сводиться к: (1) новой специализации Message-контента, (2) новому канальному порту, (3) адаптерам провайдеров, (4) конфигурации канала в БД. Ядро pipeline (приём → маршрутизация → фильтрация → шаблонизация → отправка → статусы) переиспользуется без изменений.

**AR-06.** Use cases (input ports) оформляются как интерфейсы с явными командами/результатами (Command/Result records). REST и Kafka адаптеры — только трансляция транспортных DTO в команды.

**AR-07.** Массовый I/O к провайдерам выполняется на виртуальных потоках (Java 25 Virtual Threads); блокирующие HTTP-клиенты допустимы, реактивный стек не требуется.

## 5. Мультиканальность: паттерн Message

### 5.1. Принцип

Мультиканальность реализуется через **паттерн проектирования Message** (каноническое сообщение): все уведомления, независимо от канала, представляются единой доменной сущностью `Message` с общим конвертом (envelope) и полиморфным содержимым по каналу. Pipeline обработки (валидация → дедупликация → маршрутизация → фильтрация → шаблонизация → отправка → статусы) един для всех каналов и работает с абстракцией `Message`; канальная специфика инкапсулирована в специализациях контента и в адаптерах провайдеров.

### 5.2. Структура канонического Message

```java
// domain/model — иллюстративный контракт (sealed-иерархия, Java 25)

public record Message(
    MessageId id,                    // внутренний UUIDv7
    ExternalMessageId externalId,    // message-id системы-источника (уникален в рамках потока)
    StreamId streamId,               // входящий поток (система-источник)
    BatchId batchId,                 // null для единичных сообщений
    TrafficClass trafficClass,       // CRITICAL_OTP | TRANSACTIONAL | NOTIFICATION
    Priority priority,               // LOW | NORMAL | HIGH | REALTIME
    Recipient recipient,             // адреса по каналам: msisdn, email, pushToken(s), clientId
    ChannelPlan channelPlan,         // запрошенные каналы + политика (single | fallback-цепочка Push→SMS→Email)
    MessageContent content,          // sealed: по каналу (см. ниже)
    TemplateRef template,            // опционально: id шаблона + merge-переменные
    Timing timing,                   // отложенная отправка, окно отправки, TTL
    DedupKey dedupKey,               // ключ идемпотентности
    CorrelationId correlationId,     // сквозная трассировка
    Instant acceptedAt
) {}

public interface MessageContent {}

public record SmsContent(String text, String originator /* альфа-имя */) implements MessageContent {}
public record EmailContent(String subject, String htmlBody, String textBody,
                           List<Attachment> attachments, EmailAddress from) implements MessageContent {}
public record PushContent(String title, String body, Map<String,String> data,
                          String deepLink, String image) implements MessageContent {}
```

### 5.3. Требования паттерна

**MP-01.** Конверт (envelope) сообщения канало-независим: идентификация, поток, класс трафика, приоритет, получатель, timing, дедупликация, трассировка.

**MP-02.** Контент — sealed-иерархия по каналам. Одно логическое уведомление может содержать контент для нескольких каналов (channel-agnostic API из ТЗ п. 4.1: «уведомить клиента N по каналам [SMS, Email, Push]»).

**MP-03.** `ChannelPlan` поддерживает режимы: (a) явный канал; (b) выбор канала Модулем по политикам потока и предпочтениям клиента; (c) fallback-цепочка каналов по результату доставки (например Push → SMS при недоставке Push в течение TTL) — расширение из ТЗ п. 5.8.

**MP-04.** Статусная модель едина для всех каналов (см. 6.4); канальные статусы провайдеров маппятся адаптерами на канонические.

**MP-05.** Маршрутизатор (`Router`) работает только с `Message` и конфигурацией маршрутизации; он не знает о конкретных провайдерах — выбирает `ProviderRef`, по которому application-слой резолвит адаптер через канальный порт.

**MP-06.** Сегментация SMS (GSM-7: 160/153, UCS-2: 70/67 символов на сегмент) вычисляется доменным сервисом `SegmentCalculator` до отправки — для расчёта стоимости, квот и валидации длины (см. Приложение 18.3).

## 6. Доменная модель

### 6.1. Основные агрегаты

| Агрегат | Содержание | Назначение |
|---|---|---|
| **Message** | Envelope + контент + план каналов + текущий статус + попытки доставки | Единица доставки |
| **Batch** | Метаданные пакетной рассылки: поток, размер, прогресс, статус (ACCEPTED/PROCESSING/PAUSED/STOPPED/COMPLETED), канал по умолчанию | Управление рассылкой как целым |
| **Stream** (входящий поток) | Система-источник: способ интеграции (KAFKA/REST), учётные данные, канал/провайдер по умолчанию, класс трафика по умолчанию, квоты, quiet hours, статус подключения | Регистрация систем-источников (ТЗ п. 4.2) |
| **Channel** | Тип канала, статус, привязанные провайдеры, политика балансировки и fallback | Управление каналами |
| **Provider** | Интеграционный профиль: тип адаптера, endpoint, учётные данные (в секрет-хранилище), лимиты rate/TPS, тарифы, окна обслуживания, health-статус | ТЗ п. 5.2 |
| **RoutingPolicy** | Правила выбора канала/провайдера: по потоку, классу трафика, приоритету; балансировка round-robin / по весу / по стоимости; fallback-порядок | ТЗ п. 4.3, 5.2 |
| **Template** | Шаблон уведомления: канал, локали RU/UZ/EN, версии, статус (DRAFT/ON_REVIEW/PUBLISHED/ARCHIVED), merge-поля | ТЗ п. 5.4 |
| **SuppressionEntry** | Запрет отправки: адрес/клиент, канал, причина (opt-out, жалоба, hard bounce), срок | ТЗ п. 5.5 |
| **DeliveryAttempt** | Попытка отправки: провайдер, время, результат, код ошибки провайдера, id сообщения у провайдера | Аудит и ретраи |
| **DlqEntry** | Недоставленное сообщение после исчерпания попыток: причина, возможность ручного повтора | ТЗ п. 5.3 |

### 6.2. Классы трафика (изоляция приоритетов, ТЗ п. 4.5)

| Класс | Назначение | Изоляция | SLA |
|---|---|---|---|
| `CRITICAL_OTP` | OTP, критичные коды | Отдельные Kafka-топики, отдельные пулы потоков и rate-limit-бюджеты у провайдеров, приоритет `realtime`/`high` у Playmobile | p99 ≤ 5 c от приёма до передачи провайдеру |
| `TRANSACTIONAL` | Событийные уведомления (списания, статусы заявок) | Отдельные топики/пулы | p99 ≤ 30 c (уточняется) |
| `NOTIFICATION` | Массовые рассылки (маркетинг, взыскание, HR) | Отдельные топики/пулы, троттлинг, quiet hours, send-evenly | Обработка батча без деградации первых двух классов |

**TC-01.** Ни при какой нагрузке класса `NOTIFICATION` задержка `CRITICAL_OTP` не должна превышать SLA (валидируется нагрузочным тестом: батч ≥ 500 тыс. сообщений параллельно с потоком OTP).

**TC-02.** Класс трафика назначается: явно источником в сообщении → иначе по умолчанию из настроек потока.

### 6.3. Жизненный цикл Message (каноническая статусная модель)

```
ACCEPTED → VALIDATED → ROUTED → QUEUED → SENDING → SENT_TO_PROVIDER → DELIVERED
    │           │         │        │         │             │              ├─→ UNDELIVERED (по данным провайдера)
    │           │         │        │         │             │              └─→ EXPIRED (TTL истёк)
    │           └─→ REJECTED (валидация/suppression/quiet hours/квоты)
    │                              │         └─→ RETRYING → (SENDING | FAILED)
    └─→ DUPLICATE (идемпотентность)                        └─→ FAILED → DLQ (ручной повтор → QUEUED)
                                   └─→ CANCELLED (остановка рассылки/отмена по TTL)
```

**ST-01.** Каждая смена статуса фиксируется в истории с меткой времени, актором (система/оператор) и деталями (код провайдера).
**ST-02.** Терминальные статусы: `DELIVERED`, `UNDELIVERED`, `EXPIRED`, `REJECTED`, `DUPLICATE`, `CANCELLED`, `FAILED` (после DLQ-повтора цикл возобновляется новым attempt).
**ST-03.** Маппинг статусов провайдеров на канонические — по таблицам Приложения 18.1–18.2.

### 6.4. Формат статуса для систем-источников

Статусы возвращаются источникам через Kafka в едином формате независимо от канала/провайдера (ТЗ п. 4.4):

```json
{
  "eventId": "uuid",
  "occurredAt": "2026-08-06T12:00:00Z",
  "streamId": "mobile-app",
  "batchId": "uuid | null",
  "messageId": "uuid",
  "externalMessageId": "abc0000001",
  "channel": "SMS",
  "provider": "PLAYMOBILE",
  "status": "DELIVERED",
  "providerStatus": "DLVRD",
  "reason": null,
  "segments": 2,
  "correlationId": "uuid"
}
```

## 7. Функциональные требования

Нумерация FR-x.y соответствует разделам ТЗ 5.x.

### 7.1. Приём рассылок от систем-источников (ТЗ 5.1)

- **FR-1.1.** Модуль принимает единичные сообщения и батчи через Kafka (основной способ) и REST API (синхронный, в т.ч. для OTP).
- **FR-1.2.** Модуль не формирует состав получателей, контент и расписание — принимает их полностью сформированными (допускается контент по шаблону: `templateId` + переменные).
- **FR-1.3.** Каждая система-источник регистрируется как входящий поток (stream) с отображением в админ-панели: способ интеграции, канал/провайдер по умолчанию, текущий статус подключения (по heartbeat/последней активности).
- **FR-1.4.** Валидация при приёме: обязательность полей, формат адресов (MSISDN `9989xxxxxxxx`, email RFC 5322, push-токены), допустимая длина контента по каналу, существование потока и шаблона. Ошибки — синхронно (REST 400 + код) либо событием `message.rejected` (Kafka).
- **FR-1.5.** Идемпотентность: повторная подача сообщения с тем же `(streamId, externalMessageId)` или `dedupKey` в окне дедупликации (конфигурируемо, по умолчанию 24 ч) не приводит к повторной отправке; возвращается статус `DUPLICATE` с ссылкой на оригинал.
- **FR-1.6.** Приём батча: заголовок батча (id, поток, канал, timing, шаблон) + элементы; загрузка элементов чанками; батч видим в системе с момента приёма с прогрессом обработки.
- **FR-1.7.** REST-приём OTP: подтверждение приёма ≤ 200 мс (p99), постановка в приоритетную обработку.

### 7.2. Управление каналами и провайдерами (ТЗ 5.2)

- **FR-2.1.** Подключение нескольких независимых провайдеров в рамках одного канала (SMS-1, SMS-2, …; Email-1, …; Push-1, …), каждый — отдельный интеграционный профиль: учётные данные, endpoint'ы, лимиты, тарифы (цена за сообщение/сегмент), валюта.
- **FR-2.2.** Назначение основного и одного или нескольких резервных провайдеров на канал с настраиваемым порядком fallback.
- **FR-2.3.** Балансировка между активными провайдерами одного канала: round-robin, по весам, по стоимости (least-cost routing). Стратегия настраивается на уровне канала и/или потока.
- **FR-2.4.** Канал и провайдер по умолчанию задаются для каждого входящего потока.
- **FR-2.5.** Лимиты и троттлинг скорости отправки на уровне провайдера (TPS/сообщений в минуту), с учётом ограничений провайдера (например, антиспам-лимит SMS Gate: 50 SMS/час на один номер — см. 18.2).
- **FR-2.6.** Квоты и бюджеты по количеству и стоимости сообщений в разрезе канал/провайдер/поток (день/месяц); поведение при исчерпании: блокировка с алертом либо только алерт (настраивается).
- **FR-2.7.** Включение/выключение провайдера и канала «на лету» без рестарта; режим технического обслуживания.

### 7.3. Управление рассылками на уровне Модуля (ТЗ 5.3)

- **FR-3.1.** Каждая принятая рассылка (батч) отображается как отдельная сущность: источник, канал, статус, прогресс (принято/отправлено/доставлено/ошибки), стоимость.
- **FR-3.2.** Пауза/возобновление/остановка: конкретного батча, конкретного входящего потока, всех рассылок Модуля (kill switch). Остановка не затрагивает класс `CRITICAL_OTP`, если не указано явно.
- **FR-3.3.** DLQ: просмотр недоставленных сообщений с причинами, фильтрация, ручной повтор (единично и пакетно), списание в архив.
- **FR-3.4.** Отмена сообщений по TTL: по истечении срока актуальности сообщение переводится в `EXPIRED` и не отправляется (критично для OTP).

### 7.4. Шаблоны и персонализация (ТЗ 5.4)

- **FR-4.1.** CRUD шаблонов с версионированием; локализация RU / UZ / EN; статусы DRAFT → ON_REVIEW → PUBLISHED → ARCHIVED; отправка возможна только по PUBLISHED-версии.
- **FR-4.2.** Процесс ревью: автор не может сам публиковать свой шаблон (разделение ролей maker/checker).
- **FR-4.3.** Подстановка merge-полей из переменных, переданных источником (`{"NAME":"IVAN"}`); строгий режим — отсутствие переменной = ошибка валидации сообщения.
- **FR-4.4.** Для SMS шаблон хранит вариант текста по локалям; предпросмотр с расчётом сегментов и стоимости по действующим тарифам провайдеров.
- **FR-4.5.** Поддержка соответствия шаблонов Модуля шаблонам, зарегистрированным на стороне провайдера (Playmobile `template-id`) — маппинг в профиле провайдера. Согласование шаблонов у оператора/провайдера — организационный процесс вне Модуля; Модуль хранит статус согласования.
- **FR-4.6.** Существующая база шаблонов Банка (≈470 шаблонов из прогнозного файла, направления: Чакана/Розница, МСБ, Ундирув, СРМ, Оперблок, Маркетинг, ИТ, Кадр, Риск и др.) подлежит миграции в Модуль на этапе внедрения.

### 7.5. Фильтрация и compliance на уровне доставки (ТЗ 5.5)

- **FR-5.1.** Suppression list: проверка получателя (адрес+канал либо клиент целиком) перед отправкой; причины: opt-out, жалоба, hard bounce, ошибка предыдущих отправок; управление через админ-панель и API; результат — `REJECTED` с причиной `SUPPRESSED`.
- **FR-5.2.** Учёт согласий клиента (opt-in/opt-out) как фильтр перед отправкой для нетранзакционных классов.
- **FR-5.3.** Quiet hours («часы тишины») для классов, отличных от `CRITICAL_OTP`/`TRANSACTIONAL`: настраиваются на уровне канала и/или потока; поведение: отложить до окончания окна либо отклонить (настраивается). Часовой пояс — Asia/Tashkent; при наличии признака «локальное время получателя» — по нему (поддерживается Playmobile `timing.localtime`).
- **FR-5.4.** Ограничение частоты (frequency capping) на получателя для класса `NOTIFICATION` (не более N сообщений за период) — конфигурируемо; в MVP допускается реализация только счётчиков и алертов.

### 7.6. Статистика и мониторинг (ТЗ 5.6)

- **FR-6.1.** Статистика по каждому каналу и провайдеру: отправлено / доставлено / не доставлено / в очереди / ошибки, время доставки (p50/p95/p99), в разрезах час/день/месяц.
- **FR-6.2.** Статистика по каждому батчу и входящему потоку, включая стоимость (по тарифам провайдеров и фактическим сегментам).
- **FR-6.3.** Проактивное обнаружение деградации провайдера по фактическим показателям (delivery rate, error rate, латентность, таймауты) в скользящем окне; при превышении порогов — алертинг ответственных (email/Telegram/webhook — уточняется) и автоматическое переключение на резервного провайдера (circuit breaker + failover) с автоматическим возвратом после восстановления (health-probe).
- **FR-6.4.** Выгрузка событий отправок в витрину данных Банка (BigData) — batch-экспорт либо Kafka-топик для витрины (формат согласуется с командой данных).

### 7.7. Административный интерфейс и доступ (ТЗ 5.7)

- **FR-7.1.** Управление: провайдерами, маршрутизацией, входящими потоками, шаблонами, статусами рассылок, suppression list, справочниками.
- **FR-7.2.** RBAC: роли минимум — `ADMIN` (всё), `OPERATOR` (управление рассылками: пауза/повтор/DLQ), `TEMPLATE_MANAGER` (шаблоны: создание/ревью), `VIEWER`/`ANALYST` (просмотр статистики), `SECURITY_AUDITOR` (журнал аудита). Права проверяются на backend.
- **FR-7.3.** Журнал аудита действий пользователей: кто, когда, что изменил (до/после), из какого IP; неизменяемость записей; экспорт.
- **FR-7.4.** Тестовая отправка для проверки конфигурации канала/провайдера перед вводом в эксплуатацию: на указанный адрес, с меткой TEST, без учёта в бизнес-статистике (отдельный признак).

### 8.2. REST API систем-источников (синхронный, в т.ч. OTP)

Base: `https://<host>/api/v1`, mTLS/OAuth2 client credentials (уточняется ИБ Банка), JSON UTF-8.

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/messages` | Отправка единичного сообщения (тело = IK-03). Ответ 202: `{messageId, status:"ACCEPTED"}`. p99 ≤ 200 мс |
| POST | `/batches` | Создание батча (заголовок) |
| POST | `/batches/{id}/items` | Загрузка элементов чанками (до N=10 000 за запрос, уточняется) |
| POST | `/batches/{id}/actions/start|pause|resume|stop` | Управление батчем |
| GET | `/messages/{id}` / `GET /messages?externalMessageId=&streamId=` | Статус сообщения |
| GET | `/batches/{id}` | Статус/прогресс батча |

**IR-01.** Ошибки — RFC 9457 (problem+json) с машинно-читаемым кодом (`VALIDATION_FAILED`, `DUPLICATE`, `STREAM_SUSPENDED`, `QUOTA_EXCEEDED`, `TEMPLATE_NOT_PUBLISHED` и т.д.).
**IR-02.** Rate limiting на поток; заголовки `Retry-After`.
**IR-03.** OpenAPI 3.1 спецификация — артефакт поставки, генерируется из кода.

### 8.3. Интеграция через ESB (Wso2)

Существующие потоки OTP (Humo, Uzcard, Telecom Antifraud через Open API контур) и системы, подключённые к шине, взаимодействуют с Модулем через те же REST/Kafka контракты; ESB выступает как клиент Модуля. Изменение контрактов на стороне внешних процессинговых систем не предполагается.

## 9. Интеграции с провайдерами доставки (исходящие)

### 9.1. SMS — Playmobile SMS-Broker API (основной провайдер)

Источник: «SMS-Broker API» (Playmobile).

| Параметр | Значение |
|---|---|
| Протокол | HTTP + JSON (`Content-type: application/json; charset=UTF-8`), даты ISO 8601 UTC |
| Аутентификация | Basic auth |
| Отправка | `POST <base-url>/send` — единичные и массовые; поддержка `template-id`, `variables`, `priority` (`low`/`normal`/`high`/`realtime`), `timing` (`localtime`, `start-datetime`, `end-datetime`, `allowed-starttime/endtime`, `send-evenly`), `sms.originator`, `sms.ttl`, `blacklist-id` |
| message-id | Уникален на систему-отправителя, ≤ 20 символов, формат `<префикс_организации><номер>` — генерируется Модулем и хранится в `DeliveryAttempt` |
| Получатель | MSISDN строго `9989xxxxxxxx`, без `+` и пробелов |
| Статусы (DLR) | Push на URL партнёра `<partner-url>/status`: `message-id`, `channel`, `status`, `status-date`, `description`; Модуль реализует callback-endpoint (driving adapter) |
| Ошибки | HTTP 400 + `error_code`/`error_description`; коды 100–105, 202–206, 301–306, 401–411 (см. 18.1) |
| Доп. канал | `call` (голосовая доставка TTS/IVR) — в объём MVP не входит, поле контракта учитывается |

**PM-01.** Адаптер Playmobile реализует `SmsProviderPort`: `submit(SmsSubmission): ProviderAck`, маппинг канонического Message → JSON `/send` (одиночная и батчевая формы), обработку кодов ошибок с классификацией: retryable (5xx, таймауты, 100) / non-retryable (401–406 контент/параметры) / блокирующие (102 Account lock → circuit breaker + алерт).
**PM-02.** Callback-endpoint статусов: аутентификация по IP allowlist + секрет (согласуется с Playmobile), идемпотентная обработка, маппинг статусов на канонические (18.1), подтверждение 200.
**PM-03.** Поддержка приоритетов: `CRITICAL_OTP → realtime/high`, `TRANSACTIONAL → normal`, `NOTIFICATION → low/normal` (конфигурируемо).
**PM-04.** Опциональный SMPP-адаптер (ТЗ 7.2 допускает HTTP/SMPP) — отдельный модуль, включается конфигурацией; в MVP — HTTP.

### 9.2. SMS — SMS Gate API v4.3 (резервный провайдер, smsgw.vas.uz)

| Параметр | Значение |
|---|---|
| Протокол | HTTP POST, параметры `login` + `key` в каждом запросе |
| Методы | `/api/senders` (список имён отправителей), `/api/send` (единичная), `/api/v2/send` (единичная, возвращает `id`, `parts`), `/api/v2/send_msgs` (пакетная: `sender`, `weight`, `messages[{seq, phone, text}]`), `/api/create_distribution` + `/api/send_distribution|send_distribution2` (рассылки) |
| Приоритет | `weight` 0–10 (default 10) |
| Ответы | `status.code` (0 — success; 1 — spam-лимит 50 SMS/час/номер; 10–27 — ошибки авторизации/валидации, см. 18.2), `id`, `parts`; для батча — по каждому элементу `seq/id/code/parts` |
| DLR | FEEDBACK service: POST на URL партнёра `{login, key, id, code, description}`; статусы 0 Created / 1 Sending / 2 Fail / 3 Sent / 4 Delivered / 5 Rejected / 6 Unknown / 7 InBlackList; CDMA не поддерживается |
| Поиск | `/api/v2/search` по номеру и дате (Unix timestamp) — используется для реконсиляции статусов |

**SG-01.** Адаптер SMS Gate реализует тот же `SmsProviderPort`; различия контрактов (отсутствие шаблонов/timing на стороне провайдера) компенсируются на стороне Модуля: подстановка шаблона выполняется до отправки, отложенная отправка — планировщиком Модуля.
**SG-02.** Партнёрские состояния при приёме батча (`duplicate`, `blacklist`, `unknown operator`, `format error`, `empty`, `empty text`, `ok`) маппятся на канонические статусы/причины отклонения по 18.2.
**SG-03.** Реконсиляция: для сообщений без DLR в течение конфигурируемого окна — опрос `/api/v2/search`.
**SG-04.** Секрет `key` хранится в секрет-хранилище Банка (Vault/K8s secrets), в логах маскируется.

### 9.3. Email — корпоративный SMTP

**EM-01.** Адаптер `EmailProviderPort` → SMTP (STARTTLS/TLS), пул соединений, лимит скорости; поддержка HTML+plain text (multipart/alternative), вложения (лимит размера — конфиг), кастомные заголовки (`X-Comm-Message-Id` для сквозной идентификации).
**EM-02.** Обработка bounce: разбор NDR через выделенный ящик (IMAP-poller) либо DSN — механизм уточняется с почтовой командой; hard bounce → автоматическое добавление в suppression list (FR-5.1).
**EM-03.** Требования доставляемости (SPF/DKIM/DMARC) — зона инфраструктуры Банка; Модуль поддерживает подпись DKIM при необходимости (конфигурация).

### 9.4. Push — Firebase Cloud Messaging (FCM) и Apple Push Notification service (APNs)

Push-канал реализуется двумя адаптерами, оба реализуют единый `PushProviderPort`; выбор адаптера — по платформе токена получателя (`recipient.pushTokens[].platform`).

#### 9.4.1. Адаптер FCM (Android; опционально iOS/Web через Firebase SDK)

- **PU-01.** Протокол: **FCM HTTP v1 API** (`POST /v1/projects/{project}/messages:send`); аутентификация — OAuth2 service account (JSON-ключ в секрет-хранилище, автообновление access token). Legacy HTTP API не используется (выведен Google из эксплуатации).
- **PU-02.** Отправка — по одному сообщению на запрос (модель HTTP v1); массовая доставка достигается параллелизмом на виртуальных потоках (Java 25) с троттлингом на уровне провайдера (FR-2.5).
- **PU-03.** Поддерживаемые поля: `notification` (title, body, image), `data`-payload (key-value для deep link и бизнес-контекста), `android.priority` (`HIGH` для CRITICAL_OTP/TRANSACTIONAL, `NORMAL` для NOTIFICATION), `android.ttl` (из `timing.ttlSeconds`), `android.collapse_key` (схлопывание устаревших уведомлений одного типа), локализация — на стороне шаблонов Модуля.
- **PU-04.** Обработка ошибок FCM: `UNREGISTERED`/`NOT_FOUND` → токен помечается недействительным, публикуется событие `push-token.invalidated` для систем-источников, токен исключается из реестра доставки; `UNAVAILABLE`/`INTERNAL`/HTTP 5xx → retryable (backoff); `QUOTA_EXCEEDED`/429 → троттлинг с учётом `Retry-After`; `INVALID_ARGUMENT`/`SENDER_ID_MISMATCH`/`THIRD_PARTY_AUTH_ERROR` → non-retryable → `UNDELIVERED` с причиной.
- **PU-05.** Если мобильное приложение Банка для iOS использует Firebase SDK, допускается конфигурация «FCM как единый push-провайдер для обеих платформ» (FCM сам транслирует в APNs, блок `apns` в сообщении FCM); прямой APNs-адаптер при этом остаётся резервным путём. Режим задаётся конфигурацией канала.

#### 9.4.2. Адаптер APNs (iOS, прямое подключение)

- **PU-06.** Протокол: APNs Provider API поверх **HTTP/2** (`POST /3/device/{deviceToken}`, хосты `api.push.apple.com` / sandbox); аутентификация — token-based (JWT, ключ `.p8`, key id, team id; обновление JWT ≤ 1 раза в 20 мин и ≥ 1 раза в 60 мин). Заголовки: `apns-topic` (bundle id), `apns-push-type` (`alert`/`background`), `apns-priority` (10 — immediate для critical/transactional, 5 — power-considerate для массовых), `apns-expiration` (из TTL), `apns-collapse-id`.
- **PU-07.** Использование мультиплексирования HTTP/2 (сотни параллельных стримов на соединение) и пула соединений; переустановка соединений по `GOAWAY`.
- **PU-08.** Обработка ошибок APNs: `410 Unregistered` (и `BadDeviceToken`) → инвалидция токена + событие `push-token.invalidated`; `429 TooManyRequests`, `500/503` → retryable с backoff; `400 BadRequest`, `403 InvalidProviderToken/ExpiredProviderToken` (пересоздать JWT), `413 PayloadTooLarge` (лимит 4 КБ alert) → обработка по классификации; все причины из тела ответа (`reason`) сохраняются в `DeliveryAttempt`.

#### 9.4.3. Общие требования Push-канала

- **PU-09.** Мультитокенность получателя: одно логическое сообщение доставляется на все активные устройства клиента (несколько токенов, обе платформы); в статистике — агрегированный статус по получателю и детальный по каждому токену.
- **PU-10.** **Массовые push-рассылки** поддерживаются штатным механизмом батчей (FR-1.6): система-источник передаёт батч с получателями (clientId и/или токены), Модуль выполняет fan-out по адаптерам FCM/APNs с изоляцией класса `NOTIFICATION` (TC-01), троттлингом, quiet hours и suppression-фильтрами, с прогрессом и статистикой батча как у SMS. Целевые объёмы — по прогнозу ТЗ: ~17,2 млн push/мес, пик ~19,7 млн (см. 12.2), расчётная скорость fan-out ≥ 500 push/с на инстанс.
- **PU-11.** Контент: title, body, data-payload, deep link, image; локализация RU/UZ/EN на стороне шаблонов Модуля (FR-4.1); валидация размера payload (APNs 4 КБ, FCM 4 КБ) на этапе валидации сообщения.
- **PU-12.** Статусная модель Push ограничена подтверждением приёма платформой (APNs/FCM не дают DLR о показе) — канонический статус `SENT_TO_PROVIDER`; «доставлено/открыто» возможно только по событию-подтверждению из мобильного приложения (фаза 2, событие от приложения через Kafka → обновление статуса до `DELIVERED`).
- **PU-13.** Тестовая отправка (FR-7.4) поддерживает sandbox-контуры APNs и тестовые токены FCM.

### 9.5. Общие требования к адаптерам провайдеров

- **PR-01.** Таймауты (connect/read), retry с экспоненциальным backoff + jitter, circuit breaker (Resilience4j) — параметры задаются на провайдера и управляются из конфигурации.
- **PR-02.** Health-check каждого провайдера (синтетический probe и/или пассивные метрики) → статус в админ-панели и автоматический failover/failback (FR-6.3).
- **PR-03.** Все запросы/ответы провайдеров логируются структурированно (без PII в открытом виде — маскирование текста и номера), сохраняются `providerMessageId`, коды и латентность.
- **PR-04.** Contract-тесты адаптеров на основе WireMock-стабов из документации провайдеров; sandbox-доступы запрашиваются у провайдеров на этапе интеграции.

Оценка других каналов (из ТЗ): Email ≈ 30% объёма SMS (~3,4 млн/мес, пик ~3,9 млн); Push ≈ 150% объёма SMS (~17,2 млн/мес, пик ~19,7 млн). Inapp/Stories — не проектируются на данном этапе.

**NF-01.** Расчётная производительность приёма: устойчиво ≥ 100 msg/s на инстанс с линейным масштабированием (запас ≥ 10× к пиковому среднему); подтверждается нагрузочным тестом: батч 1 млн сообщений + параллельный поток OTP 20 msg/s без нарушения SLA OTP.
**NF-02.** Скорость выгрузки батча провайдеру ограничивается настроенным троттлингом провайдера, а не производительностью Модуля.
**NF-03.** RPO ≤ 0 для принятых сообщений (fsync-подтверждение записи до ack источнику); RTO ≤ 15 мин (уточняется с инфраструктурой Банка).
**NF-04.** Пиковые направления (из прогноза): Чакана (розница, включая OTP ~660 тыс./мес по одному шаблону), МСБ (транзакционные балансовые SMS >4 млн/мес), Ундирув (массовое взыскание до 1,8 млн/мес), СРМ (маркетинг ~1–1,7 млн/мес) — профиль подтверждает необходимость изоляции классов трафика.

### 12.3. Прочие NFR

- **NF-05.** Совместимость: JDK 25 LTS, контейнерный образ на базе согласованного базового образа Банка; работа в K8s/OpenShift (liveness/readiness/startup probes, graceful shutdown с дообработкой in-flight сообщений).
- **NF-06.** Конфигурация — 12-factor: через переменные окружения/ConfigMap + бизнес-конфигурация в БД; никакие секреты в git.
- **NF-07.** Время применения изменения конфигурации маршрутизации/провайдеров — ≤ 30 с без рестарта.
- **NF-08.** Zero-downtime миграции БД (expand/contract), обратная совместимость Kafka-схем (Schema Registry, режим BACKWARD).

## 13. Безопасность и соответствие требованиям

- **SEC-01.** Аутентификация систем-источников: REST — mTLS и/или OAuth2 client credentials (по стандарту Банка); Kafka — SASL/SCRAM или mTLS + ACL на топики (поток видит только свои данные).
- **SEC-02.** Аутентификация админ-панели — SSO (OIDC), сессии с таймаутом, MFA по политике Банка.
- **SEC-03.** RBAC на уровне API (метод × ресурс × скоуп), least privilege; критичные операции (kill switch, изменение провайдера) — с подтверждением и записью в аудит.
- **SEC-04.** Секреты провайдеров (Basic-креды Playmobile, `key` SMS Gate, ключи APNs/FCM, SMTP) — в секрет-хранилище; ротация без простоя.
- **SEC-05.** PCI DSS: в сообщениях запрещено передавать полный PAN; маскирование в шаблонах и валидатор контента (детектор PAN по алгоритму Луна — reject/алерт, режим настраивается); сегментация сети по требованиям PCI.
- **SEC-06.** Требования ЦБ РУз: хранение и аудит истории уведомлений, локализация данных в контуре Банка, ретенция (DB-03).
- **SEC-07.** Защита callback-endpoint'ов провайдеров: allowlist IP, секрет/подпись, rate limiting, отдельный ingress.
- **SEC-08.** Журналирование доступа к ПДн (кто просматривал сообщения клиента) — в аудит.
- **SEC-09.** Статический и динамический анализ (SAST/DAST/dependency scanning) в CI; уязвимости critical/high блокируют релиз.

## 14. Наблюдаемость и эксплуатация

- **OBS-01.** Метрики (Micrometer → Prometheus): принято/отправлено/доставлено/ошибки по каналу-провайдеру-потоку-классу; латентности этапов pipeline (в т.ч. отдельно OTP end-to-end); глубины очередей/лагов Kafka; состояние circuit breaker'ов; квоты.
- **OBS-02.** Distributed tracing (OpenTelemetry): trace от приёма (REST/Kafka) до вызова провайдера и публикации статуса; `correlationId` источника прокидывается в baggage и логи.
- **OBS-03.** Structured logging (JSON): messageId, streamId, batchId, correlationId в MDC; маскирование PII; централизованный сбор (ELK/Loki Банка).
- **OBS-04.** Алерты: нарушение SLA OTP, delivery rate ниже порога, рост error rate провайдера, открытие circuit breaker, лаг консьюмера, переполнение DLQ, исчерпание квот, недоступность БД/Kafka.
- **OBS-05.** Дашборды Grafana: обзорный, по-канальный, по-провайдерный, инфраструктурный — артефакт поставки.
- **OBS-06.** Runbook эксплуатации: типовые инциденты (провайдер недоступен, разбор DLQ, восстановление после сбоя, ручной failover) — артефакт поставки.

## 18. Приложения

### 18.1. Playmobile: коды ошибок и маппинг

Ошибки API (HTTP 400, поле `error_code`):

| Код | Описание | Классификация ретрая |
|---|---|---|
| 100 | Internal server error | retryable |
| 101 | Syntax error | non-retryable (bug/контракт) |
| 102 | Account lock | блокирующая → circuit breaker + алерт |
| 103 | Empty channel | non-retryable |
| 104 | Invalid priority | non-retryable |
| 105 | Too much IDs | non-retryable (уменьшить чанк) |
| 202 | Empty recipient | non-retryable → REJECTED |
| 204 | Empty email address | non-retryable |
| 205 | Empty message-id | non-retryable (bug) |
| 206 | Invalid variables | non-retryable → REJECTED |
| 301–306 | Invalid localtime / start-datetime / end-datetime / allowed-starttime / allowed-endtime / send-evenly | non-retryable |
| 401 | Empty originator | non-retryable |
| 402 | Empty application | non-retryable |
| 403 | Empty ttl | non-retryable |
| 404 | Empty content | non-retryable → REJECTED |
| 405 | Content error | non-retryable → REJECTED |
| 406 | Invalid content | non-retryable → REJECTED |
| 407 | Invalid ttl | non-retryable |
| 408 | Invalid attached files | non-retryable |
| 410/411 | Invalid retry-attempts / retry-timeout | non-retryable |

DLR-статусы Playmobile (канал `sms`, поле `status` callback'а) маппятся на канонические статусы: доставлено → `DELIVERED`; недоставлено/expired → `UNDELIVERED`/`EXPIRED`; передано оператору → `SENT_TO_PROVIDER` (промежуточный). Точный перечень значений `status` фиксируется на этапе интеграции с Playmobile.

### 18.2. SMS Gate v4.3: статусы и коды

Статусы DLR (FEEDBACK, поле `code`):

| Код | Статус | Канонический |
|---|---|---|
| 0 | Created | SENT_TO_PROVIDER |
| 1 | Sending | SENT_TO_PROVIDER |
| 2 | Fail | UNDELIVERED (retryable через другой провайдер по политике) |
| 3 | Sent | SENT_TO_PROVIDER |
| 4 | Delivered | DELIVERED |
| 5 | Rejected | UNDELIVERED (non-retryable у данного провайдера) |
| 6 | Unknown | UNDELIVERED/UNKNOWN (реконсиляция SG-03) |
| 7 | InBlackList | REJECTED + кандидат в suppression |

Коды ответов API: 0 success; 1 spam (лимит 50 SMS/час на номер — учитывать в троттлинге); 10 login required; 11 key required; 12 partner not found; 13 wrong key; 14 phone required; 15 sender required; 16 wrong sender; 17 phone not match to pattern; 18 text required; 19 text too long; 20 receiver in blacklist; 21 unknown operator; 22 distribution name required; 23 distribution not created; 24 distribution_id is required; 25 distribution not found; 26 distribution is expired; 27 server side error (retryable).

Состояния элементов батча: `ok`, `duplicate`, `blacklist`, `unknown operator`, `format error`, `empty`, `empty text` — маппятся на `REJECTED` с соответствующей причиной (кроме `ok`).

### 18.3. Длина SMS и сегментация

| Кодировка | 1 часть | Каждая часть длинного сообщения | 2 / 3 / 4 / 5 / 6 / 7 частей |
|---|---|---|---|
| GSM-7 (латиница) | 160 | 153 | 306 / 459 / 612 / 765 / 918 / 1071 |
| UCS-2/Unicode (кириллица и др.) | 70 | 67 | 134 / 201 / 268 / 335 / 402 / 469 |

Примечания: наличие хотя бы одного не-GSM-символа переводит всё сообщение в UCS-2; символы `^ { } \ [ ~ ] | €` в GSM-7 считаются за два. `SegmentCalculator` обязан воспроизводить эти правила; количество сегментов используется в расчёте стоимости и квот.

### 18.4. Справочник направлений (систем-источников) из прогноза 2026

МСБ, Чакана (розница), Ундирув (взыскание), СРМ, Оперблок, Корпоратив, Маркетинг, ИТ, Кадр (HR), Тез банк, Риск, Бошка (прочие) — каждое направление/система регистрируется как отдельный входящий поток с собственными квотами и статистикой (FR-1.3, FR-2.6); прогнозные месячные объёмы направлений используются для первичной настройки квот.

### 18.5. Варианты механизма кампаний без списка получателей (проработано, реализация отложена — FR-8.11)

Требование-кандидат: запуск массовой рассылки одной командой (`templateId` или текст шаблона + параметры), без передачи Модулю списка контактов — аудиторию определяет сам Модуль. Противоречит текущему ограничению ТЗ п. 3 (аудитория — зона ответственности систем-источников), поэтому реализация требует изменения ТЗ. Рассмотренные варианты:

| Вариант | Механизм | Плюсы | Минусы |
|---|---|---|---|
| **A. Топики провайдера (FCM Topics)** | Приложение подписывает устройства на топики; команда = `templateId + topic`; fan-out выполняет FCM одним запросом | Минимальная инфраструктура; нет ПДн в Модуле; мгновенный охват | Нет per-user статистики, suppression, quiet hours; сегментация ограничена топиками; слабый аудит; только push |
| **B. Собственный реестр получателей** | Системы Банка публикуют события контактов/токенов в Kafka; Модуль ведёт реестр (PostgreSQL); команда = `templateId + критерии сегмента`; Модуль резолвит аудиторию из реестра и прогоняет через штатный pipeline | Полный контроль: статусы, compliance-фильтры, стоимость; работает для Push/SMS/Email; межканальный fallback | Модуль хранит контактные данные (правка ТЗ, согласование ИБ); нужен пайплайн синхронизации и контроль актуальности |
| **C. Внешний сервис аудиторий (pull)** | Команда = `templateId + audienceRef` (сегмент в CDP/CRM/витрине); Модуль потоково вытягивает аудиторию чанками в момент запуска, постоянно не хранит | Владелец аудитории — системы Банка (принцип ТЗ сохранён); свежие данные; полная статистика | Зависимость от SLA сервиса аудиторий; сервис/API нужно создать |
| **D. Гибрид (B + C + A)** | Единая сущность «Кампания», резолвер аудитории — порт `AudienceResolverPort` с адаптерами: реестр, audienceRef, FCM topic | Гибкость под сценарии; ложится в гексагональную архитектуру одним портом | Наибольший объём работ |

Статус: **решение о выборе варианта не принято, реализация отложена** (см. открытый вопрос № 11). В MVP предусматривается только порт `AudienceResolverPort` в ядре без реализаций, чтобы последующее включение любого варианта не требовало переработки pipeline.
