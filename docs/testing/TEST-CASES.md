# Тест-кейсы сквозного интеграционного тестирования

Кейсы к [`INTEGRATION-TEST-SPEC.md`](INTEGRATION-TEST-SPEC.md): что именно проверяется на пути сообщения от входа до статусного события. Требования — из SRS [`../sms-notification-hub-spec.md`](../sms-notification-hub-spec.md).
**Спецификация авторитетна**: при расхождении прав SRS, а расхождение здесь является дефектом документации.

## Как читать кейс

**ID** — `IT-<область>-NNN`. Новых `QA-*` документ не вводит: SRS авторитетна, и требования в неё не добавляются документом второго уровня. Каждый кейс трассируется на существующий идентификатор в колонке «Треб.».

**REST / Kafka** — через какие входы кейс исполняется. Две галочки означают **один текст теста, исполняемый дважды** (`@ParameterizedTest` по `Ingress`), а не два теста. Прочерк с пояснением в §3 спецификации означает, что функции на этом входе нет по устройству, а не по недоделке.

**Покрытие** — ✅ и имя класса, если кейс уже закрыт; 🟡 если закрыт частично (что именно не покрыто — в примечании); ⏳ если теста нет.

**Предусловия** ссылаются на эталонный контур (§2 спецификации): `ibank-otp`, `marketing-bulk`, `quota-day`, шаблоны `OTP_RU_UZ`/`DRAFT_ONLY` и т. д. Всё, чего там нет, кейс создаёт сам.

**Адреса решают поведение провайдера** (§2.3): `…00` доставлено, `…01` не доставлено, `…02` нет ответа, `…03` блокирующий отказ, `…04` непригодный адрес. Для SMS это MSISDN (`998901234500`), для PUSH — токен, для EMAIL — часть до `@` (`ivan04@example.com`).

**SQL-обвязка.** У каждого кейса есть блок в [`sql/testing/cases/`](../../sql/testing/cases/): предусловия сверх эталонного контура и проверочные запросы. Прогон одного кейса целиком — `sql/testing/bin/run-case.sh IT-FLT-006`: очистка состояния и топиков → контур → предусловия → *действие* → проверки → уборка. Подробности и подвохи (`(0 rows)` — это не «прошло») — в [`sql/testing/README.md`](../../sql/testing/README.md).

**Легенда:** ✅ покрыто · 🟡 частично · ⏳ теста нет · ⚠️ оговорка.

## Чего в кейсах нет — и почему

**Кейсов «оператор нажал кнопку».** Панель читает то, что записал этот путь; её сценарии — QA-07, [`../frontend-spec/09-testing.md`](../frontend-spec/09-testing.md).

**Кейсов на каждый код ошибки провайдера.** §18.1 и §18.2 разбираются контрактными IT адаптеров. Здесь взято по одному представителю на класс (`RETRYABLE`, `NON_RETRYABLE`, `BLOCKING`) — предметом является поведение саги, а не таблица кодов.

**Цифр производительности.** «Отправлено за N мс» в интеграционном тесте измеряет машину. `IT-TC-005` проверяет изоляцию качественно; p99 из TC-01 — нагрузочный прогон (QA-05, [`../../load/`](../../load/)).

**Кейсов на согласие клиента (FR-8.2).** `CustomerPreferencePort` — задокументированная заглушка: она всегда отвечает «записи нет». Кейс на ветку `OPT_OUT` появится вместе с настоящим реестром согласий, а до тех пор проверял бы заглушку.

**Кейсов на FR-8.11 (кампании без списка получателей).** Вне объёма Модуля; в ядре зарезервирован только неиспользуемый `AudienceResolverPort`.
