## 2. Дефект D-11 — квота из панели молча становится `ALERT_ONLY`

**Где:** `adapter/in/admin/.../mapper/AdminCommandMapper.java`, `behaviorOf`.

```java
return behavior == null ? QuotaExhaustionBehavior.ALERT_ONLY : behavior;
```

Поле «При превышении» в трёх формах панели (поток, канал, провайдер) — `Select allowClear` без
значения по умолчанию; контракт дефолт не документировал; подсказка говорила про несуществующее
`BLOCK`. Оператор, заполнивший только «Сообщений в сутки», получал квоту, которая **считает,
алертит и не останавливает ничего**, а панель при следующем открытии показывала подставленное
значение так, будто его выбрали.

### 2.1. Воспроизведение на стенде

Квота 3/сутки заведена ровно так, как её заводит оператор, — `PUT /api/admin/v1/streams/core-banking`
с телом `{"name":"Core Banking","quota":{"dailyCount":3}}`. Ответ `200`, и в нём уже видно
подставленное:

```json
"quota": {"dailyCount": 3, ..., "behavior": "ALERT_ONLY"}
```

Пять документов в `comm.inbound.transactional.v1`:

```
  status   | status_reason | count        window_type | counter      attempts
-----------+---------------+-------      ------------+---------     ---------
 DELIVERED |               |     5        DAY        |       5             5
                                          MONTH      |       5
```

**Пять из пяти доставлены при квоте три.** Это и есть жалоба.

### 2.2. Контроль — та же квота с явным поведением

Тот же поток, тот же топик, те же пять документов, отличается одно поле —
`"behavior":"BLOCK_AND_ALERT"`:

```
  status   | status_reason  | count       window_type | counter      attempts
-----------+----------------+-------      ------------+---------     ---------
 DELIVERED |                |     3        DAY        |       3             3
 REJECTED  | QUOTA_EXCEEDED |     2        MONTH      |       3
```

Контроль закрывает вопрос о транспорте: **квоты на Kafka работают**. Дефект был в том, какое значение
попадало в базу из панели.

### 2.3. Исправление

Пустое `behavior` при **заданном хотя бы одном потолке** — отказ `400` с указателем на поле, ровно как
у соседнего окна тишины (`QuietHours` требует `behavior` через `Guard.notNull`). Квота без единого
потолка по-прежнему допускает пустое поле: блокировать там нечего.

Проверено на стенде после правки:

```
PUT /streams/core-banking  {"quota":{"dailyCount":3}}
  → 400 {"code":"VALIDATION_FAILED","field":"quota.behavior","detail":"quota.behavior: is required"}
PUT /streams/core-banking  {"quota":{"dailyCount":3,"behavior":"BLOCK_AND_ALERT"}}   → 200
PUT /streams/core-banking  {"quota":{}}                                              → 200
```

Правка не переписывает уже сохранённые квоты: **ту, что заведена на живом контуре, надо пересохранить
с `BLOCK_AND_ALERT`**, иначе она так и останется алертящей.

Тронуто: `AdminCommandMapper.behaviorOf` + `QuotaDto` (javadoc), схема `Quota` в
`comm-hub-admin-v1.yaml`, общий компонент формы `web/src/shared/components/QuotaBehaviorItem.tsx`
(поле обязательно, когда заполнен любой потолок — во всех трёх формах) и подсказки `ru/uz/en`.
Пять проверок в новом `AdminCommandMapperTest`.

## 3. Дефект D-12 — отказ панельной отправки приходил как `200`

**Где:** `SendAdminController.send` и `ProviderAdminController.testSend` отдавали
`acceptedMapper.toAccepted(...)` без проверки `result.isAccepted()`.

Оператор, упершийся в квоту, получал `200 {"messageId":"…","status":"REJECTED"}` — без кода, без
причины, без `429`. В §8.2 та же развилка сделана правильно (`MessageController` бросает
`SubmissionRejectedException`), и javadoc `MessageAcceptedResponse` уже утверждал «A refusal never
comes back here» — неправдой это было ровно здесь.

После правки, квота 1/сутки на `core-banking`, две отправки из панели подряд:

```
#1 → 200 {"messageId":"019ffbe9-9ddf-7556-89fd-6515293d4d8a","status":"QUEUED"}
#2 → 429 {"code":"QUOTA_EXCEEDED","detail":"quota of stream core-banking is exhausted",
          "messageId":"019ffbe9-9e10-704b-8821-8dc705684c36"}
```

Новой advice не потребовалось: `SubmissionRejectionHandler` — bare `@RestControllerAdvice` и
обслуживает админ-цепочку наравне с §8.2. `/send/batch` не тронут намеренно: там поэлементные отказы
приходят в `failures[]`, и `202` осмыслен. Пинится `SendAdminControllerTest` (429 при отказе,
200 при приёме).

### 4.4. Как отказ конвейера виден на Kafka-входе

Проверка вне кейсов, ради вопроса «Kafka же не может ничего сообщить». Отказ по подавлению, поданный
в `.transactional.v1`:

```
parse-error, суммарный end offset до:    12
parse-error, суммарный end offset после: 12      ← ни одной новой записи

message:      REJECTED / SUPPRESSED
outbox_event: REJECTED / SUPPRESSED / published = t
лог:          INFO InboundMessageListener : Refused TRANSACTIONAL message
              core-banking/kobs-2-1: REJECTED (SUPPRESSED)
```

То есть у отказа конвейера на Kafka-входе **четыре следа и ни одного из них — в топике ошибок**:
строка `message` с каноничной причиной, событие §6.4 в `comm.outbound.status.v1` (с `reason` и
`reasonDetail`, см. §4.1), метрика и INFO-строка листенера; offset коммитится. `comm.inbound.parse-error.v1`
принимает только **нечитаемый документ** — то самое правило, что доказал `IT-ING-014` на этапе 2.

## 5. Отклонения от эталонного контура

1. **Ночной прогон и окно тишины контура.** Заход шёл после 21:00 по Ташкенту, а `01-contour.sql`
   даёт `marketing-bulk` окно 21:00–09:00 `REJECT`. Первая же попытка воспроизвести жалобу на
   `marketing-bulk` дала пять `QUIET_HOURS` — отказ **стадией раньше** квоты. Поэтому:
   - воспроизведение и контроль (§2) сделаны на `core-banking` — поток без окна;
   - у `IT-FLT-014/015/016` (частота) окно `marketing-bulk` уводится в прошлое одной строкой после
     `@arrange`: предмет этих кейсов — частотный порог, а не тихие часы, и ночь не должна их отменять.
   Кейсы, чей предмет **есть** окно (`IT-FLT-005…013`), строят окно вокруг «сейчас» сами и от времени
   суток не зависят — их не трогали.
2. **`IT-QTA-003`** — три сообщения поданы из `core-banking`, `ibank-otp` и `rate-limited`: нужны потоки
   **без собственных квот** (иначе отказ придёт измерением «stream») и **без окна тишины** (иначе ночью
   придёт `QUIET_HOURS`). В REST-половине третьим был `marketing-bulk`.
3. **`IT-FLT-008`** — как и в REST-половине, окно заводится с концом через две минуты, а не переносится
   в прошлое: перенос не трогает уже назначенный `next_attempt_at`, и диспетчер строку не заберёт.
4. **`IT-FLT-013`** — сообщение придержано `timing.sendAfter` (такт `NOTIFICATION` — одна секунда).
5. **`IT-QTA-006`** — текст на два сегмента: 100 символов кириллицы.

Конфигурация контура при этом не менялась — правки касаются только состояния и тел документов. После
прогона выполнен `99-teardown.sql`.
