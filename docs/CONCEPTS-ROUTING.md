# Провайдер, канал, поток, политика, fallback — что это и зачем

Пять понятий, из которых собирается маршрут сообщения. Здесь — назначение каждого и как они
складываются при отправке; пошаговая настройка «от пустой базы» — в
[`QUICKSTART-SEND.md`](QUICKSTART-SEND.md), экраны панели — в [`ADMIN-GUIDE.md`](ADMIN-GUIDE.md),
требования — в [`sms-notification-hub-spec.md`](sms-notification-hub-spec.md) §6.1.

---

## Провайдер (`Provider`)

Профиль **конкретного отправителя**: Playmobile, SMS Gate, SMTP-релей, FCM, APNs, фиктивный `MOCK`.

Хранит код (`^[A-Z0-9][A-Z0-9_]{1,31}$`), канал, `adapterType` — какой развёрнутый адаптер его
обслуживает, — вес для балансировки, тариф, лимиты скорости, квоту и `endpointConfig`
(отправитель/originator, приоритеты, TTL по умолчанию). Учётные данные в базе **не лежат**: они
приезжают из окружения пода обычным Spring-плейсхолдером (ADR-0044).

**Зачем.** Чтобы «куда физически уходит сообщение» было строкой в базе, а не в коде: добавление
провайдера — это новый адаптер и новая строка, домен и application-слой не меняются (AR-04). Второе
назначение — **состояние здоровья**: `UNKNOWN` / `UP` / `DOWN` / `MAINTENANCE` / `DISABLED`. Невыбираемым
делают только три последних, `UNKNOWN` маршрутизируется (провайдер без трафика никогда не наберёт
статистики, которая его оправдает). `DOWN` выкидывает провайдера из цепочки — failover получается сам
собой, без отдельного кода.

## Канал (`ChannelConfig`)

Профиль **транспорта**: `SMS`, `EMAIL`, `PUSH`. Набор каналов фиксирован enum'ом, но профиль сам собой
не появляется — `PUT /api/admin/v1/channels/{channel}` работает как upsert и создаёт его.

Хранит `fallbackOrder` (упорядоченный список кодов провайдеров), `balancingStrategy`, окно тишины,
квоту канала и статус.

**Зачем.** Это **нижний уровень политики** — действует на весь трафик канала, пока поток не
переопределит. Главное в нём — `fallbackOrder`: провайдеры для маршрутизации берутся **только** оттуда
(`FallbackChain.providerChain`). Схема пустой порядок допускает, поэтому канал без него выглядит
настроенным и не маршрутизирует ничего — самая частая ошибка первичной настройки, отвечает
`NO_ROUTE_AVAILABLE / channel SMS is not configured`.

## Поток (`Stream`)

**Система-источник**: мобильный банк, процессинг, антифрод. `streamId`
(`^[a-z0-9][a-z0-9._-]{1,63}$`) обязателен в каждом документе IK-03 и после регистрации не меняется.

Хранит имя, лимиты REST (IR-02), квоту, канал по умолчанию и **переопределения** канального профиля —
балансировку и окно тишины.

**Зачем.** Единица учёта, авторизации, квотирования и статистики: токен машины несёт claim со списком
разрешённых потоков (SEC-01), квоты считаются по потоку, экраны фильтруются по нему. Способ интеграции
у потока **не хранится** — один и тот же поток принимается и по REST, и из Kafka, транспорт выбирает
источник в момент вызова (ADR-0045).

> Переопределения потока заменяют канальное значение **целиком**, а не пересекаются с ним: окно тишины
> потока 23:00–07:00 поверх канального 21:00–09:00 даёт для этого потока ровно 23:00–07:00. Порядок
> провайдеров поток задать не может — он всегда канальный.

## Политика маршрутизации (`RoutingPolicy`)

Декларативное правило `Match → Action`, лежащее в базе и применяемое без рестарта (AD-07):

- **Match** — поток, класс трафика, приоритет, канал (любое поле может быть пустым = «любой»);
- **Action** — какой канал использовать, какой порядок провайдеров и какую балансировку.

Правила перебираются по убыванию `priority`, **первое совпавшее выигрывает**.

**Зачем.** Чтобы **развести трафик**, а не чтобы «заработало». С нулём политик всё работает: канал
берётся из плана сообщения или дефолта потока, провайдеры — из `fallbackOrder` канала. Политику заводят,
когда OTP надо гнать через дорогого надёжного провайдера, а массовую рассылку — через дешёвого.

## Fallback (`FallbackChain`)

Резервный порядок попыток. Уровней **два**:

- **внутри канала** — тот самый `fallbackOrder`: провайдер отказал → берём следующий из списка,
  пропуская выключенные, находящиеся в обслуживании, отмеченные `DOWN` и уже испробованные в этом
  сообщении (FR-2.2, FR-2.7, FR-6.3);
- **между каналами** — цепочка `ChannelPlan`, например PUSH → SMS: не достучались пушем — ушло смской
  (MP-03, FR-8.1).

**Зачем.** Доставляемость. Отдельной «настройки failover» в системе нет и не нужно: порядок выбора
провайдеров **и есть** порядок переключения при отказе.

## Как это складывается при отправке

`Router` за один проход:

1. находит подходящую политику (поток + класс трафика + приоритет);
2. выбирает канал: политика → план сообщения → дефолт потока → первый канал, на котором адресат
   достижим (FR-2.4, MP-03);
3. берёт профиль этого канала — нет профиля или он не принимает трафик, значит маршрута нет;
4. строит цепочку провайдеров через `FallbackChain` поверх `fallbackOrder`;
5. применяет балансировку — политики, а если её нет, то канала.

Роутер не знает ни одного провайдера по имени: он возвращает `ProviderRef`, а конкретный адаптер
резолвится в application-слое (MP-05, AR-04). Round-robin он тоже не хранит — позиция приходит снаружи,
так что один экземпляр обслуживает все виртуальные потоки.

## Порядок настройки

```
провайдер ──► канал ──► поток ──► шаблон ──► [политика маршрутизации]
             (fallbackOrder
              ссылается на код
              провайдера)
```

Переставить нельзя: `fallbackOrder` канала — список кодов провайдеров, и код, который ещё не
зарегистрирован, канал не примет. Политика — необязательный пятый шаг.

Правки применяются **без рестарта, но не мгновенно**: снапшот конфигурации кешируется на
`commhub.config.cache.refresh-interval` (10 с по умолчанию, потолок 30 с по NF-07).
