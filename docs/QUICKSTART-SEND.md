# От пустой базы до доставленной SMS

После первого старта конфигурация маршрутизации пуста: миграции заводят только `kill_switch` и таблицу
ролей, seed-скрипта нет и не будет (`DEPLOYMENT.md` §5.4 — маршрутизация контура не приезжает из чужого
дампа). Поэтому первая же отправка отвечает `NO_ROUTE_AVAILABLE`. Здесь — что завести, чтобы маршрут
нашёлся, и как подать сообщение тремя способами.

Все запросы `/api/admin/v1/**` требуют bearer-токен (открытого режима у панели нет, ADR-0037); тела —
`application/json`, где не сказано иное. Те же действия мышью, экран за экраном, — в
[`ADMIN-GUIDE.md`](ADMIN-GUIDE.md); развёртывание и секреты — в [`DEPLOYMENT.md`](DEPLOYMENT.md).

---

## 1. Порядок настройки

```
провайдер ──► канал ──► поток ──► шаблон ──► [политика маршрутизации]
             (fallbackOrder
              ссылается на код
              провайдера)
```

- **Провайдер первым.** `fallbackOrder` канала — список кодов провайдеров, и код, который ещё не
  зарегистрирован, канал не примет.
- **Канал вторым, и с непустым `fallbackOrder`.** Провайдеры для маршрутизации берутся **только**
  оттуда (`FallbackChain.providerChain`). Схема пустой порядок допускает, поэтому канал без него
  выглядит настроенным и не маршрутизирует ничего — самая частая ошибка первичной настройки.
- **Поток третьим.** На маршрут он не влияет, но `streamId` обязателен в каждом документе.
- **Шаблон четвёртым** — и только если отправляете из панели: поля текста там нет вовсе (ADR-0038).
  Для REST и Kafka достаточно инлайнового `content`.
- **Политика маршрутизации не нужна.** С нулём политик канал берётся из плана сообщения или дефолта
  потока, провайдеры — из `fallbackOrder`. Политики заводят, чтобы развести трафик, а не чтобы
  «заработало».

Правки применяются **без рестарта, но не мгновенно**: снапшот кешируется на
`commhub.config.cache.refresh-interval` (10 с по умолчанию, потолок 30 с по NF-07). Если сразу после
правки ничего не изменилось — подождите полминуты, прежде чем править ещё раз.

## 2. Настройка

Сквозной пример — на **фиктивном провайдере** (ADR-0041): не HTTP-заглушка, а настоящий адаптер
(`mock-sms` / `mock-email` / `mock-push`), умеющий ретрай, failover и открытие breaker'а и присылающий
отчёт о доставке отложенно. Включён только локально (`commhub.provider.mock.enabled` в корневом
`config/application.yml`), в образ не попадает, своего профиля не заводит. Боевой — §5.

### 2.1. Профиль провайдера

```http
POST /api/admin/v1/providers/MOCK

{ "channel": "SMS", "adapterType": "mock-sms" }
```

Обязательны код в пути (`^[A-Z0-9][A-Z0-9_]{1,31}$`, ЗАГЛАВНЫМИ), `channel` и `adapterType`
(`^[a-z0-9][a-z0-9-]{1,31}$`, строчными). Опционально: `weight` (по умолчанию `10`), `tariff`,
`rateLimit`, `quota`, `endpointConfig`. Правка профиля идёт уже по идентификатору —
`PUT /api/admin/v1/providers/{providerId}`, и канал с типом адаптера там не меняются.

Профиль создаётся `enabled`, здоровье `UNKNOWN` — это **выбираемое** состояние (невыбираемым делают
только `DOWN`, `DISABLED` и `MAINTENANCE`), так что маршрутизируется он сразу.

> **Тип адаптера при регистрации не проверяется**: профиль заведётся, маршрут найдётся, а отправка
> упадёт с `no adapter deployed for provider MOCK (mock-sms)` — это не `NO_ROUTE_AVAILABLE` (§6).
> Развёрнутое на этом поде отдаёт `GET /api/admin/v1/providers/adapters` (ADR-0042).

### 2.2. Профиль канала

```http
PUT /api/admin/v1/channels/SMS

{ "balancingStrategy": "PRIMARY_ONLY", "fallbackOrder": ["MOCK"] }
```

Набор каналов фиксирован (`SMS`, `EMAIL`, `PUSH`), но *профиль* канала сам собой не появляется: `PUT`
работает как upsert и создаёт его. Обязателен только `balancingStrategy` (умолчания в базе нет);
`quietHours` и `quota` опциональны.

**`fallbackOrder` схема не требует, но заполнить его надо сразу** — порядок выбора и есть порядок
переключения при отказе, а канал с пустым порядком остаётся без маршрута.

Профиль канала — нижний уровень политики: он действует для всего трафика канала, пока поток не
переопределит балансировку или окно тишины (§2.3). В профиле *провайдера* ни того ни другого нет.

### 2.3. Поток

```http
POST /api/admin/v1/streams/demo-app

{ "name": "Демо-приложение", "integrationType": "REST" }
```

Обязательны `name` и `integrationType`; идентификатор в пути — `^[a-z0-9][a-z0-9._-]{1,63}$`,
**строчными**, и после регистрации не меняется: системы-источники указывают его в каждом сообщении.
Правка — `PUT /api/admin/v1/streams/{streamId}`, где `null` значит «не трогать», а окно тишины
снимается флагом `clearQuietHours: true`.

Опциональны `quota` (`BLOCK_AND_ALERT` отклоняет, `ALERT_ONLY` пропускает и сигнализирует), `rateLimit`
(IR-02) и `quietHours`; без квоты поток не ограничен. **`integrationType` (`KAFKA` или `REST`) ничего
не ограничивает** — значение описательное, его не читает ни один listener: поток, заведённый как
`REST`, принимает и из Kafka.

> **Балансировка и окно тишины у потока — переопределения профиля канала, а не вторая копия
> настройки.** Пусто — действует канальное. Заполнено — заменяет канальное **целиком**, а не
> пересекается с ним: окно потока 23:00–07:00 поверх канального 21:00–09:00 даёт для этого потока
> ровно 23:00–07:00. Порядок провайдеров поток задать не может — он всегда канальный. OTP и
> транзакционные сообщения окно тишины не соблюдают ни на одном уровне.

### 2.4. Шаблон — только если отправляете из панели

Карточка (`direction` — бизнес-направление Банка: МСБ, Чакана, …):

```http
POST /api/admin/v1/templates/DEMO_OTP

{ "channel": "SMS", "direction": "Чакана", "owner": "retail" }
```

Обязателен только `channel`; `direction` и `owner` опциональны. Код в пути —
`^[A-Z0-9][A-Z0-9._-]{1,63}$`.

Черновик версии — `PUT`, а не `POST`: черновик перезаписывается, пока он черновик.

```http
PUT /api/admin/v1/templates/DEMO_OTP/versions

{ "locale": "RU", "text": "Здравствуйте, {NAME}! Ваш код: {CODE}" }
```

Обязательны `locale` и `text`. Опционально: `subject`, `html` (только вместе с текстом и только для
email) и **`version` — поле тела**, а не путь: без него заводится следующая версия. В ответе —
`version: 1`, `status: "DRAFT"`, разобранный список `variables` (`["NAME","CODE"]`), сам текст лежит в
`body.text`, автор — в `review.createdBy`.

Дальше workflow `DRAFT → ON_REVIEW → PUBLISHED` (FR-4.1); последний сегмент пути — `{status}`:

```http
POST /api/admin/v1/templates/DEMO_OTP/versions/RU/1/state/ON_REVIEW
POST /api/admin/v1/templates/DEMO_OTP/versions/RU/1/state/PUBLISHED
```

Статусы версии: `DRAFT`, `ON_REVIEW`, `PUBLISHED`, `ARCHIVED`; отказ ревьюера — это возврат в `DRAFT`.

> **Публикацию проводит второй человек** (FR-4.2): автор версии и публикующий обязаны различаться, и
> оба берутся из учётной записи, а не из полей формы. Локально черновик пишет `template-manager`,
> публикует `demo` — роли §10.1 заведены отдельными пользователями, пароль равен логину. Это самое
> частое место, где сценарий встаёт.

Ещё две вещи, которые путают: **статус карточки и статус версии — разные словари** (карточка бывает
`ACTIVE`/`ARCHIVED` и новая уже `ACTIVE`; отправляемым шаблон делает публикация версии), и
**публикация новой версии архивирует предыдущую в той же локали** — сендовая версия в локали всегда
одна. Переменные пишутся как `{NAME}`.

### 2.5. Проверка маршрута

```http
POST /api/admin/v1/routing/evaluate

{ "streamId": "demo-app", "channel": "SMS",
  "recipient": { "msisdn": "998901234500" }, "text": "проверка" }
```

Обязательны `streamId` и `recipient`; `channel`, `trafficClass`, `priority` и `text` опциональны.

Dry-run **ничего не отправляет**: сообщение строится в памяти и прогоняется через настоящий
маршрутизатор по настоящей конфигурации. В ответе — `routed`, канал, провайдер, `fallbackProviders`,
стратегия, `segments`, `estimatedCost`, а если маршрута нет — `rejection` с причиной (§6).

### 2.6. Поведение фиктивного провайдера

Задаётся **последними двумя символами адреса**, а не настройкой:

| Суффикс | Что делает | Зачем |
|---|---|---|
| `…00` | принято, затем `DELIVERED` | обычный happy path |
| `…01` | принято, затем `UNDELIVERED` | отчёт о недоставке |
| `…02` | ответа нет (бросает) | ретрай и failover |
| `…03` | блокирующий отказ, код `102` | circuit breaker открывается сразу |
| `…04` | адрес непригоден, код `20` | попадание в suppression list |
| прочее | принято, затем `DELIVERED` | |

Отчёт о доставке приходит через `report-delay` (локально 3 с), поэтому `SENT_TO_PROVIDER` в первые
секунды — норма, а не залипание.

## 3. Отправка

Всё ниже работает против конфигурации из §2.

### 3.1. Из панели

Содержимое берётся **только из опубликованного шаблона** (ADR-0038) — поля текста в этом разделе нет.
Порядок жёсткий: **сначала смета, потом отправка**; любая правка формы сбрасывает смету, а если
маршрута нет — подтвердить будет нельзя.

```http
POST /api/admin/v1/send/estimate          # затем POST /api/admin/v1/send/message с тем же телом

{ "streamId": "demo-app", "templateCode": "DEMO_OTP", "locale": "RU", "channel": "SMS",
  "recipient": { "msisdn": "998901234500" },
  "variables": { "NAME": "Иван", "CODE": "123456" } }
```

Обязательны `streamId`, `templateCode`, `locale`, `channel`, `recipient`; `trafficClass`, `variables` и
`externalId` опциональны (без последнего идентификатор генерируется как `panel-<uuidv7>`). Смета
отвечает числом получателей, сегментами, стоимостью, провайдером, версией шаблона, `missingVariables`
и нечитаемыми строками файла.

**`X-Commhub-Reason` обязателен на всём, что отправляет** — на `/send/message` и `/send/batch` — и не
нужен на `/send/estimate`. Значение передаётся **percent-encoded UTF-8**: значение HTTP-заголовка есть
байтовая строка, и кириллица в нём иначе не проходит.

Массовая отправка — тот же шаблон, но получатели приходят файлом, а параметры переезжают в query:

```http
POST /api/admin/v1/send/batch?streamId=demo-app&templateCode=DEMO_OTP&locale=RU&channel=SMS
Content-Type: text/csv
X-Commhub-Reason: <percent-encoded UTF-8>

msisdn,externalId,NAME,CODE
998901234500,demo-0001,Иван,123456
998901234501,,Пётр,654321
```

Смета для файла — `POST /api/admin/v1/send/estimate` с теми же query-параметрами и телом `text/csv`.

**Формат CSV.** Колонки по именам заголовка: адресная своя у каждого канала (`msisdn`, `email`,
`pushToken` + `pushPlatform`), служебные — `clientId` и `externalId`, **все остальные становятся
merge-переменными, имя колонки есть имя переменной, регистр значим** (`NAME` заполняет `{NAME}`, `name`
— нет). Потолок 50 000 строк. Строка без `externalId` получает идентификатор из
`sha256(файла) + номер строки`, поэтому тот же файл, загруженный дважды в окне дедупликации, уйдёт в
`DUPLICATE`, а не вторым сообщением каждому клиенту.

Рассылка из панели — **обычная рассылка**: видна в разделе «Рассылки», её можно приостановить и
остановить.

### 3.2. По REST (§8.2)

```http
POST /api/v1/messages

{
  "schemaVersion": "1.0",
  "streamId": "demo-app",
  "externalMessageId": "demo-0001",
  "trafficClass": "CRITICAL_OTP",
  "recipient": { "clientId": "CL-0001", "msisdn": "998901234500" },
  "channels": { "requested": ["SMS"] },
  "content": { "sms": { "text": "Ваш код: 123456" } },
  "timing": { "ttlSeconds": 300 },
  "dedupKey": "otp-CL-0001-20260811"
}
```

Ответ — `202`, заголовок `Location: /api/v1/messages/{messageId}`, тело `{messageId, status}`.

Обязательных полей три — `streamId`, `externalMessageId`, `recipient` — плюс правило «либо `content`,
либо `template`» (FR-1.2). Остальное, включая `schemaVersion`, опционально (если он задан, мажор должен
быть `1`). Ограничения: `externalMessageId` ≤ 64 символов, `dedupKey` ≤ 128, `content.sms.text` ≤ 1071,
MSISDN строго `^9989\d{8}$` — без `+`, без пробелов. Push-адреса здесь **массив**:
`"pushTokens": [{ "platform": "IOS", "token": "…" }]` — в отличие от админского `recipient`, где токен
одиночный. Неизвестные поля игнорируются; ошибки приходят как `application/problem+json` с машинным
кодом и указателем на поле.

Тот же запрос по шаблону — вместо `content`:

```json
"template": { "id": "DEMO_OTP", "locale": "RU", "variables": { "NAME": "Иван", "CODE": "123456" } }
```

**Локально токен не нужен** (`commhub.security.require-source-system-token` по умолчанию `false`, в логе
старта есть предупреждение). В контуре Банка — `true`: нужен bearer, а `streamId` проверяется против
claim'а токена (SEC-01), и чужой поток получит `403`.

Статус потом:

```http
GET /api/v1/messages/{messageId}
GET /api/v1/messages?streamId=demo-app&externalMessageId=demo-0001
```

У второй формы обязательны оба параметра.

### 3.3. Через Kafka (§8.1)

**Тело то же самое** — IK-03 разбирает один и тот же кодек для обоих транспортов. Отличается адресация:

| Топик | Класс трафика | Ключ партиционирования |
|---|---|---|
| `comm.inbound.critical.v1` | `CRITICAL_OTP` | получатель |
| `comm.inbound.transactional.v1` | `TRANSACTIONAL` | получатель |
| `comm.inbound.notification.v1` | `NOTIFICATION`, элементы рассылок | `batchId` |
| `comm.inbound.batch-control.v1` | заголовки и команды рассылок | `batchId` |

> **Класс трафика берётся из топика и перекрывает документ.** Это и есть изоляция TC-01: у каждого
> класса свой контейнер, свой пул потоков и своя consumer-группа, поэтому массовая рассылка не может
> переклеить себе метку и попасть в пул OTP. Поле `trafficClass` в теле при подаче через Kafka
> игнорируется.

Ключ нужен только для партиционирования — **listener его не читает**, входящих заголовков не требуется.
Локально удобнее всего опубликовать руками из Kafka UI на `http://localhost:8090`.

Готовые документы под каждый топик — в [`../kafka/`](../kafka/README.md): взять файл, вставить в
Kafka UI, ничего не сочиняя.

Рассылка: заголовок и команды идут в `comm.inbound.batch-control.v1`.

```json
{ "action": "CREATE",
  "batch": { "streamId": "demo-app", "channel": "SMS", "trafficClass": "NOTIFICATION",
             "template": { "id": "DEMO_OTP", "locale": "RU" }, "expectedTotal": 1000 },
  "actor": "crm" }
```

`action` ∈ `CREATE|START|PAUSE|RESUME|STOP`. Для `CREATE` обязателен блок `batch` с `streamId` и
`channel`; для всех остальных — верхнеуровневый `batchId`. `actor` и `reason` опциональны (без `actor`
действие записывается на систему, `reason` попадает в аудит). **Элементы рассылки идут не сюда**, а в
`comm.inbound.notification.v1` обычными документами IK-03 с `batchId` в конверте.

Нечитаемый документ уезжает в `comm.inbound.parse-error.v1` с заголовками `commhub-origin-topic` и
`commhub-failed-field`. Отказ конвейера — не то же самое: он сохраняется как статус и публикуется, а
listener коммитит offset.

## 4. Что произойдёт дальше

- Экран «Сообщения» → карточка: таймлайн `QUEUED → SENT_TO_PROVIDER → DELIVERED`. Карточка — буквально
  тот же документ, который система-источник получает по своему API; содержимого в ней нет и не будет
  (шифруется на хранении, DB-04). На моке `DELIVERED` приходит через 3 секунды.
- Kafka UI → `comm.outbound.status.v1`: те же переходы контрактом наружу.
- Все ветки конвейера проверяются одной загрузкой CSV с номерами на `00`, `01`, `02`, `03` и `04`
  (§2.6): доставка, недоставка, ретрай с failover, открытие breaker'а и попадание в suppression list —
  без единой настоящей SMS.

## 5. Боевой провайдер: чем отличается

**Меняется только шаг 2.1.** Канал, поток, шаблон и политики настраиваются ровно так же.

**Адаптер включается на деплое, а не в панели.** У каждого свой флаг (`PLAYMOBILE_ENABLED`,
`SMSGATE_ENABLED`, `SMTP_ENABLED`, `FCM_ENABLED`, `APNS_ENABLED`), и без него бинов в контексте нет —
значит, `GET /api/admin/v1/providers/adapters` не покажет тип, а отправка через профиль с этим типом
упадёт на `no adapter deployed`.

**Креды задаются деплоем, а не панелью** (SEC-04, ADR-0044): переменные окружения контура —
`PLAYMOBILE_USERNAME`, `PLAYMOBILE_PASSWORD`, `SMSGATE_KEY`, `FCM_SERVICE_ACCOUNT`, `APNS_PRIVATE_KEY`.
Многострочный ключ (service account FCM, `.p8` APNs) можно передать в base64 — распознаётся сам. Ни в
базе, ни в панели кредов нет вовсе, и Модуль никогда не ходит в Vault сам. Незаданная переменная — это
отказ отправки `NO_CREDENTIALS`, а не отправка без учётных данных.

**Что живёт где.** В yaml и окружении — только топология деплоя: base-url, таймауты, окна circuit
breaker'а. Настройки отправки (originator/sender, приоритеты, веса, TTL) и лимиты читаются из базы
(`provider.endpoint_config`, `provider.rate_limit_config`) и правятся из панели **без рестарта**
(AD-07, NF-07).

**Проверка — тестовая отправка** (поток, канал, необязательный провайдер, адрес, текст). **Это не
симуляция:** сообщение идёт по обычному конвейеру и реально доходит до абонента — применяются квоты
потока, фильтры канала и настоящие креды, именно поэтому она и проверяет конфигурацию (FR-7.4). В
бизнес-статистику не попадает: помечена `TEST`.

**Смена провайдера на живом контуре**: заведите второй профиль, поставьте его в `fallbackOrder` канала
**после** текущего, убедитесь по здоровью, что он выбираем, и поменяйте порядок. Канал и тип адаптера у
заведённого профиля не меняются — провайдер, сменивший канал или адаптер, это другой провайдер.

## 6. Разбор отказов

Маршрутизатор отказывает ровно в четырёх случаях, и текст отказа их различает:

| Текст | Что это значит | Что делать |
|---|---|---|
| `recipient has no usable address for the planned channels` | у получателя нет адреса под запланированный канал (например, нет `msisdn` для SMS) | проверить `recipient` и `channels.requested` |
| `channel SMS is not configured` | нет профиля канала | §2.2 |
| `channel SMS is MAINTENANCE` (или `DISABLED`) | профиль есть, но канал не `ACTIVE` | вернуть канал в `ACTIVE` |
| `no selectable provider for channel SMS` | пустой `fallbackOrder`; код в нём не резолвится; провайдер `DISABLED`/`MAINTENANCE`/health `DOWN`; политика назвала провайдера, которого нет в `fallbackOrder` | §2.1–2.2 |

Проверяются они в этом порядке, поэтому на чистом контуре первым приходит `channel … is not configured`.

Похоже, но **это не отказ маршрутизации**:

| Симптом | Причина |
|---|---|
| `no adapter deployed for provider X (mock-sms)` | маршрут найден, но `adapterType` профиля не совпал ни с одним развёрнутым адаптером. Регистрация тип не проверяет — §2.1 |
| отказ при публикации версии | автор и ревьюер совпали (FR-4.2) — §2.4 |
| в панели не выбирается язык шаблона | в этой локали нет **опубликованной** версии, только черновики |
| правка конфигурации не подействовала | кеш снапшота, до 30 с (NF-07) |
| приём отклонён на входе | поток `SUSPENDED`, исчерпана квота с `BLOCK_AND_ALERT`, сработал PAN-детектор |
| всё отложено, отправки нет | глобальный kill switch; окно тишины (`DEFER` придерживает до конца окна) |
| `400` на `/send/message` или `/send/batch` | нет `X-Commhub-Reason` — он обязателен на всём, что отправляет (§3.1) |
| `401` на `/api/admin/v1/**` | нет токена — открытого режима у панели нет (ADR-0037) |
| `403` на `/api/v1/messages` | `require-source-system-token=true`, а `streamId` не входит в claim токена (SEC-01) |

Порядок разбора: **dry-run** (§2.5) отвечает на вопрос «какой маршрут получит это сообщение» и
показывает причину отказа, ничего не отправляя; **тестовая отправка** (§5) проверяет уже провайдера и
креды. Сначала первое, потом второе.
