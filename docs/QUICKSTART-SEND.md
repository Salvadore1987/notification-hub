# От пустой базы до доставленной SMS

Сквозной сценарий: что завести в конфигурации, чтобы сообщение вообще нашло маршрут, и как потом подать
его тремя способами — из админ-панели, по REST и через Kafka.

Документ нужен потому, что **после первого старта конфигурация маршрутизации пуста**. Миграции заводят
только `kill_switch` и таблицу ролей; ни одного провайдера, канала и потока в базе нет, seed-скрипта в
репозитории тоже нет — и это осознанно (`docs/DEPLOYMENT.md` §5.4): маршрутизация контура не должна
приезжать из чужого дампа. Практическое следствие — первая же отправка на чистом контуре отвечает
`NO_ROUTE_AVAILABLE`, и по тексту отказа не всегда очевидно, какого из предусловий не хватает.

- Настройка через экраны панели, кнопка за кнопкой — `docs/ADMIN-GUIDE.md` (один раздел на экран).
- Развёртывание, переменные окружения и секреты — `docs/DEPLOYMENT.md`.
- Разбор инцидентов на работающем контуре — `docs/RUNBOOK.md`.

Здесь — только маршрут «с нуля до доставленной SMS» и то, чем он отличается на локальном стенде и в
контуре.

## 0. Что должно работать до начала

```bash
docker compose up -d              # PostgreSQL, Kafka, Keycloak, Kafka UI, WireMock, GreenMail
./gradlew :bootstrap:bootRun      # приложение на :8080, Flyway накатывается на старте
```

```bash
curl http://localhost:8080/actuator/health      # {"status":"UP", ...}
curl -i http://localhost:8080/api/admin/v1/dashboard   # 401 — панель за OIDC на любом контуре
```

`401` здесь — правильный ответ: админ-BFF требует токен всегда, конфигурации «открытый режим» не
существует (ADR-0037). Токен демо-администратора локального Keycloak:

```bash
TOKEN=$(curl -s -d grant_type=password -d client_id=commhub-admin \
  -d username=demo -d password=demo \
  http://localhost:8180/realms/commhub/protocol/openid-connect/token | jq -r .access_token)
```

Дальше в примерах — `-H "Authorization: Bearer $TOKEN"`. Панель поднимается отдельно
(`cd web && npm run dev`, `http://localhost:5173`, вход `demo/demo`); всё, что делается ниже curl'ом,
делается и мышью — соответствующий экран назван в каждом шаге.

Роли §10.1 заведены отдельными пользователями, пароль равен логину: `demo` (ADMIN), `operator`,
`template-manager`, `analyst`, `viewer`, `auditor`. Понадобятся минимум двое: публикацию шаблона
проводит **не тот**, кто его написал (FR-4.2).

## 1. Порядок настройки и почему он такой

```
провайдер ──► канал ──► поток ──► шаблон ──► [политика маршрутизации]
             (fallbackOrder
              ссылается на код
              провайдера)
```

Порядок не переставляется, и вот почему:

- **Провайдер первым.** `fallbackOrder` канала — это список кодов провайдеров, и код, который ещё не
  зарегистрирован, канал не примет.
- **Канал вторым, и с непустым `fallbackOrder`.** Провайдеры для маршрутизации берутся **только**
  оттуда (`FallbackChain.providerChain`). Канал с пустым порядком выглядит настроенным и при этом не
  маршрутизирует ничего — это самая частая ошибка первичной настройки.
- **Поток третьим.** Он не влияет на маршрут, но без него сообщение не примут: `streamId` обязателен в
  каждом документе.
- **Шаблон четвёртым** — и только если отправляете из панели: там поля текста нет вовсе (ADR-0038). Для
  REST и Kafka можно обойтись инлайновым `content`.
- **Политика маршрутизации не нужна.** С нулём политик маршрутизатор берёт канал из плана сообщения или
  дефолта потока, а провайдеров — из `fallbackOrder` канала. Политики заводят, когда трафик надо
  развести, а не чтобы «заработало».

Правки конфигурации применяются **без рестарта, но не мгновенно**: снапшот кешируется на
`commhub.config.cache.refresh-interval` (по умолчанию 10 с, потолок 30 с по NF-07). Если сразу после
правки ничего не изменилось — подождите полминуты, прежде чем править ещё раз.

## 2. Локальный стенд: настройка на фиктивном провайдере

На стенде отправлять по-настоящему нечем и не нужно: боевые креды локально недоступны и не должны быть
доступны. Вместо этого работает **фиктивный провайдер** (ADR-0041) — не HTTP-заглушка, а настоящий
адаптер с типами `mock-sms` / `mock-email` / `mock-push`. Он соблюдает контракт фазы 7 и умеет
воспроизвести ретрай, failover и открытие circuit breaker'а, а отчёт о доставке присылает отложенно —
то есть конвейер виден целиком, от `QUEUED` до `DELIVERED`.

Включён он только корневым `config/application.yml` (`commhub.provider.mock.enabled`, локально `true`),
в собранный образ бины не попадают вовсе. **Своего профиля он не заводит** — профиль создаётся руками,
ровно как для любого другого провайдера.

### 2.1. Профиль провайдера

Экран: «Каналы и провайдеры» → вкладка «Провайдеры» → «Зарегистрировать провайдера».

```bash
curl -X POST http://localhost:8080/api/admin/v1/providers/MOCK \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"channel":"SMS","adapterType":"mock-sms"}'
```

Обязательны три вещи: код в пути (`^[A-Z0-9][A-Z0-9_]{1,31}$` — ЗАГЛАВНЫМИ), `channel` и `adapterType`
(`^[a-z0-9][a-z0-9-]{1,31}$` — строчными). Всё остальное — вес (по умолчанию `10`), тариф, лимиты,
квота, ссылка на креды, `endpointConfig` — необязательно.

Профиль создаётся `enabled`, здоровье `UNKNOWN`. **`UNKNOWN` — это выбираемое состояние**: невыбираемым
провайдера делает только `DOWN` (плюс `DISABLED` и `MAINTENANCE`), поэтому свежий профиль маршрутизируется
сразу, ничего «прогревать» не нужно.

> **Тип адаптера в панели выбирается из списка, а не набирается** — список отдаёт `GET /providers/adapters`
> и это то, что развёрнуто именно на этом поде (ADR-0042). При этом **регистрация тип не проверяет**:
> профиль с несуществующим типом заведётся, маршрут найдётся, а отправка упадёт с
> `no adapter deployed for provider MOCK (mock-sms)`. Это не `NO_ROUTE_AVAILABLE` — см. §6.

### 2.2. Профиль канала

Экран: та же страница → вкладка «Каналы» → у строки `SMS` действие «Настроить».

```bash
curl -X PUT http://localhost:8080/api/admin/v1/channels/SMS \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"balancingStrategy":"PRIMARY_ONLY","fallbackOrder":["MOCK"]}'
```

Набор каналов фиксирован (`SMS`, `EMAIL`, `PUSH`), их не заводят и не удаляют — но *профиль* канала сам
собой не появляется: на новом контуре все три показаны как «не настроен», и `PUT` здесь работает как
upsert, то есть создаёт профиль. `balancingStrategy` обязателен, умолчания в базе нет.

**`fallbackOrder` надо заполнить сразу.** Порядок выбора и есть порядок переключения при отказе.

### 2.3. Поток

Экран: «Входящие потоки» → «Зарегистрировать поток».

```bash
curl -X POST http://localhost:8080/api/admin/v1/streams/demo-app \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"Демо-приложение","integrationType":"REST"}'
```

Идентификатор — `^[a-z0-9][a-z0-9._-]{1,63}$`, **строчными**, и после регистрации не меняется: системы-
источники указывают его в каждом сообщении. Обязательны `name` и `integrationType`.

> **`integrationType` ничего не ограничивает.** Значение описательное — ни один listener и ни один
> контроллер его не читает. Поток, заведённый как `REST`, принимает и из Kafka, и наоборот. Значений
> два: `KAFKA` и `REST`.

Здесь же — квоты (`BLOCK_AND_ALERT` отклоняет, `ALERT_ONLY` пропускает и сигнализирует), rate limit
(IR-02) и окно тишины. Ни один из блоков не обязателен; без квоты поток не ограничен.

### 2.4. Шаблон — только если отправляете из панели

Экран: «Шаблоны» → «Завести шаблон», затем в карточке «Новый черновик».

```bash
# карточка (direction — бизнес-направление Банка: МСБ, Чакана, …)
curl -X POST http://localhost:8080/api/admin/v1/templates/DEMO_OTP \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"channel":"SMS","direction":"Чакана","owner":"retail"}'

# черновик версии — PUT, а не POST: черновик перезаписывается, пока он черновик
curl -X PUT http://localhost:8080/api/admin/v1/templates/DEMO_OTP/versions \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"locale":"RU","text":"Здравствуйте, {NAME}! Ваш код: {CODE}"}'
```

В ответе — `version: 1`, `status: "DRAFT"`, разобранный список переменных (`["NAME","CODE"]`) и
`review.createdBy` с логином автора. Номер версии можно не указывать: без него заводится следующая.

Дальше — workflow `DRAFT → ON_REVIEW → PUBLISHED` (FR-4.1):

```bash
curl -X POST ".../templates/DEMO_OTP/versions/RU/1/state/ON_REVIEW" -H "Authorization: Bearer $TOKEN"
curl -X POST ".../templates/DEMO_OTP/versions/RU/1/state/PUBLISHED" -H "Authorization: Bearer $TOKEN2"
```

> **Публикацию проводит второй человек** (FR-4.2). Автор версии и тот, кто её публикует, обязаны
> различаться, и оба берутся из учётной записи, а не из полей формы. Обойти это через панель нельзя — и
> не нужно. Локально: черновик пишет `template-manager`, публикует `demo` (второй токен, `$TOKEN2`).
>
> Это самое частое место, где сценарий встаёт. Признак — «Опубликовать» заблокирована с подсказкой, а по
> API приходит отказ от use case'а.

Две вещи, которые путают:
- **Статус карточки и статус версии — разные словари.** Карточка бывает `ACTIVE`/`ARCHIVED`; новая уже
  `ACTIVE`, переводить её никуда не надо. Отправляемым шаблон делает **публикация версии**.
- **Публикация новой версии архивирует предыдущую в той же локали** — в локали всегда ровно одна
  отправляемая версия.

Переменные пишутся как `{NAME}`. Для REST/Kafka с инлайновым `content` этот шаг пропускается целиком.

### 2.5. Проверка до отправки

Экран: «Маршрутизация» → карточка «Проверка маршрута (dry-run)».

```bash
curl -X POST http://localhost:8080/api/admin/v1/routing/evaluate \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"streamId":"demo-app","channel":"SMS","recipient":{"msisdn":"998901234500"},"text":"проверка"}'
```

Dry-run **ничего не отправляет**: сообщение строится в памяти и прогоняется через настоящий
маршрутизатор по настоящей конфигурации. В ответе — канал, провайдер, порядок fallback, стратегия,
число сегментов и оценка стоимости; если маршрута нет — причина отказа (см. §6).

### 2.6. Поведение фиктивного провайдера

Задаётся **последними двумя символами адреса**, а не настройкой, — правило запоминается с одного раза:

| Суффикс | Что делает | Зачем |
|---|---|---|
| `…00` | принято, затем `DELIVERED` | обычный happy path |
| `…01` | принято, затем `UNDELIVERED` | отчёт о недоставке |
| `…02` | ответа нет (бросает) | ретрай и failover |
| `…03` | блокирующий отказ, код `102` | circuit breaker открывается сразу |
| `…04` | адрес непригоден, код `20` | попадание в suppression list |
| прочее | принято, затем `DELIVERED` | |

Отчёт о доставке приходит через `report-delay` (локально 3 с), поэтому `SENT_TO_PROVIDER` в первые
секунды — это норма, а не залипание.

## 3. Три способа отправки

Всё ниже работает против конфигурации из §2.

### 3.1. Из админ-панели

Экран `/send`, две вкладки: «Одно сообщение» и «Рассылка из файла». Поток, код шаблона и язык
выбираются списками; язык сужен до локалей, в которых **есть публикация**.

**Поля текста нет ни в одной вкладке** — содержимое берётся только из опубликованного шаблона
(ADR-0038), то есть из того, что уже прочитал второй человек.

Порядок жёсткий: **сначала смета, потом отправка**.

1. Заполнить форму (адрес и значения переменных — или перетащить CSV).
2. «Рассчитать смету» → число получателей, сегменты, выбранный провайдер, оценка стоимости, версия
   шаблона, незаполненные переменные и нечитаемые строки файла.
3. «Отправить». Панель спросит обоснование — оно обязательно и попадает в аудит (FR-7.3).

Кнопка отправки закрыта сметой: **любая правка формы сбрасывает смету**, а если маршрута нет — смета
покажет причину и подтвердить будет нельзя.

По API это выглядит так:

```bash
curl -X POST http://localhost:8080/api/admin/v1/send/estimate \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"streamId":"demo-app","templateCode":"DEMO_OTP","locale":"RU","channel":"SMS",
       "recipient":{"msisdn":"998901234500"},"variables":{"NAME":"Иван","CODE":"123456"}}'

curl -X POST http://localhost:8080/api/admin/v1/send/message \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H 'X-Commhub-Reason: %D0%BF%D1%80%D0%BE%D0%B2%D0%B5%D1%80%D0%BA%D0%B0' \
  -d '{"streamId":"demo-app","templateCode":"DEMO_OTP","locale":"RU","channel":"SMS",
       "recipient":{"msisdn":"998901234500"},"variables":{"NAME":"Иван","CODE":"123456"}}'
```

`X-Commhub-Reason` обязателен и **передаётся percent-encoded UTF-8**: значение HTTP-заголовка — байтовая
строка, и кириллица в нём иначе не проходит.

**Формат CSV.** Колонки по именам заголовка. Адресная — своя у каждого канала (`msisdn`, `email`,
`pushToken` + `pushPlatform`); служебные — `clientId` и `externalId`. **Все остальные колонки становятся
merge-переменными, имя колонки есть имя переменной, регистр значим**: колонка `NAME` заполняет `{NAME}`,
а `name` — не заполняет. Потолок — 50 000 строк.

```
msisdn,externalId,NAME,CODE
998901234500,demo-0001,Иван,123456
998901234501,,Пётр,654321
```

Строка без `externalId` получает идентификатор из `sha256(файла) + номер строки`, поэтому тот же файл,
загруженный дважды в окне дедупликации, уйдёт в `DUPLICATE`, а не вторым сообщением каждому клиенту.

Рассылка из панели — **обычная рассылка**: её видно в разделе «Рассылки», можно приостановить и
остановить.

### 3.2. По REST (§8.2)

```bash
curl -i -X POST http://localhost:8080/api/v1/messages \
  -H 'Content-Type: application/json' -d '{
  "schemaVersion": "1.0",
  "streamId": "demo-app",
  "externalMessageId": "demo-0001",
  "trafficClass": "CRITICAL_OTP",
  "recipient": { "clientId": "CL-0001", "msisdn": "998901234500" },
  "channels": { "requested": ["SMS"] },
  "content": { "sms": { "text": "Ваш код: 123456" } },
  "timing": { "ttlSeconds": 300 },
  "dedupKey": "otp-CL-0001-20260811"
}'
```

Ответ — `202` с `Location: /api/v1/messages/{messageId}` и телом `{messageId, status}`.

**Локально токен не нужен**: `commhub.security.require-source-system-token` по умолчанию `false`, и в
логе старта об этом есть предупреждение. В контуре Банка — `true`, и тогда нужен bearer, а `streamId`
проверяется против claim'а токена (SEC-01): чужой поток получит `403`.

Обязательных полей три — `streamId`, `externalMessageId`, `recipient` — плюс правило «либо `content`,
либо `template`» (FR-1.2). MSISDN строго `^9989\d{8}$`: без `+`, без пробелов. Неизвестные поля
игнорируются; ошибки приходят как `application/problem+json` с машинным кодом и указателем на поле.

Тот же запрос по шаблону — вместо `content`:

```json
"template": { "id": "DEMO_OTP", "locale": "RU", "variables": { "NAME": "Иван", "CODE": "123456" } }
```

Статус потом: `GET /api/v1/messages/{messageId}` или
`GET /api/v1/messages?streamId=demo-app&externalMessageId=demo-0001`.

### 3.3. Через Kafka (§8.1)

**Тело то же самое** — IK-03 разбирает один и тот же кодек для обоих транспортов. Отличается только
адресация:

| Топик | Класс трафика | Ключ партиционирования |
|---|---|---|
| `comm.inbound.critical.v1` | `CRITICAL_OTP` | получатель |
| `comm.inbound.transactional.v1` | `TRANSACTIONAL` | получатель |
| `comm.inbound.notification.v1` | `NOTIFICATION`, элементы рассылок | `batchId` |
| `comm.inbound.batch-control.v1` | заголовки и команды рассылок | `batchId` |

> **Класс трафика берётся из топика и перекрывает документ.** Это и есть изоляция TC-01: у каждого класса
> свой контейнер, свой пул потоков и своя consumer-группа, поэтому массовая рассылка не может
> переклеить себе метку и попасть в пул OTP. Поле `trafficClass` в теле при подаче через Kafka
> игнорируется.

Ключ нужен только для партиционирования — **listener его не читает**, и никаких входящих заголовков не
требуется. Локально удобнее всего опубликовать руками из Kafka UI на `http://localhost:8090`.

Рассылка: заголовок и команды идут в `comm.inbound.batch-control.v1`

```json
{ "action": "CREATE",
  "batch": { "streamId": "demo-app", "channel": "SMS", "trafficClass": "NOTIFICATION",
             "template": { "id": "DEMO_OTP", "locale": "RU" }, "expectedTotal": 1000 },
  "actor": "crm" }
```

(`action` ∈ `CREATE|START|PAUSE|RESUME|STOP`; для всех, кроме `CREATE`, нужен `batchId`), а **элементы —
в `comm.inbound.notification.v1`** обычными документами IK-03 с `batchId` в конверте.

Нечитаемый документ уезжает в `comm.inbound.parse-error.v1` с заголовками `commhub-origin-topic` и
`commhub-failed-field`. Отказ конвейера — не то же самое: он сохраняется как статус и публикуется, а
listener коммитит offset.

## 4. Что должно произойти дальше

- Экран «Сообщения» → карточка: таймлайн `QUEUED → SENT_TO_PROVIDER → DELIVERED`. Карточка — буквально
  тот же документ, который система-источник получает по своему API; содержимого в ней нет и не будет
  (шифруется на хранении, DB-04).
- Kafka UI → `comm.outbound.status.v1`: те же переходы контрактом наружу.
- На моке `DELIVERED` приходит через 3 секунды после `SENT_TO_PROVIDER`.

Проверить сразу все ветки конвейера можно одной загрузкой CSV с номерами, оканчивающимися на `00`, `01`,
`02`, `03` и `04` (§2.6): получатся доставка, недоставка, ретрай с failover, открытие breaker'а и
попадание в suppression list — без единой настоящей SMS.

## 5. Боевой провайдер: чем отличается

**Меняется только шаг 2.1.** Канал, поток, шаблон и политики настраиваются ровно так же.

**Адаптер включается на деплое, а не в панели.** У каждого свой флаг (`PLAYMOBILE_ENABLED`,
`SMSGATE_ENABLED`, `SMTP_ENABLED`, `FCM_ENABLED`, `APNS_ENABLED`), и без него бинов в контексте нет —
а значит, `GET /providers/adapters` не покажет тип, и отправка через профиль с этим типом упадёт на
`no adapter deployed`.

**Креды — это ссылки, а не значения** (SEC-04, ADR-0036). `env:ИМЯ` — переменная окружения контура,
`prop:ключ` — Spring-property; модификатор `base64:` для многострочного секрета (service account FCM,
`.p8` APNs). Ни в базе, ни в панели самого секрета нет, и Модуль никогда не ходит в Vault сам.

```bash
export PLAYMOBILE_ENABLED=true
export PLAYMOBILE_USERNAME_REF=env:PLAYMOBILE_USER
export PLAYMOBILE_PASSWORD_REF=env:PLAYMOBILE_PASSWORD
```

**Что живёт где.** В yaml и окружении — только топология деплоя: base-url, таймауты, окна circuit
breaker'а. Настройки отправки (originator/sender, приоритеты, веса, TTL) и лимиты читаются из базы
(`provider.endpoint_config`, `provider.rate_limit_config`) и правятся из панели **без рестарта**
(AD-07, NF-07).

**Проверка — «Тестовая отправка»** на вкладке провайдеров: поток, канал, необязательный провайдер
(закрепляет отправку за одним, исключая остальные), адрес, текст.

> **Это не симуляция.** Сообщение идёт по обычному конвейеру и реально доходит до абонента: применяются
> квоты потока, фильтры канала и настоящие креды — именно поэтому она и проверяет конфигурацию (FR-7.4).
> В бизнес-статистику не попадает: помечена `TEST` и включается флажком «Показывать тестовые».

`mock-sms` на боевом контуре не появится: свойство выключено по умолчанию, а в образе бинов мока нет
вовсе. Но профиль с таким типом завести можно — он просто не отправит ничего.

Смена провайдера на живом контуре: заведите второй профиль, поставьте его в `fallbackOrder` канала
**после** текущего, убедитесь по «Здоровью», что он выбираем, и поменяйте порядок. Канал и тип адаптера
у заведённого профиля не меняются — провайдер, сменивший канал или адаптер, это другой провайдер.

## 6. Разбор отказов

Маршрутизатор отказывает ровно в четырёх случаях, и текст отказа их различает:

| Текст | Что это значит | Что делать |
|---|---|---|
| `channel SMS is not configured` | нет профиля канала | §2.2 |
| `channel SMS is MAINTENANCE` | профиль есть, но канал не `ACTIVE` | вернуть канал в `ACTIVE` |
| `no selectable provider for channel SMS` | пустой `fallbackOrder`; код в нём не резолвится; провайдер `DISABLED`/`MAINTENANCE`/health `DOWN`; политика назвала провайдера, которого нет в `fallbackOrder` | §2.1–2.2 |
| `recipient has no usable address for the planned channels` | у получателя нет адреса под запланированный канал (например, нет `msisdn` для SMS) | проверить `recipient` и `channels.requested` |

Похоже, но **это не отказ маршрутизации**:

| Симптом | Причина |
|---|---|
| `no adapter deployed for provider X (mock-sms)` | маршрут найден, но `adapterType` профиля не совпал ни с одним развёрнутым адаптером. Регистрация тип не проверяет — §2.1 |
| отказ при публикации версии | автор и ревьюер совпали (FR-4.2) — §2.4 |
| в панели не выбирается язык шаблона | в этой локали нет **опубликованной** версии, только черновики |
| правка конфигурации не подействовала | кеш снапшота, до 30 с (NF-07) |
| приём отклонён на входе | поток `SUSPENDED`, исчерпана квота с `BLOCK_AND_ALERT`, сработал PAN-детектор |
| всё отложено, отправки нет | глобальный kill switch; окно тишины (`DEFER` придерживает до конца окна) |
| `401` на `/api/admin/v1/**` | нет токена — открытого режима у панели нет (ADR-0037) |
| `403` на `/api/v1/messages` | `require-source-system-token=true`, а `streamId` не входит в claim токена (SEC-01) |

Быстрый порядок разбора: **dry-run** (§2.5) отвечает на вопрос «какой маршрут получит это сообщение» и
показывает причину отказа, не отправляя ничего; **тестовая отправка** проверяет уже провайдера и креды.
Сначала первое, потом второе.
