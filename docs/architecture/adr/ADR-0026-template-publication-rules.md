# ADR-0026. Правила шаблонов живут в домене: одна отправляемая версия на локаль, maker/checker, архивация вместо удаления

| | |
|---|---|
| **Статус** | Принято · реализовано |
| **Дата** | 09.08.2026 |
| **Требования SRS** | FR-4.1…FR-4.6, §7.4, §11.2 |
| **Связанные решения** | [ADR-0015](ADR-0015-rejection-is-a-verdict.md), [ADR-0007](ADR-0007-configuration-in-postgres.md) |

## Контекст

Шаблон — это текст, который уходит клиентам Банка от имени Банка. Ошибка в нём стоит дороже большинства
технических дефектов, а исправлять её приходится задним числом по уже отправленным сообщениям. Поэтому правила
публикации должны быть невозможно нарушить, а не «проверяться в сервисе».

## Решение

Слой шаблонов повторяет форму фазы 8: `ManageTemplates` группирует CRUD агрегата, `GetTemplates` — сторона чтения
(карточка, каталог без тел, предпросмотр), отказы — `ConfigurationConflictException` (409) и `NotFoundException`
(404), а не вердикты (ADR-0015).

**Два правила стоят в домене и не должны переписываться выше:**

1. **У локали ровно одна отправляемая версия** — `Template.publishVersion`: публикация v2 архивирует v1.
   Публикация выполняется **первой**, поэтому отклонение по maker/checker оставляет предыдущую версию
   опубликованной, а не обнуляет канал.
2. **Переписывать можно только `DRAFT`** — `TemplateVersion.updateBody`. Версия на ревью — это то, что сейчас
   смотрит проверяющий, а опубликованная — то, из чего рендерились уже отправленные сообщения.

**Автор и проверяющий берутся из `Actor`, а не из поля команды** (FR-4.2): поле команды означает, что автор
может назначить проверяющим себя. Безымянный актор — сам Модуль — не может ни создать версию, ни опубликовать её.

**Удаление шаблона — это архивация** (`TemplateCatalogStatus`, `template.status`): его код стоит в истории каждого
сообщения, отрендеренного из него. Архивная карточка сохраняет версии и перестаёт быть отправляемой
(`Template.isSendable`, проверяется `TemplateApplier`).

**Предпросмотр в панели намеренно нестрогий и не проверяет статус**: он существует, чтобы им пользовались на
черновике. Незаполненное поле остаётся видимым как `{NAME}` и попадает в список недостающих. Путь отправки при
этом строгий: отсутствие переменной — отклонение `TEMPLATE_VARIABLE_MISSING` (FR-4.3).

**Стоимость (FR-4.4) считается настоящим `SegmentCalculator` по настоящим тарифам** провайдеров и котируется по
каждому провайдеру с флагом `selectable`. Второй реализации подсчёта сегментов в системе нет.

**Импорт (FR-4.6) идёт через агрегат** (`ImportTemplates` + `:adapter:in:importer`): колонки CSV по именам,
идемпотентность по формулировке, плохие строки попадают в отчёт и не останавливают импорт, а публикация требует
`approver`, отличного от `author`. Выключен по умолчанию (`commhub.import.templates.enabled`).

## Альтернативы

- **Проверять правила в сервисе.** Второй путь записи (импорт, миграция, скрипт) обходит их молча.
- **Физическое удаление шаблона.** История отправленных сообщений теряет опору: код есть, шаблона нет.
- **Строгий предпросмотр.** Делает функцию бесполезной ровно в том сценарии, для которого она создавалась.
- **Разрешить автору публиковать «в порядке исключения».** Исключение становится правилом за один инцидент.

## Последствия

**Положительные.** Отправить можно только опубликованную версию, и она у локали одна — вопрос «каким текстом
ушло» имеет однозначный ответ. Разделение ролей нельзя обойти через API.

**Цена.** Публикация требует второго человека, и в маленькой команде это ощущается как трение. Это и есть
требование FR-4.2. Архивация означает, что каталог растёт и требует фильтра по статусу в UI.

## Как нарушение будет замечено

Unit-тесты домена покрывают обе инварианты, включая порядок «публикация перед проверкой прав». Тесты импорта
проверяют, что импорт не может опубликовать шаблон с одним и тем же автором и проверяющим.
