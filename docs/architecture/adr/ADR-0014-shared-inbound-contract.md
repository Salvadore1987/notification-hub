# ADR-0014. Один разбор контракта IK-03 на оба транспорта

| | |
|---|---|
| **Статус** | Принято · реализовано |
| **Дата** | 08.08.2026 |
| **Требования SRS** | IK-03, IK-04, IR-01, FR-1.4, §8.2 |
| **Связанные решения** | [ADR-0005](ADR-0005-traffic-class-isolation.md), [ADR-0015](ADR-0015-rejection-is-a-verdict.md), [ADR-0016](ADR-0016-handwritten-openapi.md) |

## Контекст

§8.2 говорит прямо: тело REST-запроса **есть** сообщение IK-03. Если разбор написать дважды — в контроллере и в
консьюмере — то через полгода REST будет принимать то, что отвергает Kafka, и наоборот. Расхождение обнаружится
в проде, у источника, который переключился с одного транспорта на другой.

## Решение

Разбор живёт в одном модуле — `:adapter:in:contract`:

- записи полезной нагрузки в `dto`, MapStruct-маппер `InboundPayloadMapper`,
  `InboundMessageCodec` / `InboundBatchCodec` поверх собственного `InboundJson`;
- **корень IK-03 читается поле за полем**, а не биндится целиком: тринадцать полей превышают предел в 8
  компонентов record (Checkstyle `ParameterNumber`). Это входное зеркало `StatusEventCodec`. Вложенные блоки
  (`recipient`, `channels`, `content`, `template`, `timing`) биндятся Jackson-ом обычным образом;
- **bean validation не используется**: правила принадлежат доменным value objects, а кодек добавляет только то,
  чего они увидеть не могут (наличие обязательных блоков, согласованность канала и контента). Нарушение —
  `InboundContractException` с указателем на поле;
- **указатель на поле рендерят оба транспорта**: REST → `problem+json` (IR-01), Kafka → заголовки события
  `comm.inbound.parse-error.v1` (IK-04).

Отдельное правило, вытекающее из ADR-0005: **класс трафика берётся из топика и переопределяет документ**.

## Альтернативы

- **Свой разбор в каждом адаптере.** Гарантированное расхождение; уже описано выше.
- **Общий модуль DTO без кодека.** Половина проблемы: типы общие, а правила «что считать корректным» — снова
  в двух местах.
- **Bean validation аннотациями на DTO.** Дублирует правила, которые уже выражены в value objects домена, и
  разводит их: аннотация говорит `@Pattern`, а `Msisdn` — своё, и однажды они разойдутся.

## Последствия

**Положительные.** Источник переключается между REST и Kafka без сюрпризов. Сообщение об ошибке одинаково точно
в обоих транспортах — с указанием конкретного поля. Правило проверки существует ровно в одном месте: либо в
value object, либо в кодеке.

**Цена.** Ручное чтение корня — это цикл по полям, который нужно поддерживать при расширении контракта; за это
платит ограничение в 8 компонентов record, принятое по всему проекту. Модуль `contract` становится общей
зависимостью rest и kafka — при его правке пересобираются оба, и это правильно.

## Как нарушение будет замечено

Контрактные тесты гоняют один и тот же набор документов через оба транспорта и сверяют вердикты. Появление
второго парсера видно как второй `…Codec` вне модуля `contract`.
