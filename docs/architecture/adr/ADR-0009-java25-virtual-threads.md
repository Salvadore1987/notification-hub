# ADR-0009. Java 25 и виртуальные потоки вместо реактивного стека

| | |
|---|---|
| **Статус** | Принято · реализовано |
| **Дата** | 06.08.2026 |
| **Требования SRS** | AR-07, NF-01, NF-05, PU-02, §3.1 |
| **Связанные решения** | [ADR-0020](ADR-0020-provider-ack-contract.md), [ADR-0024](ADR-0024-email-smtp-decisions.md), [ADR-0025](ADR-0025-push-fanout-and-terminal-status.md) |

## Контекст

Работа Модуля — это I/O: HTTP к провайдерам, SMTP, JDBC, Kafka. Push по модели FCM HTTP v1 отправляется по одному
сообщению на запрос, то есть массовая доставка достигается исключительно параллелизмом (расчётно ≥ 500 push/с на
инстанс). Классический пул платформенных потоков на таких объёмах упирается в память, а реактивный стек —
традиционный ответ на эту проблему — стоит переписывания всего кода в цепочки операторов.

## Решение

Java 25 (LTS) с виртуальными потоками. Блокирующий код остаётся блокирующим:

- HTTP к провайдерам — JDK `HttpClient` на виртуальных потоках (`ProviderRestClients`), таймауты обязательны.
- Fan-out push по устройствам получателя — параллельно на виртуальных потоках; получатель с одним устройством
  остаётся на вызывающем потоке (`PushFanOut`).
- Реактивный стек не используется нигде.

Из языка берётся то, что даёт модель: records для команд, DTO и value objects; sealed-иерархии для контента,
статусов и полезной нагрузки outbox; pattern matching в разборе ответов провайдеров.

## Альтернативы

- **Spring WebFlux / Project Reactor.** Решает ту же задачу и требует реактивных драйверов везде — включая JDBC
  (R2DBC) и почту, где реактивного клиента просто нет. Стек-трейсы и отладка становятся заметно дороже, а
  выигрыш на нашей нагрузке (пик ~10 SMS/с, push — параллелизмом) не окупает этого.
- **Пул платформенных потоков побольше.** Работает до определённого масштаба; на десятках тысяч одновременных
  вызовов push стоимость стека на поток становится решающей.
- **Java 21.** Виртуальные потоки уже есть, но проект целится в JDK 25 LTS по §3.1, и часть языковых удобств
  (в т. ч. в разборе) там богаче.

## Последствия

**Положительные.** Код читается как последовательный: вызов провайдера — это вызов, а не цепочка. Стек-трейс
показывает путь. Тесты пишутся обычными assert-ами, а не `StepVerifier`.

**Цена и грабли.** Виртуальные потоки дёшевы настолько, что это само становится риском: «дать релею десять тысяч
соединений» технически тривиально, а релей, которому дали десять тысяч соединений, перестаёт быть релеем.
Поэтому лимиты параллелизма проставлены явно и по-разному: пул SMTP-соединений **и есть** предел канала
(ADR-0024), у HTTP-провайдеров предел задаёт троттлинг. Второй известный риск — `synchronized` вокруг блокирующего
вызова прикалывает виртуальный поток к носителю; в коде адаптеров таких блоков нет.

Toolchain: Gradle 9.7 скачивает JDK 25 через foojay, если его нет локально, — сборка не зависит от того, что
установлено у разработчика.

## Как нарушение будет замечено

Появление реактивных типов в сигнатурах ловится на ревью и противоречит соглашениям слоя (`LayerConventionsTest`
держит форму use case-ов: команда на входе, результат на выходе). Нагрузочные сценарии `load/k6/` показывают,
упирается ли инстанс в потоки.
