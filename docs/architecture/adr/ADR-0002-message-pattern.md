# ADR-0002. Мультиканальность через паттерн Message и единый pipeline

| | |
|---|---|
| **Статус** | Принято · реализовано |
| **Дата** | 06.08.2026 |
| **Требования SRS** | AD-02, MP-01…MP-06, AR-05 |
| **Связанные решения** | [ADR-0001](ADR-0001-hexagonal-architecture.md), [ADR-0006](ADR-0006-canonical-status-model.md), [ADR-0025](ADR-0025-push-fanout-and-terminal-status.md) |

## Контекст

Каналов три сейчас и до девяти в перспективе. Соблазн — сделать «сервис SMS», «сервис Email», «сервис Push»:
каждый со своим приёмом, своей дедупликацией, своими фильтрами и своей статусной моделью. Через год это три
разные дедупликации с тремя разными окнами и три несовпадающих ответа на вопрос «что значит доставлено».

## Решение

Одно каноническое сообщение и один pipeline на все каналы.

- **Конверт канало-независим** (`MessageEnvelope`): идентификация, поток, класс трафика, приоритет, получатель,
  timing, ключ дедупликации, correlation id.
- **Контент — sealed-иерархия по каналам** (`SmsContent`, `EmailContent`, `PushContent`). Одно логическое
  уведомление несёт контент **для нескольких каналов сразу**, поэтому сообщение хранит `MessageContents` —
  контент на канал, а не единственный `MessageContent` (MP-02).
- **Pipeline один и стоит в `application/service/pipeline`**: дедупликация → шаблон → валидация → маршрутизация →
  фильтры → квоты. Точка входа одна — `MessagePipeline`, поэтому единичное сообщение, элемент батча и повтор из DLQ
  проходят один и тот же путь.
- **`Router` не знает провайдеров** (MP-05): он выбирает ссылку на провайдера по конфигурации маршрутизации,
  а прикладной слой резолвит адаптер через канальный порт.

Канальная специфика допускается ровно в двух местах: в специализации контента и в адаптере провайдера.

## Альтернативы

- **Общий интерфейс без общего конверта** («каждый канал сам по себе, договоримся об интерфейсе отправки»).
  Не решает главного: дедупликация, квоты, quiet hours и статусы всё равно нужны каждому каналу, и будут написаны
  трижды.
- **Один универсальный `MessageContent` с необязательными полями всех каналов.** Компилятор перестаёт помогать:
  «письмо без темы» и «push без токена» становятся runtime-проверками вместо невозможных состояний.

## Последствия

**Положительные.** Добавление канала — это специализация контента, канальный порт, адаптеры и строка конфигурации;
ядро pipeline переиспользуется (AR-05). Все каналы автоматически получают дедупликацию, квоты, фильтры,
трассировку и одинаковый набор статусов.

**Цена.** Есть места, где канал приходится различать явно, и это нормально: push — единственный канал, где у
получателя несколько адресов, и fan-out по устройствам живёт **над** портом, чтобы сага по-прежнему видела один
вызов и один ответ (см. ADR-0025). Sealed-иерархия означает, что новый канал требует правки в местах разбора
контента — но компилятор их перечислит сам, и это лучший из возможных способов узнать список.

## Как нарушение будет замечено

Отдельный «путь для канала» в обход `MessagePipeline` виден на ревью как второй вызов дедупликации или квот.
`LayerConventionsTest` держит форму слоя; sealed-иерархия делает пропущенный канал ошибкой компиляции в `switch`.
