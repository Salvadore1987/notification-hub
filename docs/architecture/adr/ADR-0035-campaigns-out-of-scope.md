# ADR-0035. Кампании без списка получателей вне объёма; в ядре остаётся только порт

| | |
|---|---|
| **Статус** | Принято · вне объёма (решение Банка от 06.08.2026, вернуться перед фазой расширений) |
| **Дата** | 06.08.2026 |
| **Требования SRS** | FR-8.11, §1.3, §18.5, открытый вопрос № 11 |
| **Связанные решения** | [ADR-0001](ADR-0001-hexagonal-architecture.md), [ADR-0002](ADR-0002-message-pattern.md) |

## Контекст

Требование-кандидат: запускать массовую рассылку одной командой (`templateId` плюс параметры), не передавая
Модулю список контактов — аудиторию Модуль определяет сам. Оно прямо противоречит ключевому ограничению ТЗ
(§1.3): формирование аудитории — зона ответственности систем-источников, а Модуль является транспортным и
оркестрирующим слоем. Реализация потребовала бы правки ТЗ и согласования с ИБ (Модуль начал бы хранить
контактные данные клиентов).

В §18.5 проработаны четыре варианта: A — топики провайдера (FCM Topics), B — собственный реестр получателей,
C — внешний сервис аудиторий (pull по `audienceRef`), D — гибрид через порт-резолвер.

## Решение

**В текущий объём не входит** (решение Банка от 06.08.2026). Массовые рассылки выполняются штатным механизмом
батчей (FR-1.6, PU-10) со списком получателей от системы-источника — с прогрессом, статистикой, фильтрами
compliance и стоимостью, то есть со всем тем, чего вариант A как раз не даёт.

**Архитектурный задел — ровно один и минимальный**: в ядре объявлен выходной порт `AudienceResolverPort` без
реализаций, и его никто не внедряет. Это сделано затем, чтобы последующее включение **любого** из вариантов
§18.5 добавляло адаптер, а не переписывало pipeline.

`ApplicationContextIT` перечисляет порты без реализации явно, поэтому «пустой» порт не является забытым кодом —
он является задокументированным состоянием, за которым следит тест.

## Альтернативы

- **Реализовать вариант A (FCM Topics) как самый дешёвый.** Даёт мгновенный охват и не даёт ничего из
  требуемого Модулю: ни статистики по получателю, ни suppression, ни quiet hours, ни аудита; работает только для
  push.
- **Реализовать вариант B (собственный реестр).** Самый полный по возможностям и означает, что Модуль начинает
  хранить контактные данные клиентов — правка ТЗ, согласование с ИБ, конвейер синхронизации и ответственность за
  актуальность.
- **Реализовать вариант C (внешний сервис аудиторий).** Сохраняет принцип ТЗ и требует, чтобы такой сервис
  сначала появился на стороне Банка.
- **Не оставлять даже порта.** Экономит один интерфейс и означает, что включение любого варианта будет правкой
  саги, а не добавлением адаптера.

## Последствия

**Положительные.** Ограничение §1.3 не нарушено, объём MVP не размыт, персональные данные клиентов в Модуль не
переезжают. Дверь оставлена открытой ценой одного интерфейса.

**Цена.** Источники обязаны передавать списки получателей — для массовых рассылок это заметный объём в Kafka.
Он покрыт механизмом батчей и учтён в оценке нагрузки (§12.2).

## Как пересмотреть

Открытый вопрос № 11 SRS: выбор варианта из §18.5 перед фазой расширений. Пересмотр оформляется новым ADR,
который выбирает вариант и описывает адаптер к `AudienceResolverPort`; этот ADR получает статус «заменён».
