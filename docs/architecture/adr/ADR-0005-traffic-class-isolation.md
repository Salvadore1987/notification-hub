# ADR-0005. Изоляция классов трафика строится из топиков, а не из приоритетов в очереди

| | |
|---|---|
| **Статус** | Принято · реализовано |
| **Дата** | 06.08.2026 |
| **Требования SRS** | AD-05, TC-01, TC-02, IK-01, NF-01, NF-04 |
| **Связанные решения** | [ADR-0014](ADR-0014-shared-inbound-contract.md), [ADR-0029](ADR-0029-kill-switch-polarity.md) |

## Контекст

Профиль нагрузки Банка: массовое взыскание до 1,8 млн SMS в месяц, маркетинг 1–1,7 млн, транзакционные балансовые
свыше 4 млн — и на этом фоне OTP с SLA p99 ≤ 5 с от приёма до передачи провайдеру. Батч на 500 тысяч сообщений
не имеет права сдвинуть OTP ни на секунду.

## Решение

Изоляция делается инфраструктурой, а не вежливостью планировщика:

- **Отдельный топик на класс трафика**: `comm.inbound.critical.v1`, `.transactional.v1`, `.notification.v1`
  (+ `.batch-control.v1` для команд батчей).
- **Отдельные контейнер-фактори и пул потоков на класс** в `KafkaConsumerConfig`: массовый класс не занимает
  потоки критического физически.
- **Отдельные бюджеты лимитов** на класс у провайдера и на поток.
- **Класс трафика берётся из топика и переопределяет документ.** Поле `trafficClass` в теле остаётся, но
  решающим является топик, в который источник положил сообщение (уточнение к TC-02).

Для REST класс приходит из документа и из настроек потока: там изоляция достигается лимитами на поток и
приоритетом провайдера (`CRITICAL_OTP → realtime/high`).

## Альтернативы

- **Один топик с полем приоритета.** Не изолирует ничего: миллион записей класса `NOTIFICATION` стоит в тех же
  партициях перед OTP, и никакой сортировкой это не лечится — Kafka не приоритетная очередь.
- **Отдельный deployment для OTP** (открытый вопрос № 7 SRS). Даёт изоляцию и на уровне процессов, но удваивает
  эксплуатацию и не отменяет необходимости раздельных топиков. Решение оставлено за архкомитетом; текущая
  архитектура его не блокирует — топики и пулы уже разделены, останется развести поды.
- **Приоритетные пулы внутри одного консьюмера.** Один медленный вызов провайдера в массовом классе всё равно
  занимает поток, общий с OTP.

## Последствия

**Положительные.** Изоляция не зависит от честности источника в поле документа: она следует из того, в какой
топик у источника есть право писать (ACL). Нагрузочный сценарий TC-01 проверяет именно то, что заявлено.

**Цена.** Источник обязан выбрать топик, а не просто поле, — это заметно в интеграции и требует объяснения в
онбординге потоков. Число топиков растёт с числом классов.

## Как нарушение будет замечено

`load/k6/tc01-otp-isolation.js` — батч параллельно с потоком OTP, метрика `accept-to-provider` по классу
`CRITICAL_OTP`. Правило алерта на нарушение SLA OTP ссылается на раздел runbook. Интеграционные тесты проверяют,
что класс приходит из топика: сообщение с «неправильным» полем в теле обрабатывается по топику.
