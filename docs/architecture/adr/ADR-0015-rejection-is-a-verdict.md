# ADR-0015. Отклонение сообщения — это вердикт, а не исключение

| | |
|---|---|
| **Статус** | Принято · реализовано |
| **Дата** | 08.08.2026 |
| **Требования SRS** | IR-01, FR-1.4, FR-1.5, FR-5.1, IK-04 |
| **Связанные решения** | [ADR-0014](ADR-0014-shared-inbound-contract.md), [ADR-0026](ADR-0026-template-publication-rules.md) |

## Контекст

Отклонение в Модуле — это норма, а не сбой: дубликат, номер в suppression, часы тишины, исчерпанная квота,
незаполненная переменная шаблона, неопубликованный шаблон. На потоке в миллионы сообщений такие исходы идут
постоянно. Исключение как способ их выразить означает stack trace на каждое штатное событие, «управление потоком
через throw» и — в Kafka — падение листенера там, где нужно спокойно закоммитить offset.

## Решение

**Отклонение возвращается как результат.** Use case отвечает вердиктом (`PipelineVerdict`, `FilterVerdict`),
который несёт канонический `RejectionReason` (IR-01). Исключений бизнес-уровня в pipeline нет; `NotFoundException`
— единственное исключение, близкое к бизнесу.

Как вердикт выглядит для каждого транспорта:

- **REST** — `problem+json` по RFC 9457 с машиночитаемым кодом (`rest/problem/ProblemType`).
- **Kafka** — листенер **логирует вердикт и коммитит**. Отклонение не является ошибкой обработки: пересчитывать
  его повторной доставкой бессмысленно, результат будет тот же.
- **Статус сообщения** — `REJECTED` или `DUPLICATE` с причиной, и он уезжает источнику через
  `comm.outbound.status.v1` как обычный статус.

Advice-классы живут по одному на задачу в `rest/handlers` (и `callback/handlers` для 403), а
`UnexpectedFailureHandler` обязан оставаться последним по порядку — иначе он перехватит то, что должен был
обработать специализированный.

**Одно намеренное исключение из правила.** Административные операции (`Manage…`) отвечают исключениями —
`ConfigurationConflictException` (409) и `NotFoundException` (404). Противоречивая правка конфигурации — это
ошибка оператора в интерактивной сессии, а не трафик, который системам Банка нужно уметь обрабатывать. IR-01
описывает pipeline, а не панель.

## Альтернативы

- **Исключения на все отклонения.** Единообразно и дорого: stack trace на штатный дубликат, и в Kafka — выбор
  между «уронить листенер» и «поймать всё подряд».
- **Коды возврата без типа (числа, строки).** Теряется исчерпывающесть: компилятор не подскажет, что появилась
  новая причина отклонения, которую забыли отобразить в problem+json.
- **Вердикты и в администрировании тоже.** Заставляет каждый контроллер панели вручную разворачивать вердикт в
  409/404 — много кода ради единообразия, которое здесь ничего не даёт.

## Последствия

**Положительные.** Логи не забиты трассировками штатных событий. Консьюмер не застревает на «отравленном»
сообщении, которое на самом деле просто отклонено. Причина отклонения — часть контракта, и её список конечен.

**Цена.** Вызывающий обязан разобрать вердикт — компилятор этого не потребует, если результат проигнорировать.
Смягчается тем, что точка входа одна (`MessagePipeline`), и её результат некуда деть.

## Как нарушение будет замечено

Unit-тесты pipeline проверяют каждый вид отклонения; тесты REST — соответствие кода в `problem+json`
канонической причине; тесты консьюмера — что отклонение приводит к коммиту, а не к повторной доставке.
