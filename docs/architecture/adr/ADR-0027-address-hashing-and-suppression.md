# ADR-0027. Адрес хешируется в одном месте; suppression имеет два семейства выборок

| | |
|---|---|
| **Статус** | Принято · реализовано |
| **Дата** | 09.08.2026 |
| **Требования SRS** | FR-5.1…FR-5.4, SEC-08, DB-05, EM-02, PU-04 |
| **Связанные решения** | [ADR-0012](ADR-0012-application-level-encryption.md), [ADR-0024](ADR-0024-email-smtp-decisions.md), [ADR-0025](ADR-0025-push-fanout-and-terminal-status.md) |

## Контекст

Suppression list сравнивает адреса тремя разными путями: путь отправки проверяет получателя, счётчики частоты
ключуются по нему, администрирование добавляет и снимает записи, а аудит SEC-08 фиксирует, чьи сообщения
смотрели. Если хоть один из путей посчитает хеш чуть иначе — с другим регистром, с `+` или без, с другой
нормализацией, — запрет будет молча ничего не находить. Это отказ, который не выглядит отказом.

## Решение

**Хеширование адреса живёт ровно в одном месте** — `application/service/support/RecipientAddresses`. SMS и EMAIL
нормализуются своими value objects домена (то есть теми же правилами, что и при приёме), push-токен непрозрачен
и хешируется как есть.

**У выборок suppression два семейства, и они читаются похоже, но означают разное:**

- `findActive…` — **путь отправки**: строка для канала **или** строка «все каналы», с учётом срока действия;
- `find…` — **путь администрирования**: ровно одна конкретная область канала, включая истёкшие строки, потому что
  именно с этой строкой столкнётся уникальный индекс при добавлении.

Перепутать их — значит либо не найти действующий запрет, либо получить конфликт индекса на пустом месте.

**Автоматические записи идут не через `ManageSuppressions`, а через `SuppressionRegistrar`**: провайдер, назвавший
адрес непригодным (§18.2 коды 20 и 7), жёсткий возврат почты (EM-02), инвалидированный push-токен. Регистратор
идемпотентен через `saveIfAbsent` (`ON CONFLICT DO NOTHING`) и записывает провайдера как `created_by`.
Достижим он из саги через `MessagePipeline.suppress` и из `ProcessProviderStatus` через
`ProviderStatusCommand.suppressAs`.

**Следствие suppression применяется до и независимо от смены статуса.** «Этот адрес мёртв» — утверждение об
адресе, поэтому отчёт, не меняющий статус сообщения, обязан всё равно остановить следующую отправку.

**Порядок фильтров фиксирован**: suppression → согласия → часы тишины → частотный лимит (`DeliveryFilters`).

**Часы тишины разрешаются клиент → поток → канал, и окно клиента побеждает** — оно единственное несёт часовой
пояс получателя. Это вся честная поддержка «локального времени», которую Модуль может дать: каждый принятый
MSISDN начинается с `9989`, то есть `Asia/Tashkent`, и флаг при этом всё равно едет в Playmobile.

`frequency_counter` агрегируется в почасовые корзины, а не по строке на отправку (объёмы §12.2), поэтому его
счёт — документированный потолок, а не точное число. `RetentionSweepScheduler` держит его и `dedup_registry` в
размере своих окон.

**PAN (SEC-05):** находка **всегда** считается метрикой (`MetricsPort.panDetected`) и **никогда** не логируется
текстом. Отклоняет ли она сообщение, решает `PanPolicy` — кроме SMS, где отклоняет всегда; тела шаблонов
проверяются безусловно.

`CustomerPreferencePort` — документированная заглушка (FR-8.2): реестр согласий принадлежит мастер-системе Банка
(открытый вопрос № 8), и превращать порт в такой реестр нельзя.

## Альтернативы

- **Хешировать по месту использования.** Ровно тот отказ, который описан в контексте: запрет, который ничего не
  находит, и никто не замечает.
- **Хранить адрес в suppression в открытом виде.** Второе хранилище персональных данных, теперь ещё и с другой
  ретенцией.
- **Одна универсальная выборка suppression.** Либо путь отправки начинает игнорировать строку «все каналы», либо
  администрирование перестаёт видеть истёкшую строку, с которой столкнётся индекс.
- **Автоматические записи через административный use case.** Тянет за собой требование актора-человека и запись
  аудита на каждый bounce.

## Последствия

**Положительные.** Запрет, поставленный из панели, из провайдера или из возврата почты, находится всеми путями
одинаково. Аудит SEC-08 может ключеваться хешем адреса — «кто смотрел этого клиента» становится одним
индексированным запросом.

**Цена.** По хешу нельзя восстановить адрес, поэтому экран suppression показывает то, что ввёл оператор, и
маскирует его на выходе. Почасовые корзины частотного лимита означают, что лимит — это потолок, а не точный счёт;
это задокументировано и осознанно.

## Как нарушение будет замечено

Unit-тесты проверяют, что все три пути дают один хеш для одного адреса. Интеграционные тесты покрывают оба
семейства выборок, включая строку «все каналы» и истёкшую строку. Тест PAN проверяет, что текст находки не
попадает в лог.
