# ADR-0032. Health-группы намеренно неравны: liveness не знает ничего внешнего

| | |
|---|---|
| **Статус** | Принято · реализовано |
| **Дата** | 09.08.2026 |
| **Требования SRS** | NF-05, NF-03, AD-03, OBS-04 |
| **Связанные решения** | [ADR-0003](ADR-0003-transactional-outbox.md), [ADR-0022](ADR-0022-passive-provider-health.md) |

## Контекст

В K8s три пробы означают три разных вопроса, и типичная ошибка — ответить на все одним индикатором «всё ли
хорошо». Последствие этой ошибки конкретное: при недоступности PostgreSQL kubelet начинает перезапускать поды,
и авария базы превращается в аварию базы **плюс** рестарт-цикл всего сервиса ровно в тот момент, когда команда
разбирается с базой.

## Решение

Группы наполнены по-разному и осознанно:

- **liveness — не знает ничего внешнего.** Отвечает только на вопрос «этот процесс жив и способен работать».
  Перезапуск пода из-за недоступной PostgreSQL заменяет одну аварию другой во время первой.
- **readiness — добавляет базу данных.** Инстанс без базы не может принять сообщение: непринятая транзакция
  означает непринятое сообщение (RPO, NF-03), поэтому такой под должен уйти из балансировки, но не
  перезапускаться.
- **Индикаторы брокера и провайдеров публикуются, но не входят ни в одну группу.** Outbox существует ровно затем,
  чтобы недоступность брокера не останавливала приём (AD-03) — выводить под из балансировки из-за брокера значит
  отменить смысл outbox. А провайдер недоступен на всех подах одинаково: вывести из балансировки нужно было бы
  все, что равно отказу сервиса вместо failover.

Эти индикаторы существуют для наблюдения: их читают дашборды и правила алертов (OBS-04), а не kubelet.

Плюс `graceful shutdown` с дообработкой сообщений в полёте (NF-05).

## Альтернативы

- **Одна общая проверка на все три пробы.** Описана в контексте: превращает деградацию зависимости в
  рестарт-цикл.
- **Включить брокер в readiness.** Останавливает приём при недоступном брокере — то есть ровно то, чего
  избегает outbox.
- **Включить провайдеров в readiness.** Все поды одновременно становятся неготовыми; failover при этом не
  срабатывает, потому что маршрутизировать больше некому.

## Последствия

**Положительные.** Авария зависимости остаётся аварией зависимости. Приём переживает недоступность брокера, а
падение провайдера обрабатывается failover, а не рестартами.

**Цена.** «Зелёный» liveness не означает, что сервис делает полезную работу, — поэтому наблюдение обязано
опираться на метрики backlog и алерты, а не на пробы. `BacklogMetrics` (возраст самой старой неопубликованной
строки outbox) существует именно для этого.

## Как нарушение будет замечено

Chaos-сценарии ставят PostgreSQL и брокер на `docker pause` и проверяют: под не перезапускается, приём при
недоступном брокере продолжается, а при недоступной базе под уходит из готовности. Правило алерта на возраст
backlog ссылается на раздел runbook.
