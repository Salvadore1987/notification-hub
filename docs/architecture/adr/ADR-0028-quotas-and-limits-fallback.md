# ADR-0028. Квоты — три измерения; ограничитель никогда не становится причиной остановки

| | |
|---|---|
| **Статус** | Принято · реализовано |
| **Дата** | 08.08.2026 |
| **Требования SRS** | FR-2.5, FR-2.6, IR-02, NF-02, NF-07 |
| **Связанные решения** | [ADR-0007](ADR-0007-configuration-in-postgres.md), [ADR-0029](ADR-0029-kill-switch-polarity.md) |

## Контекст

Ограничивать нужно в разных местах и по разным причинам: у направления есть бюджет (FR-2.6), у провайдера —
договорной TPS и антиспам-правила (FR-2.5, например 50 SMS в час на номер у SMS Gate), у REST-потока — лимит
запросов (IR-02). Эти ограничения независимы, и попытка выразить их одним счётчиком приводит к тому, что
исчерпание бюджета маркетинга останавливает OTP.

## Решение

**Квота — это три измерения, а не одно.** `QuotaGuard` проходит цепочку **поток → канал → провайдер**, и
`check` с `register` обязаны проходить **одни и те же области**: проверить по трём, а зарегистрировать по двум
значит расходовать бюджет, который никто не проверяет.

Поведение при исчерпании настраивается (блокировка с алертом либо только алерт) — как требует FR-2.6.

**Три ограничителя читают конфигурацию по форме «читаем раз в окно» и все три откатываются на конфигурацию
развёртывания**, если в реестре пусто или он недоступен:

- `StreamLimits` — лимиты REST на поток из `stream.rate_limit_config` (IR-02, ответ с `Retry-After`);
- `ProviderRuntimeSettings` — лимиты из `provider.rate_limit_config` и рычаги отправки (отправитель, приоритеты,
  веса, TTL по умолчанию) из `provider.endpoint_config`;
- `CachingProviderConfigRepository` — снимок маршрутизации.

Правило отката несущее: **ограничитель не имеет права стать причиной, по которой сообщения перестали идти.**
Недоступный реестр означает работу по значениям развёртывания, а не отказ в приёме.

Ровно одно исключение из этого правила — kill switch, и его полярность обратная по построению (ADR-0029).

**Троттлинг провайдера — это предел скорости выгрузки батча** (NF-02): Модуль обязан упираться в ограничение
провайдера, а не в собственную производительность.

## Альтернативы

- **Один общий счётчик на поток.** Не выражает ни договорного TPS провайдера, ни антиспам-правила на номер.
- **Квоты в Redis** (как допускает §10.1). Даёт точность и добавляет ещё одно хранилище состояния в поставку;
  на текущих объёмах PostgreSQL справляется, а решение остаётся открытым для детального проектирования.
- **Отказывать в приёме при недоступном реестре лимитов.** Превращает деградацию конфигурации в отказ сервиса.

## Последствия

**Положительные.** Исчерпание бюджета одного направления не задевает остальные. Ограничения провайдера
соблюдаются на всех инстансах, потому что счётчики общие. Недоступность конфигурации деградирует до значений
развёртывания, а не до простоя.

**Цена.** Счётчики квот — это запись в БД на горячем пути; они агрегированы по периодам, а не по событиям.
Откат на значения развёртывания означает, что при длительной недоступности реестра лимиты могут отличаться от
настроенных администратором — это видно в логе как явное сообщение об использовании отката.

## Как нарушение будет замечено

Unit-тесты `QuotaGuard` проверяют совпадение областей у `check` и `register`. Интеграционные тесты гасят реестр
и убеждаются, что приём продолжается по значениям развёртывания. Алерт OBS-04 на исчерпание квот.
