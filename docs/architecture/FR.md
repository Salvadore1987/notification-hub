# Функциональные требования (FR)

Документ сводит функциональные требования Модуля в один перечень с трассировкой «требование → реализация → проверка».
Источник требований — SRS [`docs/sms-notification-hub-spec.md`](../sms-notification-hub-spec.md) (v1.0, разделы 5–11);
здесь требования не переписываются заново, а фиксируются в формулировке, пригодной для приёмки, и связываются с кодом.

**Спецификация авторитетна.** Если этот документ и SRS расходятся — прав SRS, а расхождение является дефектом
документации и подлежит исправлению здесь.

## Как читать

| Обозначение | Значение |
|---|---|
| ✅ | реализовано и покрыто тестами |
| 🟡 | реализовано частично, ограничение описано в строке |
| ⏳ | известный незакрытый долг — см. [раздел 12](#12-известные-долги) |
| 🔵 | сознательно отнесено на фазу 2 |
| ⛔ | вне объёма разработки по решению Банка |

Колонка «Реализация» указывает Gradle-модуль и ключевой класс; полные соглашения слоёв — в
[`CLAUDE.md`](../../CLAUDE.md), решения — в [`adr/`](adr/), нефункциональная часть — в [`NFR.md`](NFR.md).

## 1. Приём рассылок от систем-источников (SRS §7.1)

| ID | Требование | Статус | Реализация |
|---|---|---|---|
| FR-1.1 | Приём единичных сообщений и батчей через Kafka (основной способ) и REST (синхронный, в т. ч. OTP) | ✅ | `:adapter:in:kafka`, `:adapter:in:rest`; use cases `SubmitMessage`, `SubmitBatch` |
| FR-1.2 | Модуль не формирует получателей, контент и расписание; допускается контент по шаблону (`templateId` + переменные) | ✅ | `MessagePipeline` → `TemplateApplier`; аудитории резолвит источник (см. FR-8.11) |
| FR-1.3 | Регистрация системы-источника как входящего потока: канал и провайдер по умолчанию, статус подключения | ✅ | `ManageStreams` / `StreamConfigService`, таблица `stream`, раздел «Входящие потоки» в панели. Способ интеграции не хранится — поле было описательным и удалено ([ADR-0045](adr/ADR-0045-drop-stream-integration-type.md)) |
| FR-1.4 | Валидация при приёме: обязательные поля, форматы адресов, длина контента, существование потока и шаблона; ошибка синхронно (REST) либо событием (Kafka) | ✅ | Value objects домена + `MessageValidator`; `InboundContractException` с указателем на поле, REST → problem+json, Kafka → `comm.inbound.parse-error.v1` |
| FR-1.5 | Идемпотентность по `(streamId, externalMessageId)` либо `dedupKey` в окне дедупликации (по умолчанию 24 ч) → `DUPLICATE` без повторной отправки | ✅ | `DeduplicationService`, `DedupRegistryPort`, таблица `dedup_registry`; окно — из `:adapter:out:policy` |
| FR-1.6 | Приём батча: заголовок + элементы чанками; батч виден с момента приёма с прогрессом обработки | 🟡 | `SubmitBatchService`, `POST /batches`, `POST /batches/{id}/items`; прогресс сверх `processed` — долг ⏳ [Д-2](#12-известные-долги) |
| FR-1.7 | REST-приём OTP: подтверждение ≤ 200 мс (p99), приоритетная обработка | ✅ | Приём и постановка в обработку разделены (outbox), класс трафика из топика или документа; измеряется метрикой `accept` |

| ID | Требование | Статус | Реализация |
|---|---|---|---|
| FR-2.1 | Несколько независимых провайдеров в рамках канала, каждый — свой профиль: учётные данные, endpoint, лимиты, тарифы | ✅ | Агрегат `Provider`, таблица `provider`, `ManageProviders` / `ProviderConfigService`; тип адаптера предлагается по развёрнутым бинам — `GetDeployedAdapters` / `DeployedAdapterQueryService` (ADR-0042) |
| FR-2.2 | Основной и резервные провайдеры канала с настраиваемым порядком fallback | ✅ | `ChannelConfig.fallbackOrder`, доменный `FallbackChain` |
| FR-2.3 | Балансировка между активными провайдерами: round-robin, по весам, по стоимости | ✅ | Доменный `Router` + `RoutingRotation`; стратегия — на канале и/или потоке |
| FR-2.4 | Канал и провайдер по умолчанию для каждого входящего потока | ✅ | Агрегат `Stream`, применяется в `MessagePipeline` до маршрутизации |
| FR-2.5 | Лимиты и троттлинг скорости на уровне провайдера (TPS, сообщений в минуту), с учётом ограничений провайдера | ✅ | `ProviderThrottle` в `:adapter:out:provider:support`, значения из `provider.rate_limit_config` через `ProviderRuntimeSettings` |
| FR-2.6 | Квоты и бюджеты по количеству и стоимости в разрезе канал / провайдер / поток; поведение при исчерпании настраивается | ✅ | `QuotaGuard` (три измерения: поток → канал → провайдер), `QuotaCounterPort`, таблица `quota_counter` |
| FR-2.7 | Включение и выключение провайдера и канала на лету, режим обслуживания | ✅ | Статусы `provider.enabled` / `channel.status`, применение ≤ 30 с через `CachingProviderConfigRepository` (NF-07) |

## 4. Шаблоны и персонализация (SRS §7.4)

| ID | Требование | Статус | Реализация |
|---|---|---|---|
| FR-4.1 | CRUD шаблонов с версионированием; локали RU/UZ/EN; DRAFT → ON_REVIEW → PUBLISHED → ARCHIVED; отправка только по PUBLISHED | ✅ | `Template` / `TemplateVersion` (инвариант «одна отправляемая версия на локаль» — в домене), `ManageTemplates`, `TemplateApplier`; версия рендера фиксируется в `message.template_version_id` (§10.1) — `Message.applyTemplateVersion` из `TemplateOutcome.version` |
| FR-4.2 | Ревью: автор не публикует собственный шаблон (maker/checker) | ✅ | Автор и ревьюер берутся из `Actor`, не из полей команды; безымянный актор (сам Модуль) не может ни того, ни другого. Связь отправленного с актом ревью даёт `message.template_version_id`: «код + локаль» указывают на версию, опубликованную сейчас, а не на ту, которой отправили ([ADR-0026](adr/ADR-0026-template-publication-rules.md)) |
| FR-4.3 | Подстановка merge-полей из переменных источника; строгий режим — отсутствие переменной есть ошибка валидации | ✅ | `TemplateApplier` → отклонение `TEMPLATE_VARIABLE_MISSING`; админский предпросмотр намеренно нестрогий |
| FR-4.4 | Для SMS — текст по локалям; предпросмотр с расчётом сегментов и стоимости по действующим тарифам | ✅ | `GetTemplates` / `TemplateQueryService` + доменный `SegmentCalculator` и тарифы провайдеров, котировка на провайдера с флагом `selectable` |
| FR-4.5 | Соответствие шаблонов Модуля шаблонам провайдера (Playmobile `template-id`), хранение статуса согласования | ✅ | `ProviderTemplateBinding` в профиле провайдера; само согласование — организационный процесс вне Модуля |
| FR-4.6 | Миграция существующей базы шаблонов Банка (≈470 шаблонов) | ✅ | `ImportTemplates` + `:adapter:in:importer` (CSV по именам колонок, идемпотентность по формулировке, отчёт о плохих строках); off по умолчанию (`commhub.import.templates.enabled`) |

## 13. Разделы админ-панели (SRS §11.2)

Все двенадцать разделов реализованы (`web/src/pages/<section>/`), маршруты и пункты меню объявлены один раз в
`web/src/layout/navigation.tsx`: дашборд, рассылки, сообщения, DLQ, входящие потоки, каналы и провайдеры,
маршрутизация, шаблоны, suppression list, статистика и отчёты, аудит, администрирование.

Отклонения от §11.2, принятые сознательно:

- **Пользователей и паролей в Модуле нет** — §10.1 это допускает: идентичность приходит из корпоративного SSO,
  а отображение групп в роли является конфигурацией развёртывания и показывается в разделе «Администрирование» только для чтения.
- **Экспорт статистики — CSV**; XLSX не производится (см. [ADR-0018](adr/ADR-0018-admin-masking-and-paging.md)).
- **Дашборд опрашивается раз в 15 с** (рекомендация самого контракта), SSE не используется; отсутствие OTP-трафика
  показывается как «нет трафика», а не как ноль латентности.
- **Алертов на дашборде нет**: OBS-04 уже вычисляет Alertmanager, и он видит то, чего запрос в БД увидеть не может, —
  например, поды, переставшие отдавать метрики.
